#+title: Generated Correlator Implementation Plan

This node plans the next correlator rewrite.  It connects the public
[[id:20260603T094138.285453][Correlators]] interface, the current [[id:20260606T064107.303587][Wick]]
runtime, the preset data in [[id:20260606T163500.000000][Presets]], and the
median benchmark node [[id:20260607T130000.000000][Correlator Performance
Benchmarks]].  The goal is not a new special case for [[id:20260606T183200.000000][Free
Boson Preset]] or [[id:20260606T183300.000000][BC]]; it is a generated
correlator kernel for free-field CFTs with user-written physics data and
private performance machinery.  Both comptime lowering and runtime traversal
must be generic over operator families, supports, Wick factor vocabularies,
zero-mode evaluators, topology data, and boundary extensions.

* Objective

The user writes operator families, Wick contractions, zero-mode data, boundary
data, and optional rendering preferences.  The system generates the compact
runtime tables, pair caches, branch walkers, zero-mode pruning data, and result
stream adapters at comptime.

The generated runtime must preserve the current performance envelope.  A change
is not complete unless the median benchmark runner remains green and the emitted
symbolic stream is equivalent to the current stream.

* Non-goals

- Do not expose pair caches, branch-state storage, rule-index arrays, residual
  masks, or zero-mode dry-run machinery to theory authors.
- Do not materialize full symbolic expressions by default.
- Do not make the correlator depend on free-boson names, =bc= names, sphere
  topology, or a fixed set of tensor factors.
- Do not replace the current procedural runtime with a dynamic interpreter.
  The generated code should still be simple loops over compact arrays.

* Target user-side shape

The public specification should be close to the physics notation and compact
enough to read as a small DSL.  A theory author should describe fields,
contractions, zero modes, and topology data.  They should not describe how to
index rules, cache pairs, allocate branch storage, or specialize traversal.

The DSL has five declaration forms:

- =parameter=: named scalar, tensor, rank, modular, or topology data used by
  rules and zero modes.
- =operator=: a local field family with support, label schema, statistics, and
  optional generated builder name.
- =wick=: one contraction rule between two operator families, written as a
  finite sum of terms.
- =zeroMode=: one residual base-case rule, written as a consumption and
  emission declaration.
- =surface=: topology/config data that selects coordinate kernels, zero-mode
  sectors, normalization factors, and modular parameters.

The public API should make the common case look like this:

#+begin_src zig
pub const X = cft.defineTheory(.{
    .parameters = .{
        parameter(.alpha_prime, .scalar),
        parameter(.dimension, .rank),
    },

    .operators = .{
        operator(.dX, .{
            .labels = .{ label(.mu, .index) },
            .support = .holomorphic,
            .statistics = .bosonic,
        }),
        operator(.expX, .{
            .labels = .{ label(.k, .momentum) },
            .support = .bulk_pair,
            .statistics = .bosonic,
        }),
    },

    .wick = .{
        wick(.dX, .dX).term(.{
            .scalar = -alpha_prime / 2,
            .coordinate = pole(.left_z, .right_z, -2).differentiate(.left, .right),
            .tensor = metric(.left.label(0), .right.label(0)),
        }),

        wick(.dX, .expX).term(.{
            .scalar = -i * alpha_prime / 2,
            .coordinate = pole(.left_z, .right_z, -1).differentiate(.left),
            .tensor = momentumIndex(.right.label(0), .left.label(0)),
            .residuals = .{ .right },
        }),
    },

    .zero_modes = .{
        zeroMode(.free_boson_constant, .{
            .consumes = .{ .expX },
            .emits = momentumDelta(.{ .momenta = labels(.expX, .k) }),
        }),
    },
});
#+end_src

The exact spelling can change, but the shape should remain this tight.  The
outer declarations are data.  The inner expressions are algebraic descriptions
of coefficient factors.

* DSL vocabulary

The DSL should have a small fixed core.

** Operator declarations

An operator declaration names one family and its runtime labels:

#+begin_src zig
operator(.b, .{
    .support = .holomorphic,
    .statistics = .fermionic,
})

operator(.expX, .{
    .support = .bulk_pair,
    .statistics = .bosonic,
    .labels = .{ label(.k, .momentum) },
})
#+end_src

From this, comptime generates compact kind ids, insertion packers, label
packing, and public builders such as:

#+begin_src zig
try X.op.dX(&local, mu, 0, z);
try X.op.expX(&local, k, z, zbar);
try Ghost.op.b(&local, 0, z);
try Ghost.op.c(&local, 0, z);
#+end_src

The user should not write the builder implementation.  They only declare the
operator family and support.

** Wick declarations

A Wick rule is a finite sum of factor products.  The factor language should be
small and explicit:

#+begin_src zig
wick(.dX, .dX).term(.{
    .scalar = -alpha_prime / 2,
    .coordinate = pole(z(.left), z(.right), -2).differentiate(.left, .right),
    .tensor = metric(label(.left, .mu), label(.right, .mu)),
})

wick(.dX, .expX).term(.{
    .scalar = -i * alpha_prime / 2,
    .coordinate = pole(z(.left), z(.right), -1).differentiate(.left),
    .tensor = momentumIndex(label(.right, .k), label(.left, .mu)),
    .residuals = .{ .right },
})
#+end_src

The DSL terms lower to compact factor descriptors:

- scalar factors;
- coordinate kernels;
- tensor factors;
- action factors;
- residual operator references.

Multiple terms mean an explicit sum.  Multiple factors inside one term mean a
product.  The user never writes =term_index=, rule payloads, candidate lists, or
branch signs.

** Coordinate kernels

Coordinate kernels are declared abstractly and lowered by support and surface:

#+begin_src zig
pole(z(.left), z(.right), -1)
green(.torus, z(.left), z(.right), .{ .modulus = .tau })
greenExp(.torus, z(.left), z(.right), .{ .modulus = .tau })
primeForm(z(.left), z(.right), .{ .modulus = .tau })
#+end_src

The sphere and torus should use the same Wick DSL shape.  Only the surface
declaration changes which coordinate kernel records are generated.  For torus
free boson and torus =bc=, the stringbook fixes the kernel definitions and
normalizations.

** Tensor and scalar factors

The core factor constructors should cover the current cases without exposing
internal unions:

#+begin_src zig
metric(label(.left, .mu), label(.right, .nu))
momentumIndex(label(.right, .k), label(.left, .mu))
momentumPair(label(.left, .k), label(.right, .k))
projectorMetric(config(.neumann_projector), label(.left, .mu), label(.right, .nu))
phaseBilinear(label(.left, .charge), label(.right, .charge), .spin_structure)
cocycle(label(.left, .charge), label(.right, .charge), .table)
#+end_src

These names describe symbolic factors.  Lowering decides the exact compact
payload layout.

** Zero-mode declarations

Zero modes should be declared as residual consumers with symbolic emissions:

#+begin_src zig
zeroMode(.sphere_bc_top, .{
    .sector = .sphere,
    .consumes = exactly(3, .c),
    .emits = bcTopForm(.{ .support = .sphere_holomorphic }),
})

zeroMode(.torus_bc_top, .{
    .sector = .torus,
    .consumes = torusGhostZeroModes(.b, .c),
    .emits = torusBcZeroModeFactor(.{ .modulus = .tau }),
})

zeroMode(.free_boson_constant, .{
    .sector = .torus,
    .consumes = any(.expX),
    .emits = momentumDelta(.{ .momenta = labels(.expX, .k), .normalization = stringbook(.torus_free_boson) }),
})
#+end_src

The =torus_bc_top= and torus free-boson normalization declarations must cite
the stringbook formulas in prose in the relevant org node.  The DSL names can
be compact, but the convention source must be unambiguous.

** Surface declarations

Surface data should be declared once and selected by correlator config:

#+begin_src zig
surface(.sphere, .{
    .coordinate_model = .rational,
})

surface(.torus, .{
    .coordinate_model = .elliptic,
    .moduli = .{ parameter(.tau, .modular) },
    .source = .stringbook,
})
#+end_src

The surface declaration lowers to opaque topology/config data.  Runtime does
not branch on =sphere= or =torus= names; it receives lowered support ids,
coordinate-kernel descriptors, and zero-mode procedures.

* DSL non-leakage rules

The user-side DSL must not expose:

- compact operator kind ids;
- label-span arithmetic;
- support masks;
- rule-index tables;
- candidate pair tables;
- payload ids;
- branch-state size declarations;
- pair-cache declarations;
- zero-mode dry-run procedures;
- sink fast-path declarations.

If a computation needs larger internal storage, the public declaration is a
single budget choice:

#+begin_src zig
.budget = .large
#+end_src

The generated lowering explains what this budget expands.  The user should not
tune =max_accumulated_terms=, =max_cached_pair_terms=, or residual-array sizes.

* Generalization requirements

The generated correlator must support more than sphere =bc= and free bosons.
The internal model should therefore be expressed in these general terms:

- Operator family: statistics, support, insertion shape, label schema,
  quantum-number metadata, and optional normal-order behavior.
- Wick rule: ordered or symmetric pattern, finite sum of primitive terms,
  scalar factors, coordinate kernels, tensor factors, action factors, and
  residual operator references.
- Zero-mode rule: residual-consumption predicate, validation pass, emission
  pass, and optional empty-residual emission.
- Topology/config: surface or boundary support, projectors, normalization
  data, spin-structure data, and rank-dependent constants.
- Output sink: branch sink, event sink, renderer sink, materializing sink, and
  benchmark sink.

This shape covers first-order systems, free fermions, beta-gamma systems,
bosonized superghosts, spin-structure factors, boundary fields, projected
boundary conditions, and profile/background insertions without changing the
Wick traversal algorithm.

Generality is a design invariant, not a late cleanup step.  Every comptime pass
and every runtime procedure must be written against the lowered abstract model,
not against preset names or the current examples.  Free boson and sphere =bc=
are regression fixtures for semantics and speed; torus free boson and torus
=bc= are the first generalization fixtures.  The stringbook is the source of
truth for the torus examples: its torus Green functions, ghost zero-mode
saturation, normalization conventions, and modular data determine the spec.
None of these examples are templates for hard-coded branches.

* Generic comptime design

Comptime logic must be factored by abstract roles:

- =operator schema lowering= handles names, supports, label schemas,
  statistics, and insertion shapes for any theory.
- =factor vocabulary lowering= maps user-declared scalar, coordinate, tensor,
  action, and residual factors into compact descriptors.  New factor families
  must be added by extending the factor vocabulary, not by editing traversal.
- =rule graph lowering= builds kind-pair candidate tables from Wick rules
  without knowing whether a kind is =dX=, =b=, a torus =b=, a spin-structure
  field, or a boundary field.
- =zero-mode lowering= generates accept and emit procedures from residual
  consumption rules.  The base-case algorithm sees only these procedures and
  survivability bits.
- =topology/config lowering= provides opaque config values, rank sources,
  projectors, spin structures, and normalizations.  Runtime code treats these
  as resolved payloads.
- =budget lowering= computes stack bounds from the lowered graph and selected
  budget class, independent of the preset that produced the graph.

No comptime pass may inspect a theory namespace string such as =free_boson= or
=bc=.  A pass may inspect declared capabilities, for example whether a factor
kind is coordinate-like, tensor-like, residual-producing, mandatory before base,
or zero-mode consumable.

* Generic runtime design

Runtime correlator logic must depend only on compact lowered data:

- ordered =LocalOp= records;
- kind ids and support ids;
- normal-order group ids;
- fermion parity bits;
- precomputed pair candidates;
- factor descriptor slices;
- zero-mode accept and emit callbacks;
- sink capabilities.

The runtime may branch on generic properties, for example =has_residuals=,
=is_fermionic=, =has_branch_sink=, or =pure_full_contraction=.  It may not branch
on operator names, theory names, surface names, or preset-specific factor
names.  A new theory should become runnable by adding spec data and factor
lowering support, not by modifying the Wick branch walker.

* Data flow

There are four layers.

1. =spec=: user-facing theory data.  This layer is declarative and contains no
   branch-walker or cache details.
2. =lowering=: comptime validation and table construction.  This layer assigns
   compact ids, resolves labels and coordinate slots, computes pair candidate
   tables, and derives budgets.
3. =runtime=: generated procedural code.  This layer walks bitsets, emits
   symbolic factors, prunes zero-mode failures, and dispatches to branch or
   event sinks.
4. =sinks=: output adapters.  This layer counts, renders, serializes, or
   materializes the symbolic stream.

Only =spec= and selected =sinks= are part of the user-facing API.

* Lowering algorithms

** Operator lowering

For each operator family, comptime lowering assigns a compact kind id and
records:

- support tag and insertion slots;
- label schema and label slot count;
- statistics bit;
- zero-mode-consumable bit;
- normal-order compatibility bit;
- renderer metadata.

Generated operator builders use this table to construct =LocalOp= values.  The
current manual helpers such as family-specific =kind=, =singleInsertion=, and
=pairInsertion= disappear from presets.

This pass must be independent of concrete presets.  Holomorphic fields,
antiholomorphic fields, bulk-pair fields, boundary fields, and future insertion
shapes are represented by support descriptors and insertion packers generated
from the operator schema.

** Wick-rule lowering

For each Wick rule, lowering resolves symbolic references into compact
descriptors:

- left and right kind ids;
- support compatibility;
- primitive term ranges;
- scalar, coordinate, tensor, action, and residual ranges;
- mandatory-before-base flag;
- fermion sign behavior.

The output is a rule graph:

- =first_rule_by_kind[kind]= and =next_rule= lists for fast candidate lookup;
- =pair_key=(left_kind,right_kind)= to primitive terms;
- per-term factor slices stored in structure-of-arrays form;
- optional reversed rule records when a rule is symmetric.

The runtime must not search strings or high-level union trees in the inner
loop.  It walks the lowered arrays.

This pass must not privilege free-boson or =bc= contractions.  A differentiated
pole, a Green kernel, a spin-structure factor, a cocycle, and a profile action
are all just lowered factor descriptors with different emit procedures.

** Budget derivation

Budgets are generated from the lowered rule graph:

- maximum operator count from the selected public budget;
- maximum pair depth = floor(max_operator_count / 2);
- maximum pair candidates from reachable kind pairs;
- maximum primitive terms per branch;
- maximum scalar, coordinate, tensor, action, and residual factors per branch;
- maximum pair-cache entries;
- maximum zero-mode residuals.

When a theory exceeds a budget, the compile error should name the limiting
quantity and the theory feature that caused it.  The user should raise one
budget class, not individual internal array sizes.

** Zero-mode lowering

A zero-mode rule is lowered into two generated procedures:

- =accept=: dry-run validation and residual-consumption only;
- =emit=: emits zero-mode factors after validation succeeds.

This preserves the current important invariant: no zero-mode factor is emitted
for a branch that later fails.  The lowering pass also computes the
zero-mode-survivable bit per operator kind, allowing early branch pruning.

The zero-mode interface must support more than momentum conservation and
=c=-ghost top forms.  A zero-mode rule can consume residuals by kind, label
predicate, insertion support, topology sector, or declared quantum data.  The
runtime only asks whether validation succeeds and then replays emission.

* Runtime algorithms

** Branch traversal

The runtime keeps the current bitset-oriented traversal:

- =live_mask= stores operators still present in the branch.
- =first_live= chooses the next operator deterministically.
- Candidate pairs are read from lowered kind-pair tables.
- Normal-order groups reject internal contractions.
- Residual operators are added by term descriptors, not allocated.
- Fermion signs are computed from skipped live fermions and branch parity.
- A base case is attempted only when all live operators are zero-mode
  survivable or absent.

The traversal remains generic because it only sees kind ids, factor
descriptors, support slots, and zero-mode callbacks.

The branch walker is therefore shared by free bosons, first-order systems,
fermions, superghosts, boundary extensions, and mixed product theories.  Any
special theory behavior must appear as lowered data or factor emission code,
not as a new traversal branch.

** Full-contraction fast path

If lowering proves that a call is pure full contraction, with no optional
residual search, the runtime uses the accumulated full-contraction path:

- append each primitive pair term to a stack-backed branch object;
- cache repeated pair payloads inside the branch object;
- emit one branch object when the base case succeeds;
- replay as primitive events when the sink lacks branch support.

This is the path responsible for current =dX= and =bc= performance.  It must be
preserved.

** Residual and mixed path

When residuals can survive, the same branch object is still used, but the base
case runs zero-mode validation on the residual cursor.  Exponential and profile
cases should not be special-cased in traversal; they are generated from rule
metadata.

** Sink dispatch

The runtime emits symbolic data in two equivalent forms:

- Branch form: one accumulated product per successful Wick/base branch, plus
  zero-mode factors.
- Event form: primitive term boundary, scalar factors, coordinate factors,
  tensor factors, action factors, residual refs, zero-mode factors, base end.

Branch form is a performance optimization and a compact symbolic representation.
Event form is the canonical fallback.  A branch sink must be replayable into
the event sink with identical semantics.

* Symbolic output plan

The kernel emits symbolic factors, not pretty strings.  A correlator result is:

#+begin_src text
sum branch
branch = product(wick factors) * product(zero-mode factors)
wick factor = scalar * coordinate kernels * tensor factors * actions * residual refs
#+end_src

The first rendering target is a lightweight renderer sink that prints this
stream as a readable expression for small cases.  It should be explicitly
bounded and should refuse large outputs unless the user opts in.

The default API should support:

#+begin_src zig
try X.correlator(&X.config.sphere, ops, sink);
const result = try X.correlatorResult(&X.config.sphere, ops, allocator, .small);
try result.writeMathematica(writer);
try result.writeLatex(writer);
#+end_src

The streaming API remains primary for large computations.  The materialized
result API is a convenience layer with explicit memory limits.

* Review checklist

Before merging a milestone:

- Does the user-facing spec mention only physics data?
- Are all generated tables private?
- Does the runtime inner loop walk compact arrays and bitsets?
- Are zero modes dry-run validated before emission?
- Can the branch stream replay to the event stream?
- Did the median benchmark run after the change?
- Did any new result-inspection path allocate a large expression by default?
