#+title: Lisp CFT DSL Specification

* Purpose

This node specifies the Lisp-facing CFT language and the Zig boundary it
generates.  It extends the public-surface requirements in
[[id:20260607T170000.000000][CFT API Leakage Handoff]] and the generated-kernel plan in
[[id:20260607T140000.000000][Generated Correlator Implementation Plan]].

The central design rule is:

- Lisp owns the compact user language, inference, symbolic operator data, and
  expression conversion.
- Zig owns typed descriptor lowering, validation, table generation, and the
  fast runtime.

The user should not write verbose declaration records just to state a familiar
contraction.  The surface must be close in effort to the old Mathematica style,
but it must be genuine Lisp: concise forms, macros, first-class data, and no
Mathematica syntax embedded in Lisp.

The scope of this language is the definition of a worldsheet CFT, not the
whole perturbative sigma-model calculation.  Pure-spinor and NLSM modules are
built around perturbation theory about a free or otherwise controlled base CFT.
Those modules should own the perturbative expansion, regularization choices,
background-field expansion, integrated deformation bookkeeping, and loop
organization.  The CFT DSL supplies the base theory services they need:
operators, normal ordering, correlators, OPEs, selection rules, zero-mode
saturation, and basis generation.

Generated Zig is not optimized for human beauty.  It is optimized as a clear
machine-generated boundary: Lisp emits explicit descriptor data, Zig validates
it at comptime, lowers it into compact tables, and feeds those tables to the
runtime.  Repetitive generated Zig is acceptable when the Lisp surface stays
crisp and the runtime data path stays lean.

* Current Zig Fit

The current Zig design is a good fast backend, but it is not yet a seamless
endpoint for the Lisp DSL.

What is already aligned:

- =shared.declare= has the right kind of internal metadata: operators, Wick
  rules, zero-mode rules, surfaces, config entries, composition helpers, and
  opaque config handles.
- The runtime correlator is generic over compact operator records and lowered
  rule tables.  It is not tied to the names =dX=, =bc=, or =eta_xi=.
- Opaque public =LocalOperator=, =OperatorList=, and config handles keep most
  engine storage hidden.
- Product and boundary composition already flow through private merge helpers.

What is not enough for Lisp:

- =shared.declare.Spec= is too low-level for user language generation.  It
  already expects compact kind ids, low-level support enums, fixed label-kind
  tags, prebuilt =wick.Expr= payloads, and specialized zero-mode payloads.
- The current handwritten presets mix three jobs: physics declarations, Zig
  helper functions, and lowered runtime storage.  A Lisp generator could emit
  code shaped like those files, but that would be ad hoc and brittle.
- The current result API exposes the sink protocol shape.  Lisp should not
  implement =emitWickTermStart=, branch replay, residual callbacks, or resolved
  factor unions.
- Names passed to =Local.coord("z")=, =Local.index("mu")=, and similar helpers
  are not preserved in the runtime result path.
- The current label vocabulary is too small for future theories.  It has
  =index=, =momentum=, and =profile=, but the full DSL needs charges, spinor
  labels, lattice vectors, current algebra indices, Chan-Paton labels, picture
  labels, discrete sectors, and user scalar parameters.
- Weight and quantum-number rules are not yet first-class in the executable
  preset layer.  This matters immediately for =expX=, whose conformal weight
  depends on the supplied momentum.

Conclusion: the Lisp side should not generate today's handwritten preset files
line by line.  It should generate a normalized Zig =CFTSpec= or =BCFTSpec=
module.  Zig comptime then lowers that spec into the current runtime tables.
The current =shared.declare= layer can be the first lowering target, but it
must be reached through a cleaner spec frontend.

* Language Layers

The DSL has three layers.

** Surface Lisp

This is what users write.  It is compact and equation-like.  It uses Lisp forms
and macros, not property-list boilerplate.

Example:

#+begin_src lisp
(defcft free-fermion-10
  (source stringbook)
  (sphere)

  (fermion psi (mu z) :h 1/2)

  (wick (psi mu z) (psi nu w)
    (/ (eta mu nu) (- z w))))
#+end_src

The form declares that =psi= is fermionic, has one non-coordinate label =mu=,
is inserted at =z=, has weight \(1/2\), and contracts with itself through the
metric tensor and coordinate pole.  The user does not declare that =z= and =w=
are coordinates or that =mu= and =nu= are indices; those are inferred from the
field signature and tensor use.

** Normalized Lisp IR

Macros expand the surface into explicit typed data:

- theory name and convention source;
- surfaces and modular parameters;
- field families;
- field argument roles;
- weight and quantum-number rules;
- Wick equations as sums of products of symbolic factors;
- zero-mode saturation rules;
- named operator templates;
- reusable calculation operator data.

This IR is still Lisp-side and user-facing enough to inspect.  It is not the
Zig engine layout.

** Generated Zig Spec

The normalized IR emits Zig with:

- =CFTSpec= or =BCFTSpec= declarations;
- generated field constructors for ABI calls;
- result adapters;
- validation tests for the generated module;
- no hand-written branch traversal, pair-cache storage, or residual-mask
  procedures.

Zig comptime lowers the spec to compact storage: kind ids, label schemas,
operator packers, pair lookup tables, zero-mode tables, branch limits, and
runtime configs.

The emitted Zig should be deterministic and explicit, not pretty.  The contract
is the descriptor schema, not a second user-facing Zig language.

* Genericity Requirement

The Lisp-to-Zig layer must be a compiler for a small physics IR, not a list of
special cases for known CFTs.  Adding a theory must normally add declarations
or library macros written in the same DSL that users can write.  It must not
add branches such as "if theory is eta-xi", "if theory is SO32", or "if field is
spin-field" inside the generic lowering path.

The fixed compiler vocabulary is:

- field families, statistics, support, coordinate arity, and label roles;
- surfaces, moduli, boundary data, and gluing maps;
- scalar, tensor, kernel, cocycle, and residual-operator factor expressions;
- weight rules and quantum-number rules;
- Wick, OPE, and zero-mode rules as typed equations;
- operator families, normal-ordered composites, descendants, integrated
  operators, and unintegrated operators;
- basis rules, grading rules, and quotient relations;
- representation, lattice, and tensor references owned by tensor-code;
- named operator templates and first-class operator values;
- result expression node kinds.

A new CFT is valid for the DSL when it can be expressed with that vocabulary.
If it cannot, the correction is to add one generic vocabulary item or backend
primitive, then use it as data.  The correction is not to add a theory-named
emitter.

** Surface Presets

Library presets such as =free-boson-10=, =eta-xi=, =rns-superghost=, and
=so32-fermions= are surface packages.  They may provide concise macros and
default declarations, but those macros expand to the same normalized IR as
ordinary user forms.

Allowed:

#+begin_src lisp
(use-cft-preset stringbook:rns-flat)
#+end_src

which expands to declarations for free bosons, matter fermions, ghosts, and
superghosts.

Not allowed:

#+begin_src lisp
(when (eq theory 'rns-flat)
  (emit-rns-specific-zig ...))
#+end_src

Theory names may occur in preset packages, documentation, and tests.  They must
not occur in the generic IR normalizer, Zig emitter, ABI generator, or runtime
engine except as user-visible names stored in symbol tables.

** Generic Lowering Pipeline

The compiler pipeline is fixed:

1. Parse surface forms into generic AST nodes.
2. Infer roles for coordinates, labels, moduli, parameters, and tensors.
3. Normalize to the Lisp IR.
4. Validate the IR against generic capability tables.
5. Emit a deterministic Zig =CFTSpec= and ABI wrapper from the IR.
6. Let Zig comptime lower =CFTSpec= into compact runtime tables.

The lowerer dispatches on IR node kind, never on CFT name.  For example,
=SO32= appears only as a representation reference attached to a label role and
tensor factor.  Spin fields appear as fields with spinor labels, branch-cut
kernels, and residual-operator OPE terms.  Eta-xi appears as a first-order
fermion system with a constant zero mode and rational or elliptic kernels.

** Lisp Compiler Responsibilities

The Lisp compiler owns:

- parsing compact forms;
- expanding user and library macros;
- inferring ordinary roles;
- normalizing factor expressions;
- checking arity, surface compatibility, label consistency, and zero-mode
  requirements;
- expanding =defop= templates into operator data;
- normalizing basis-generation declarations into graded vector-space data;
- preserving user names;
- generating the high-level Zig spec and the stable ABI wrapper.

The Lisp compiler does not own:

- Wick traversal;
- OPE traversal;
- basis enumeration kernels;
- zero-mode branch search;
- pair-cache storage;
- tensor representation algebra;
- special physics formula generation by theory name;
- engine result sink internals;
- Zig packed layouts.

Any formula specific to a theory must live either in the DSL declarations or in
a generic tensor/kernel primitive that is usable by unrelated theories.

** Boundary To Perturbative Modules

Pure-spinor-code and NLSM-code should consume this DSL through a CFT service
interface.  They should not extend the CFT DSL into a general action language.

The CFT layer owns:

- base fields and their OPE or Wick rules;
- composite operator definitions;
- BRST currents and other conserved currents as CFT operators;
- zero-mode and selection rules;
- conformal weights and other gradings;
- basis generation modulo declared null, gauge, BRST-exact, total-derivative,
  equation-of-motion, or pure-spinor-constraint relations;
- correlator and OPE evaluation for finite operator insertions.

The perturbative modules own:

- choosing the base CFT;
- declaring the perturbing integrated operator;
- expanding =exp(-S_int)= into insertions;
- organizing loop order and degeneration limits;
- applying regularization and counterterms;
- mapping geometric or background-field data to CFT operator coefficients.

The boundary should therefore look like this:

#+begin_src lisp
(defcft ps-flat-base
  ...
  (current Q (z) :brst
    (R (lambda alpha z) (d alpha z)))
  (relation (pure-spinor lambda gamma))
  (basis vertex
    :grade ((ghost-number 2) (weight 0) (hbar 0))
    :mod ((Q-exact) (gauge) (pure-spinor-constraint))))

(defperturbation ps-curved-bg
  :base ps-flat-base
  :integrated (V-curved-background fields)
  :order alpha-prime)
#+end_src

Only =defcft= belongs to this specification.  =defperturbation= is sketched to
make the ownership boundary explicit.

* Core Surface Syntax

** Theory Declarations

#+begin_src lisp
(defcft eta-xi
  (source stringbook)
  (sphere)
  (torus tau)

  (fermion eta (z) :h 1)
  (fermion xi  (z) :h 0 :zero constant)

  (fermion etab (zb) :h 1 :bar)
  (fermion xib  (zb) :h 0 :bar :zero constant)

  (wick (eta z) (xi w)
    (/ 1 (- z w)))

  (wick (etab zb) (xib wb)
    (/ 1 (- zb wb)))

  (wick (eta z) (xi w) :on (torus tau)
    (prime-log-d z w tau))

  (wick (etab zb) (xib wb) :on (torus tau)
    (prime-log-d zb wb tau))

  (zero xi  :on (sphere (torus tau)) :kind xi-constant)
  (zero xib :on (sphere (torus tau)) :kind xi-constant))
#+end_src

The =:bar= annotation is only needed when the name and coordinate convention do
not make antiholomorphic support obvious.  The surface =torus tau= declares the
modular parameter =tau=.

** Label-Dependent Fields

=expX= has label-dependent weight.  The field declaration must allow this
without requiring an on-shell value.

#+begin_src lisp
(defcft free-boson-10
  (source stringbook)
  (dimension 10)
  (parameter alpha-prime 1)
  (sphere)

  (boson dX  (mu z)  :h 1)
  (boson dXb (mu zb) :h 1 :bar)

  (primary expX (k z zb)
    :h    (* 1/4 alpha-prime (dot k k))
    :hbar (* 1/4 alpha-prime (dot k k))
    :zero constant)

  (wick (dX mu z) (dX nu w)
    (* -1/2 alpha-prime (eta mu nu) (pow (- z w) -2)))

  (wick (dX mu z) (expX k w wb)
    (* -1/2 alpha-prime i (p k mu) (pow (- z w) -1)))

  (wick (expX p z zb) (expX k w wb)
    (* (pow (- z w)   (* 1/2 alpha-prime (dot p k)))
       (pow (- zb wb) (* 1/2 alpha-prime (dot p k))))))
#+end_src

On-shell conditions are calculation assumptions, not part of the field
definition:

#+begin_src lisp
(with-assumptions ((= (dot k k) 0))
  (corr sphere (R (expX k z zb)) (R (expX p w wb))))
#+end_src

** Operator Data

Field calls produce Lisp operator data.  Normal ordering and user-defined
operator templates also produce data.

#+begin_src lisp
(with-cft free-boson-10
  (let* ((v1 (expX k1 z1 zb1))
         (v2 (expX k2 z2 zb2))
         (dx (dX mu z3))
         (local (R dx v1)))
    (corr sphere local (R v2))))
#+end_src

Reusable templates are declared with =defop=.  They are not new fundamental
fields unless they are explicitly registered as fields in =defcft=.

#+begin_src lisp
(with-cft rns-flat
  (defop unintegrated-ns (eps k z zb)
    (R (c z)
       (cb zb)
       (dot eps (psi z))
       (expX k z zb)))

  (let ((v1 (unintegrated-ns eps1 k1 z1 zb1))
        (v2 (unintegrated-ns eps2 k2 z2 zb2)))
    (corr sphere v1 v2)))
#+end_src

** Calculation Forms

#+begin_src lisp
(with-cft eta-xi
  (corr (torus tau)
    (R (eta z))
    (R (xi w))))
#+end_src

#+begin_src lisp
(with-cft free-fermion-10
  (let ((a (R (psi mu z)))
        (b (R (psi nu w))))
    (corr sphere a b)))
#+end_src

=corr= accepts:

- normal-ordered local operators =R=;
- stored operator objects;
- =ops= lists for explicit multilocal data;
- sums and scalar multiples when Lisp can distribute them before calling Zig;
- assumptions that simplify result expressions after Zig returns.

** OPE And Basis Forms

OPEs are a first-class service, not an incidental side effect of correlator
evaluation.  The same rule language should support contractions into scalar
factors and OPE terms with residual operator output.

#+begin_src lisp
(with-cft rns-flat
  (ope (psi mu z) (S alpha w)
    :to-order 1))
#+end_src

Basis generation is also part of the CFT endpoint.  It enumerates operator
families by gradings and then quotients by relations declared in the theory.
The engine should stream basis candidates and accepted representatives; Lisp
can collect them when the space is small.

#+begin_src lisp
(defbasis massless-ns
  :grade ((h 1) (hbar 1) (ghost-number 2) (picture -1 -1))
  :built-from (dX dXb psi psib expX c cb)
  :mod ((total-derivative) (BRST-exact) (on-shell)))

(with-cft rns-flat
  (basis massless-ns :momentum k :assume ((= (dot k k) 0))))
#+end_src

The basis declaration is physics data.  Lisp expands it to a graded generation
problem; Zig receives compact field families, grading vectors, relation ids,
and product bounds.  Zig must not allocate the whole basis unless Lisp asks for
a bounded collection.

* Inference Rules

Inference happens in Lisp before Zig generation.

** Field Signatures

A field declaration:

#+begin_src lisp
(fermion psi (mu z) :h 1/2)
#+end_src

creates an argument schema:

- =z= is the insertion coordinate because it is the last coordinate-shaped
  argument.
- =mu= remains untyped until rules use it.  In =(eta mu nu)= it becomes a
  vector index.
- the field has holomorphic support unless =:bar=, a barred coordinate
  convention, or a two-coordinate bulk signature says otherwise.

Bulk fields use two coordinates:

#+begin_src lisp
(primary expX (k z zb) ...)
#+end_src

The last two arguments are the holomorphic and antiholomorphic coordinates.

** Role Inference

Roles are inferred by context:

- occurrence in =(eta mu nu)= or =(delta mu nu)= means vector index;
- occurrence in =(p k mu)= or =(dot k p)= means momentum;
- occurrence in charge-vector operations means charge or lattice vector;
- occurrence in spin tensors means spinor index or spin weight;
- occurrence as a modular argument to =torus= or =prime-log-d= means modular
  parameter;
- occurrence in field-call coordinate position means coordinate.

If a symbol has conflicting inferred roles, macro expansion fails and asks for
one local annotation:

#+begin_src lisp
(boson J (a z) :h 1 :labels ((a current-index)))
#+end_src

** Derivatives

Derivatives can be written as either argument offsets or explicit differential
forms:

#+begin_src lisp
(wick (D (psi mu z)) (psi nu w)
  (D z (/ (eta mu nu) (- z w))))

(wick ((d 2) (psi mu z)) (psi nu w)
  ((d z 2) (/ (eta mu nu) (- z w))))
#+end_src

The normalized IR stores derivative counts on insertions and coordinate
kernels.  The user does not write =include_left=, =include_right=, or runtime
coordinate slots.

** Surfaces

If a theory has exactly one surface, =wick= and =corr= may omit =:on=.  If a
theory has multiple surfaces, omitted =:on= means "all compatible surfaces"
only when the kernel expression is surface-independent.  Otherwise expansion
fails.

* Normalized Lisp IR

The IR uses explicit records.  Names are illustrative; exact Common Lisp class
names are not important.

#+begin_src lisp
(:cft
 :name free-boson-10
 :source stringbook
 :parameters ((alpha-prime scalar :default 1)
              (dimension rank :default 10))
 :surfaces ((sphere :coordinate rational)
            (torus :coordinate elliptic :moduli (tau)))
 :fields ((dX :statistics boson
              :support holo
              :args ((mu unresolved) (z coord))
              :labels ((mu index))
              :h 1)
          (expX :statistics boson
                :support bulk
                :args ((k unresolved) (z coord) (zb coord))
                :labels ((k momentum))
                :h (* 1/4 alpha-prime (dot k k))
                :hbar (* 1/4 alpha-prime (dot k k))
                :zero constant))
 :wick-rules (...)
 :zero-modes (...))
#+end_src

This layer is the contract between the user language and code generation.  It
is intentionally richer and more stable than =shared.declare.Spec=.

** IR Schema

The stable IR contains only generic records:

- =CFT= with name, source, parameters, surfaces, and declarations;
- =Surface= with kind, coordinate model, moduli, and boundary data;
- =FieldFamily= with statistics, support, argument schema, weights, quantum
  rules, and zero-mode policy;
- =LabelRole= with role kind and optional representation, lattice, or tensor
  domain reference;
- =FactorExpr= with scalar arithmetic, kernels, tensors, cocycles, residual
  operators, and actions;
- =WeightRule= and =QuantumRule= with symbolic expressions over labels and
  parameters;
- =WickRule= and =OpeRule= with field patterns, surface guards, coefficient
  terms, and optional residual operators;
- =ZeroModeRule= with field family, surface guard, saturation role, and
  generated factor expression;
- =OperatorTemplate= with parameters and a normal-ordered operator body.

This schema is the only object the Zig emitter reads.  Preset macros may be
convenient, but after expansion the emitter must not be able to tell whether a
declaration came from a preset or from the user.

* Generated Zig Contract

The generated Zig module should have four parts.

** Physics Spec

The module emits a high-level Zig spec:

#+begin_src zig
pub const Theory = cft.defineTheory(.{
    .source = .stringbook,
    .parameters = ...,
    .surfaces = ...,
    .fields = ...,
    .weights = ...,
    .wick = ...,
    .zero_modes = ...,
});
#+end_src

This spec is not today's =shared.declare.Spec= directly.  It is a frontend
that can lower into =shared.declare= for current presets and later into a
full =CFTKernel=.

This generated spec may be verbose.  It should avoid clever source-level
abstractions unless they make validation stronger, reduce lowered table size,
or remove duplicated lowerer logic.  The Lisp side does the DSL work; Zig
comptime does descriptor-to-kernel conversion.

** Generated ABI

Each generated theory module exports a stable Lisp-callable interface:

- create and destroy a calculation context;
- intern a symbol name and role;
- create field insertions from field id plus runtime labels;
- create normal-ordered local operators;
- freeze a multilocal operator list;
- select a correlator config or surface;
- run a correlator;
- stream high-level result terms.

The ABI must not expose =kernel.Call=, =Handle=, =PairLookupEntry=,
=BranchState=, residual masks, or =emitWick*= method names.

** Result Stream

The default result is a Lisp-readable expression event stream:

#+begin_src lisp
(:sum
  (:term
    (:tensor metric :left mu :right nu)
    (:kernel rational-pole :from z :to w :power -1)))
#+end_src

This is not the compact debug text sink.  It is a stable expression protocol
with nodes such as:

- =:sum=;
- =:term=;
- =:scalar=;
- =:kernel=;
- =:tensor=;
- =:zero-mode=;
- =:residual-operator=;
- =:action=.

The runtime may stream these nodes directly and must not materialize huge
expression trees by default.

For the Lisp REPL there are three public result modes:

- =corr= collects the stream into a bounded Lisp expression object;
- =corr-stream= exposes the event stream to a Lisp callback;
- =corr-count= runs the fast count/void path for benchmarks and diagnostics.

The collector lives on the Lisp side.  Zig still streams events and may abort
when Lisp reports that the collector reached its configured limit.  The
returned Lisp value should then be marked as truncated rather than silently
dropping terms.

** Name Preservation

The generated module keeps a name table for coordinates, indices, momenta,
charges, spinors, sectors, and parameters.  Runtime compact ids can still be
used internally, but rendered result nodes refer back to user names.

* Separation Of Internals

There are four boundaries.

** User Lisp Boundary

Visible:

- =defcft=, field declarations, =wick=, =zero=, =surface=, =source=;
- field constructor functions/macros;
- =R=, =ops=, =corr=, =ope=, =project=;
- =defop= for composite operator templates;
- assumptions and simplification hooks.

Hidden:

- compact kind ids;
- label spans;
- rule indexes;
- pair lookup tables;
- branch accumulators;
- residual masks;
- dry-run zero-mode pruning;
- Zig sink method names.

** Lisp IR Boundary

Visible to codegen, not ordinary users:

- inferred label roles;
- normalized surfaces;
- normalized weight and quantum-number rules;
- normalized Wick terms;
- normalized zero-mode consumers;
- named generated entrypoints.

Hidden:

- exact Zig packed record layout;
- table ordering chosen by Zig;
- branch and benchmark state.

** Zig Spec Boundary

Visible to generated Zig:

- explicit field and rule declarations;
- exact scalar and tensor symbolic factor descriptors;
- weight-rule ASTs;
- quantum-number-rule ASTs;
- surface and convention descriptors.

Hidden from generated Zig source:

- hand-written traversal loops;
- pair-cache construction procedures;
- residual-mask search code;
- zero-mode dry-run implementation.

Those are implemented once in the Zig library.

** Engine Boundary

Visible to the engine:

- compact =MultiOp= data;
- lowered =CorrelatorConfig=;
- lowered Wick and zero-mode tables;
- typed sink/result adapter.

Hidden from the engine:

- theory names such as =eta-xi= or =SO32=;
- Lisp macro syntax;
- physical meanings of picture number, GSO parity, Chan-Paton labels, or gauge
  group names.

The engine transforms compact records.  It does not interpret the user's
physics language.

* Ad Hoc Generation Audit

The current preset files are partially generated in spirit but handwritten in
shape.  A Lisp backend could reproduce them, but that would be the wrong target.

Ad hoc parts:

- per-preset =kind= enums and =familyKind= calls are manually arranged;
- operator builder namespaces are manually spelled;
- Wick helpers such as =freeBosonDxdX= or =etaXiTorus= are hand-authored;
- zero-mode storage functions are handwritten per preset;
- result sinks are user-extensible through engine method names;
- tests inspect engine events directly.

Acceptable backend parts:

- the compact runtime structures;
- =Spec.wickRules= and =Spec.zeroModeRules= lowering;
- private pair lookup construction;
- branch-state sizing;
- generic =streamCorrelator= over an opaque config and opaque operator list.

Required correction:

- introduce a single high-level =defineTheory= or =CFTSpec= frontend;
- migrate handwritten presets to use that frontend;
- make Lisp generate only that frontend plus ABI wrappers;
- keep =shared.declare= as a private lowerer until it is replaced by the
  fuller generated-kernel implementation.

** No Theory-Name Lowering

The Lisp-to-Zig layer fails review if new generic compiler code mentions CFT
names outside these places:

- preset packages;
- examples and documentation;
- test fixture names;
- user-visible symbol tables emitted from a concrete theory.

Generated Zig must be deterministic from the normalized IR.  There should be
one emitter for fields, one emitter for factor expressions, one emitter for
rules, one emitter for zero modes, and one emitter for ABI wrappers.  There
must not be separate emitters for eta-xi, SO(32), spin fields, or superghosts.

If future work needs a new concept, it should add the narrowest generic
primitive.  Examples are "branch-cut kernel", "spinor label role", "cocycle
factor", "residual operator body", or "representation tensor reference".  Once
added, that primitive must be usable by any theory declaration.

* Future CFT Coverage

** Free Bosons, bc, eta-xi

These are already close to the desired data model.

Required DSL features:

- first-order systems;
- top-form zero modes;
- constant-mode zero modes;
- rational and elliptic coordinate kernels;
- sphere, disk, and torus surfaces;
- boundary gluing as BCFT data, not runtime special cases.

** Free Fermions

Free fermions require:

- fermionic statistics;
- metric tensor factors;
- support for holomorphic and antiholomorphic copies;
- spin-structure-dependent kernels on torus later;
- no hidden scalar-only shortcut, because all meaningful =psi= correlators
  involve tensor factors.

The DSL form:

#+begin_src lisp
(fermion psi (mu z) :h 1/2)
(wick (psi mu z) (psi nu w)
  (/ (eta mu nu) (- z w)))
#+end_src

lowers to a generic Wick rule with one coordinate kernel and one tensor factor.

** Coupled phi, eta-xi, And Free Fermions

The RNS superghost and matter-fermion systems should not be modeled as one
hard-coded theory branch.  They are a product of declarations:

- a linear-dilaton boson =phi= with background charge;
- =eta= and =xi= first-order fermions with xi zero mode;
- matter fermions =psi^mu=;
- bosonized exponentials =expPhi[q,z]=;
- optional =beta=, =gamma= presentation as composite operators or a parallel
  first-order presentation;
- picture number and GSO parity as named quantum-number rules, not engine
  concepts.

Example:

#+begin_src lisp
(defcft rns-superghost
  (source stringbook)
  (sphere)

  (boson dphi (z) :h 1 :background-charge 2)
  (primary exp-phi (q z)
    :h (* -1/2 q (+ q 2))
    :quantum ((picture q)))

  (fermion eta (z) :h 1)
  (fermion xi  (z) :h 0 :zero constant)

  (defop beta (z)
    (R (exp-phi -1 z) (D (xi z))))

  (defop gamma (z)
    (R (eta z) (exp-phi 1 z))))
#+end_src

Spin fields couple to this through the matter-fermion or bosonized-H sector,
not by modifying the =eta_xi= engine.

** Spin Fields

Spin fields require more than the current executable preset model:

- spinor labels and chirality;
- cocycles;
- branch-cut coordinate powers;
- bosonized charge-vector presentation;
- gamma-matrix tensor structures in results;
- OPE rules that may emit residual spin fields and tensor factors;
- picture/GSO quantum numbers carried by operator data.

The DSL should let the user define spin fields compactly:

#+begin_src lisp
(spin-field S (alpha z)
  :chirality chiral
  :h 5/8
  :presentation (bosonized-H charge-of alpha))

(wick (psi mu z) (S alpha w)
  (* (pow (- z w) -1/2)
     (gamma mu alpha beta)
     (S beta w))
  :residual right)
#+end_src

This rule is not a pure Wick contraction into scalars.  It is an OPE-like rule
with residual operator output.  The future engine must support a uniform rule
interface whose term can contain coefficient factors and residual operator
bodies.  The current correlator already has residual refs, but the public spec
needs to express residual generated operators, not just "left" or "right"
survives.

** Pure Spinor Base CFTs

Pure-spinor-code should not force the core DSL to describe a full curved
target-space sigma-model action.  It should define a controlled base CFT, then
use perturbation-theory machinery outside this DSL to insert integrated
deformations.

For flat space the base CFT needs:

- free bosons \(X^m\);
- first-order systems \(p_\alpha,\theta^\alpha\) and their barred partners;
- the constrained beta-gamma ghost system \(\lambda^\alpha,w_\alpha\) and its
  barred partner;
- gauge-invariant ghost composites such as \(N_{mn}\), \(J_\lambda\), and
  \(T_\lambda\);
- BRST currents \(Q=\oint \lambda^\alpha d_\alpha\) and barred copies;
- pure-spinor constraints and gamma-matrix identities as quotient relations;
- ghost number, conformal weight, Lorentz representation, and chirality
  gradings;
- pure-spinor zero-mode saturation rules.

The CFT declaration should be able to say:

#+begin_src lisp
(defcft ps-flat-base
  (source pure-spinor)
  (sphere)

  (boson dX (m z) :h 1)
  (fermion theta (alpha z) :h 0)
  (fermion p     (alpha z) :h 1)
  (bosonic-ghost lambda (alpha z) :h 0
    :constraint (pure-spinor lambda gamma))
  (bosonic-ghost w      (alpha z) :h 1
    :gauge-shift (* Omega m (gamma m lambda alpha)))

  (wick (p alpha z) (theta beta w)
    (/ (delta alpha beta) (- z w)))

  (defop d (alpha z)
    (R (p alpha z)
       (* -1/2 (gamma m theta alpha) (dX m z))
       ...))

  (current Q (z) :brst
    (R (lambda alpha z) (d alpha z)))

  (relation (pure-spinor lambda gamma))
  (relation (gauge-invariant-only w :through (N J-lambda T-lambda)))

  (basis unintegrated-vertex
    :grade ((ghost-number 2) (h 0) (hbar 0))
    :mod ((Q-exact) (pure-spinor-constraint) (gauge))))
#+end_src

The ellipsis in the example is intentional prose, not final syntax.  The
important point is that the base CFT exposes operators, OPEs, BRST action,
relations, and bases.  Curved backgrounds, \(AdS_5\times S^5\), and
large-radius expansions then consume this service by defining perturbing
integrated operators and asking for OPEs, correlators, and cohomology bases.

** NLSM And Calabi-Yau Perturbation Bases

NLSM-code likewise starts from a base CFT.  In large-volume perturbation theory
or background-field expansion, the base can be a local free theory for target
coordinates and their worldsheet superpartners.  The NLSM module owns the
geometric expansion of the metric, \(B\)-field, dilaton, curvature couplings,
and counterterms.  The CFT DSL owns the free-field and abstract-SCFT services
used during the expansion.

For Calabi-Yau threefold and \((2,2)\) applications, the CFT language must be
able to represent:

- chiral and anti-chiral operator families as CFT operators;
- the holomorphic and antiholomorphic \(N=2\) superconformal generators
  \(T,J,G^\pm\) and barred copies;
- R-charges, spectral-flow charges, left/right weights, and sector labels;
- chiral-ring products and quotient relations;
- marginal operators and exactly marginal deformation labels;
- abstract conformal data supplied by the user when the IR CFT is not expressed
  as free fields;
- free-field large-volume presentations when the NLSM perturbation code needs
  local Wick/OPE services.

The same endpoint should allow both presentations:

#+begin_src lisp
(defcft cy3-large-volume-base
  (source stringbook)
  (surface sphere)

  (boson dZ  (i z)    :h 1)
  (boson dZb (ibar zb) :hbar 1)
  (fermion psi+ (i z) :h 1/2 :charge 1)
  (fermion psi- (i zb) :hbar 1/2 :charge -1)

  (current T (z))
  (current J (z))
  (current G+ (z))
  (current G- (z)))

(defcft cy3-abstract-scft
  (source conformal-data)
  (n2-sca :left (T J G+ G-) :right (Tb Jb Gb+ Gb-) :central-charge 9)
  (sector NS)
  (ring chiral
    :basis (phi a)
    :product Cabc
    :metric eta-ab))
#+end_src

The abstract form is essential.  We should not require a user who knows the
\((2,2)\) SCFT conformal data to encode performance internals or a fake
free-field realization.  Conversely, the free-field base is essential for the
NLSM perturbation code.  Both lower to the same service categories: operators,
OPEs, correlators when available, gradings, selection rules, and bases.

** SO(32) Fermions

The heterotic \(SO(32)\) fermions are another free-fermion system plus gauge
representation data.  The CFT engine and generic emitter should not know the
name \(SO(32)\).

The DSL should express:

#+begin_src lisp
(defcft so32-fermions
  (source stringbook)
  (group gauge SO32 :vector-index A :dimension 32)
  (sphere)

  (fermion lambda (A z) :h 1/2 :representation (vector SO32))

  (wick (lambda A z) (lambda B w)
    (/ (delta A B) (- z w))))
#+end_src

What this requires:

- label kind =gauge-index=;
- tensor factor =delta= over a declared representation;
- optional current operators such as \(J^{AB} = :lambda^A lambda^B:\);
- finite projections or GSO-like constraints as DSL data;
- tensor-code ownership of \(SO(32)\) representation algebra.

The generic compiler still sees a fermionic field with a label role and a
tensor-valued coefficient.  The engine sees compact labels and factors.  The
group-specific tensor algebra is a tensor-code problem.

** Lattice And Current-Algebra CFTs

\(E_8\times E_8\), Narain lattices, and bosonized gauge sectors need:

- lattice-vector labels;
- cocycle tables;
- momentum-lattice constraints;
- theta/character data for loop surfaces;
- current algebra modes if basis generation is needed.

The DSL should allow declarations such as:

#+begin_src lisp
(lattice Gamma16 :even-self-dual :rank 16)
(primary V (p z) :h (* 1/2 (dot p p)) :constraint (in p Gamma16))
(wick (V p z) (V q w)
  (* (cocycle p q)
     (pow (- z w) (dot p q))))
#+end_src

Again, the engine receives coordinate powers, cocycles, and labels.  It does
not know why the lattice is \(SO(32)\) or \(E_8\times E_8\).

** Boundary CFTs

Boundary theories should be generated from bulk CFT plus boundary extension:

- gluing automorphism for fields and labels;
- boundary operator families;
- mixed bulk-boundary Wick/OPE rules;
- zero-mode rules;
- Chan-Paton labels.

The engine should only see the doubled/lowered rules.  It should not execute
"D-brane logic" during correlator traversal.

* Required Zig Additions

The current backend needs these additions before the Lisp endpoint can be
called seamless:

1. A high-level =defineTheory= or =CFTSpec= frontend above =shared.declare=.
2. More label kinds: charge, spinor, gauge index, lattice vector, current index,
   Chan-Paton, modular parameter, scalar parameter, and discrete sector.
3. Weight-rule and quantum-number-rule declarations.
4. A name-preserving runtime symbol table.
5. A stable generated ABI for Lisp.
6. A result adapter that streams Lisp expression nodes.
7. A public/advanced split for custom sinks, keeping =emitWick*= internal.
8. A residual-operator rule vocabulary for spin-field and projected OPE work.
9. Tests that prove generated modules do not expose engine internals.

* Acceptance Criteria

The design is ready when these facts are true:

- A user can write \(Wick[\psi^\mu(z),\psi^\nu(w)] =
  \eta^{\mu\nu}/(z-w)\) in compact Lisp as:

  #+begin_src lisp
  (wick (psi mu z) (psi nu w)
    (/ (eta mu nu) (- z w)))
  #+end_src

- A user can store =(psi mu z)= or =(R (c z) (expX k z zb))= as Lisp data and
  reuse it in multiple correlators.
- The Lisp compiler infers coordinates, momenta, indices, and modular
  parameters in ordinary cases.
- The generated Zig contains a high-level theory spec and ABI wrappers, not
  hand-unrolled branch traversal or pair-cache logic.
- The generic Lisp-to-Zig compiler has no theory-name dispatch.  CFT names
  appear only in presets, docs, tests, and user-visible symbol tables.
- Zig result output preserves user names and returns structured Lisp expression
  nodes.
- Current correlator benchmarks remain green.
- Future \(SO(32)\), \(\phi,\eta,\xi,\psi\), spin-field, and lattice CFTs can
  be expressed by adding declaration data and tensor-code support, not by
  adding theory-name branches to the correlator engine.
