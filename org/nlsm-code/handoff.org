#+title: NLSM Code Handoff

This note records the current implementation state of =nlsm-code= and the next
steps for the generic type-II \(R^4\) computation.  It is a handoff note, not a
design replacement: the detailed physics plan remains
[[id:20260609T193000.000000][Type II R4 Implementation Plan]].

* Current State

The implemented pipeline is now:

1. bootstrap RNC vertex rows;
2. candidate diagram multisets;
3. explicit pairing branches driven by the =cft-code= correlator, with
   differentiated propagator factors;
4. optional Wick-species pairability summaries;
5. reduced kernel-signature rows;
6. evaluated kernel rows carrying pole, finite, and nonlocal data;
7. explicit pole rows as a projection;
8. beta rows from simple poles.

* Module Contracts

The current module boundaries are already useful and should be preserved unless
there is a hard reason to change them.

1. =rnc_vertices.zig=

   Owns only vertex rows and the bootstrap catalog.  It should eventually emit
   the real type-II component RNC expansion, but it should not know anything
   about poles, beta functions, or target cohomology.

2. =diagram_plan.zig=

   Owns only candidate multisets and loop/background counting.  It is not the
   place to do Wick contractions or geometry canonicalization.

3. =wick_signatures.zig=

   Owns pairability by quantum species.  It remains a cheap filter and summary
   layer.  The explicit pairing engine now lives in =pairing_engine.zig=.

4. =kernel_signature_reducer.zig=

   Owns the bridge from candidate or Wick-summary data to reduced kernel rows.
   It may accumulate combinatorial weights and target tensors, but it should
   not evaluate master integrals or collapse terms by geometry identities.

5. =pole_extractor.zig=

   Owns the analytic kernel-evaluation map from reduced signatures to Laurent,
   finite, and nonlocal rows.  Pole extraction is now only a projection of that
   broader evaluator.

6. =beta_assembly.zig=

   Owns only the simple-pole to beta-row conversion in the fixed MS scheme.
   It should remain a deterministic post-processing stage over local pole rows.

7. =local_geometry_reducer.zig=

   Owns only cheap local target-geometry quotients.  It is not yet the full
   tensor canonicalizer.

* Exact Bootstrap Shortcuts Still Present

These shortcuts are intentional for now.  They must be removed in a specific
order, not all at once.

1. The vertex catalog is fixed by hand.

   This is acceptable only because the current target is the one-loop bootstrap
   path.  The next real step is to replace this with a streamed component RNC
   expansion while preserving the same row format.

2. Diagram planning is multiset-level only.

   There is no explicit connected-graph or automorphism analysis beyond the
   current coarse counting.  That is acceptable for the present bootstrap
   invariants, but not for the real four-loop job.

3. Wick signatures count species, not pairings.

   =streamWickSignatures= is only a consistency filter plus a compact summary.
   It is not the actual Wick engine.

4. Kernel reduction still uses a bootstrap kernel dictionary.

   The branch path now consumes explicit pairings and explicit
   differentiated-propagator rows.  What is still bootstrap is the reduced
   master-family dictionary used downstream by =pole_extractor.zig=.

5. Kernel evaluation uses a bootstrap rule table.

   The current =stringbookBootstrapEvaluations= table is enough for the low-loop
   checks only.  It should be treated as scaffolding.

* Open Technical Risks

The next implementer should keep these risks visible:

- candidate rows carry slices into caller-owned storage, so any sink that keeps
  them must copy the =vertices= slice immediately;
- combinatorial factors must remain exact rationals all the way through pole
  extraction;
- modules that import =cft-code= should be verified through the build graph,
  since isolated leaf =zig test= runs do not wire sibling package modules;
- =external_derivative_order= in the current kernel rows refers to surviving
  background operator legs, not to derivatives on quantum lines;
- CY3/K3 compatibility depends on preserving =target_flavor= and keeping
  target-specific quotients out of the generic contraction and pole layers.

* What Is Real Already

The following statements are already true in code:

- combinatorial rational factors are preserved explicitly;
- target flavor is carried through the pipeline, so later CY3/K3 quotients can
  reuse the same contraction, pole, and beta layers;
- a one-loop bootstrap path reaches a beta row end-to-end through explicit
  pairing branches;
- mixed \(d\xi\) and \(\bar d\xi\) primitive pairs are now excluded at the
  pairing stage, matching the current free-field sphere inventory in
  =cft-code=;
- the =nlsm-code= build graph now imports =cft-code= directly, so the
  primitive pair-kernel inventory and the accepted Wick branches are sourced
  from the worldsheet module rather than kept as a separate NLSM-only copy;
- action vertices are lowered as local insertions at a common worldsheet point
  without normal-order protection, because the same-point \(\xi\xi\)
  contractions inside one interaction vertex are part of the counterterm
  computation, not something to subtract away in advance;
- fermion branch signs now survive into =PairingBranchRow= and therefore into
  the reduced kernel coefficient;
- the reduced kernel signature now preserves vertex count, pair count, and the
  separate \(\partial X_0\), \(\bar\partial X_0\) background-leg counts, so
  the first mixed supersymmetric two-loop branch is no longer collapsed onto
  the old bosonic placeholder signature;
- the code remains stream-first and does not materialize large symbolic sums.

This satisfies the immediate =AGENTS.md= constraints:

- explicit procedural code;
- lean row formats;
- no large intermediate symbolic expressions;
- minimal public API;
- literal-programming notes tied to narrow modules.

* What Is Still A Bootstrap

Several pieces are still placeholder technology, not the final \(R^4\) engine.

1. RNC vertices

   The current vertex generator now lowers a first explicit component source
   table.  It already includes the pure bosonic metric-sector rows, the first
   mixed fermion-connection rows
   \(\partial X_0\,\xi\,\psi\psi\,R\) and
   \(\partial X_0\,\xi^2\,\psi\psi\,\nabla R\), and the quartic
   fermion-curvature row.  It is still not the full type-II action in real
   RNC.

2. Diagram planning

   The current plan enumerates candidate vertex multisets, not connected Wick
   graphs with explicit pairing data.

3. Wick stage

   =pairing_engine.zig= now lowers the current bosonic and =N=(1,1)= bootstrap
   candidates into the actual =cft-code= correlator and reconstructs pairing
   branches from the streamed Wick events.  What remains bootstrap is the
   narrow primitive-kernel classifier that compresses those branch events into
   the present reduced kernel signature.  =wick_signatures.zig= remains a
   consistency-summary layer.

4. Kernel reduction

   =kernel_signature_reducer.zig= now consumes explicit pairing branches and
   their differentiated propagator factors, but its reduced signature is still
   matched against a bootstrap low-loop pole library.  It does not yet encode
   the full master-family data needed for the four-loop type-II job.

5. Pole rules

   =pole_extractor.zig= contains only a bootstrap low-loop table.  It is not
   yet the full dimensional-regularization master-family library needed for the
   four-loop calculation.

6. Geometry reduction

   =local_geometry_reducer.zig= is still a cheap local quotient layer.  It does
   not yet perform the full generic-RNC tensor canonicalization needed for the
   final \(R^4\) invariant matching.

* Next Step Order

The next steps should follow the physics dependency graph and should stay
aligned with =AGENTS.md=: keep modules narrow, stream-first, and literal.

1. Widen the reduced kernel signature

   The branch stage now comes from the real correlator backend for the current
   bootstrap worldsheet models.  The next bottleneck is downstream:
   =KernelSignature= is still a small low-loop descriptor.  It has to grow to
   represent the master families needed by the four-loop type-II job.

2. Replace the remaining bootstrap kernel dictionary

   =kernel_signature_reducer.zig= already consumes explicit branch kernel data.
   The next revision should widen the reduced signature so the pole extractor
   can distinguish the real master families needed beyond the present low-loop
   scaffold.  The first step of that widening is already done: mixed
   left/right connection branches now survive as distinct two-loop signatures.

3. Replace the bootstrap RNC catalog with a real type-II component expansion

   This work has started: the current component table already replaces the old
   fixed catalog for the first metric and mixed connection families.  It now
   also records the raw fermion-metric derivative vertices
   \(\xi^2\psi_L\bar\partial\psi_L R\),
   \(\xi^2\psi_R\partial\psi_R R\) on a separate =contact_only= channel.
   Those rows are part of the component expansion, but they are not emitted by
   the present primitive lowering path.  The next missing vertex sectors are
   the higher-order connection terms beyond the present \(-{1\over 3}R\,\xi\)
   and \(-{1\over 6}\nabla R\,\xi^2\) rows.  The first contact-term boundary is
   now in code as well: =contact_terms.zig= streams the raw differentiated rows
   as compact =ContactTermRow= descriptors instead of leaving them implicit.

   This is no longer blocked by primitive free-field support: the chiral
   fermion derivative count now flows through =cft-code=, the pairing layer,
   and the reduced kernel signature.  The present boundary is sharper.  The
   raw component rows are stored, but they are classified as =contact_only=
   because \(\bar\partial(1/(z-w))\) and \(\partial(1/(\bar z-\bar w))\) are
   distributional contact terms rather than primitive chiral kernels.  The
   remaining step is therefore to integrate those =ContactTermRow= descriptors
   into the same regulated local-evaluation path as the ordinary kernel rows,
   not to guess a primitive lowering for them.

4. Extend the pole extractor to real master families

   The next pole-extractor revision should introduce named low-loop master
   families derived once in the note and stored as explicit rules.  Only then
   should the code move to higher-loop families.

5. Strengthen the local geometry reducer

   Add the generic real-Riemannian \(R^4\) tensor canonicalization needed for
   the ordinary type-II calculation.  Keep CY3/K3-specific quotient logic as
   later target-flavor specializations on top of that.

6. Add action matching only after the beta tensor is stable

   The effective-action map must remain a post-processing stage.  Do not mix
   it into contraction, pole extraction, or beta assembly.

* End-To-End Invariant To Preserve

While the implementation evolves, the following bootstrap invariant should keep
passing:

#+begin_src text :tangle no
streamBootstrapVertices
  -> streamDiagramCandidates
  -> streamPairingBranches
  -> streamKernelTermsFromPairingBranches
  -> evaluateKernelRows
  -> extractPoleRows
  -> assembleBetaRows

For the current bosonic one-loop metric check, that path must continue to emit
one beta row with coefficient \(1/3\).  If that fails while refactoring the
middle stages, the change should be treated as a regression until the intended
new normalization is derived and documented explicitly.

* CY3 And K3 Alignment

The current architecture already preserves the correct generalization boundary.
The parts intended to be reusable for CY3/K3 are:

- scheme and counterterm rows;
- diagram planning;
- Wick pairability and later explicit pairing;
- kernel signature reduction;
- pole extraction;
- beta assembly.

The parts expected to specialize later are:

- target-flavor quotient rules;
- complex/Kahler vertex catalogs;
- compactification/cohomology projection;
- final invariant matching in special holonomy bases.

So the next engineering work should not fork the pipeline for CY3/K3.  It
should strengthen the generic stages and only later add target-specific vertex
catalogs and tensor quotients.

* Immediate Working Rules

For the next implementer:

- do not widen the public API unless a later stage truly needs it;
- do not introduce expression trees where row streams suffice;
- preserve rational combinatorial factors exactly;
- keep every new public declaration documented in the note and in code;
- add tests only for actual invariants or pipeline contracts.
