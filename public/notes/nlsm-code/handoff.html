This note records the current implementation state of nlsm-code and the next steps for the generic type-II \(R^4\) computation. It is a handoff note, not a design replacement: the detailed physics plan remains Type II R4 Implementation Plan.

Current State

The implemented pipeline is now:

  1. bootstrap RNC vertex rows;
  2. candidate diagram multisets;
  3. Wick-species pairability signatures;
  4. reduced kernel-signature rows;
  5. explicit pole rows from a small rule table;
  6. beta rows from simple poles.

The relevant notes and tangled modules are:

  • NLSM Scheme And Counterterms
    • src/nlsm-code/scheme.zig
    • src/nlsm-code/counterterms.zig
  • NLSM RNC Vertices
    • src/nlsm-code/rnc_vertices.zig
  • NLSM Diagram Plan
    • src/nlsm-code/diagram_plan.zig
  • NLSM Wick Signatures
    • src/nlsm-code/wick_signatures.zig
  • NLSM Kernel Signature Reducer
    • src/nlsm-code/kernel_signature_reducer.zig
  • NLSM Pole Extractor

  • NLSM Beta Assembly
    • src/nlsm-code/beta_assembly.zig
  • NLSM-Code
    • src/nlsm-code/nlsm-code.zig

The current public root exposes:

  • target-geometry reducer rows;
  • RNC vertex rows;
  • diagram candidate rows;
  • Wick-signature rows;
  • kernel-term rows;
  • pole rows;
  • beta rows;
  • the fixed stringbook-style \(d=2-\epsilon\) MS scheme.

What Is Real Already

The following statements are already true in code:

  • combinatorial rational factors are preserved explicitly;
  • target flavor is carried through the pipeline, so later CY3/K3 quotients can reuse the same contraction, pole, and beta layers;
  • a one-loop bootstrap path reaches a beta row end-to-end;
  • the code remains stream-first and does not materialize large symbolic sums.

This satisfies the immediate AGENTS.md constraints:

  • explicit procedural code;
  • lean row formats;
  • no large intermediate symbolic expressions;
  • minimal public API;
  • literal-programming notes tied to narrow modules.

What Is Still A Bootstrap

Several pieces are still placeholder technology, not the final \(R^4\) engine.

  1. RNC vertices

    The current vertex generator emits a fixed bootstrap catalog, not a full component expansion of the type-II action in real RNC.

  2. Diagram planning

    The current plan enumerates candidate vertex multisets, not connected Wick graphs with explicit pairing data.

  3. Wick stage

    wick_signatures.zig only checks pairability by species and derivative weight. It is not yet the explicit pairing engine.

  4. Kernel reduction

    kernel_signature_reducer.zig uses a summary-level mapping from candidate data to kernel signatures. It does not yet derive signatures from explicit Wick branches.

  5. Pole rules

    pole_extractor.zig contains only a bootstrap low-loop table. It is not yet the full dimensional-regularization master-family library needed for the four-loop calculation.

  6. Geometry reduction

    local_geometry_reducer.zig is still a cheap local quotient layer. It does not yet perform the full generic-RNC tensor canonicalization needed for the final \(R^4\) invariant matching.

Next Step Order

The next steps should follow the physics dependency graph and should stay aligned with AGENTS.md: keep modules narrow, stream-first, and literal.

  1. Replace Wick summaries with an explicit pairing engine

    Add a module that consumes one WickSignatureRow and enumerates admissible pairings by species and derivative pattern. It should emit branch rows, not symbolic expressions. This is the first genuinely necessary step before the four-loop calculation becomes credible.

  2. Route kernel reduction through explicit Wick branches

    Once pairings are explicit, kernel_signature_reducer.zig should stop using the current summary-level shortcut and instead accumulate kernel signatures from actual branch data.

  3. Replace the bootstrap RNC catalog with a real type-II component expansion

    Add a note/module for the real RNC component vertices of the \(N=(1,1)\) worldsheet model in ordinary real coordinates. Keep the row format, replace the source of rows.

  4. Extend the pole extractor to real master families

    The next pole-extractor revision should introduce named low-loop master families derived once in the note and stored as explicit rules. Only then should the code move to higher-loop families.

  5. Strengthen the local geometry reducer

    Add the generic real-Riemannian \(R^4\) tensor canonicalization needed for the ordinary type-II calculation. Keep CY3/K3-specific quotient logic as later target-flavor specializations on top of that.

  6. Add action matching only after the beta tensor is stable

    The effective-action map must remain a post-processing stage. Do not mix it into contraction, pole extraction, or beta assembly.

CY3 And K3 Alignment

The current architecture already preserves the correct generalization boundary. The parts intended to be reusable for CY3/K3 are:

  • scheme and counterterm rows;
  • diagram planning;
  • Wick pairability and later explicit pairing;
  • kernel signature reduction;
  • pole extraction;
  • beta assembly.

The parts expected to specialize later are:

  • target-flavor quotient rules;
  • complex/Kahler vertex catalogs;
  • compactification/cohomology projection;
  • final invariant matching in special holonomy bases.

So the next engineering work should not fork the pipeline for CY3/K3. It should strengthen the generic stages and only later add target-specific vertex catalogs and tensor quotients.

Immediate Working Rules

For the next implementer:

  • do not widen the public API unless a later stage truly needs it;
  • do not introduce expression trees where row streams suffice;
  • preserve rational combinatorial factors exactly;
  • keep every new public declaration documented in the note and in code;
  • add tests only for actual invariants or pipeline contracts.
