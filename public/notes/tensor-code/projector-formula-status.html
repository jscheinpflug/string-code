This note records the current state of the explicit-projector goal for Tensor-Code. It should be read with the requirements in Clebsch-Gordan, the streaming structures in Tensor Rendering, the context boundary in Tensor Context, the projector store in Tensor Projector, and the current generic backend in Generic Highest-Weight Backend.

Status

The goal is not complete. The current implementation can store and stream a large Spin(10) invariant basis in a symbolic, lowered form, but it is not yet a fully evaluable component tensor system. The remaining work is not cosmetic: there is still no component evaluator for the streamed atoms, and the general ADE projector construction is only partially present.

The strongest completed milestone is that the Spin(10) stress case has moved past abstract path counting. The context can enumerate the \(16^{12}\) singlet basis as compact coupling paths and can render every path through the current local formula registry without named projector placeholders. The current tests assert the expected path count \(73744\), zero missing local formula steps for that basis, and a lowered Clifford-factor stream with no compact projector operators.

Update 2026-06-08: the finite Clifford-exterior Gram solver described in Finite Projector Gram Solver Plan is now the active tensor-form/tensor-spinor lowering path for expanded rendering. Compact projection atoms are still available as compact metadata outside .expanded_terms, but expanded streaming asks the structural program caches for term counts and raises typed unsupported errors instead of silently emitting compact placeholders.

The solver now uses fixed candidate words, exact Gram contraction, pivot selection, inverse-Gram term streaming, structural program caches, and right-spinor chirality metadata for tensor-form terminal bilinears. The previous hard Spin(10) terminal case orthogonal_tensor_spinor_opposite_form_add_shift_terminal_channel is solved as a structural gamma-map/adjoint pair plus carried-form deltas, not by a new family-specific closed form.

It streams the same expanded, lowered formula path used by rendering, with Clifford products lowered to factor atoms, and returns an EvaluationAudit. The old evaluateInvariant(invariant, ...) entry point remains unsupported because an InvariantHandle is only meaningful inside a basis.

Achieved

  • Compact invariant bases are stored as path records, not dense tensors.
  • The Spin(10) \(16^{12}\) basis count is represented as \(73744\) stored coupling paths.
  • Local coupling steps carry projector ids with derivation metadata.
  • Expanded rendering fails with typed errors when a formula route is missing.
  • Formula coverage audits distinguish local steps, boundary steps, expandable steps, missing steps, distinct projector ids, and the first missing projector.
  • Boundary realization projectors exist for constrained realizations, including the gamma-traceless vector-spinor case \(144\subset 10\otimes16\).
  • The \(144\) boundary formula is generated by projector-constructor.zig as the vector-spinor identity minus the gamma-trace projector with coefficient \(-1/N\), the rank-one Gram trace-subtraction form \(I - T G^{-1} T^*\).
  • Spin(10) spinor and tensor-spinor local formula routes are broad enough for the current \(16^{12}\) path set.
  • Compact Clifford-product atoms encode gamma-block reductions without expanding large products into memory.
  • Lowered Clifford-product factors can be streamed as explicit metric and output-vector factor atoms.
  • Lowered streams can be scanned and audited without retaining all emitted terms.
  • A basis-aware evaluation stream can now consume one invariant through its owning basis and receive lowered symbolic terms without materializing the full expression.
  • Tensor-form and tensor-spinor compact projection descriptors route through structural projector program caches for expanded rendering. A zero structural term count becomes a typed unsupported error in .expanded_terms instead of a silent compact fallback.
  • Structural projector programs enumerate primitive signatures from form profiles, tower powers, chirality, duality, and spinor presence metadata, then compute exact Gram matrices and stream inverse-Gram projector terms.
  • Tensor-form terminal bilinears now carry right-spinor chirality in the compact rendering atom, constructor spec, structural key, and cache key.
  • Generalized terminal rank-split cases are recognized by the finite Clifford-exterior rank equation, including carried-form deltas such as \(\{2,3\}\to\{1,2,4\}\).
  • Middle-form/Hodge, rank-split, gamma-delta, gamma-wedge, spinor-tower, and form-spinor structural fixtures pass through the generic solver path.
  • The constructor includes a structural fixture with nonzero off-diagonal Gram entries and exact inverse-Gram mixed-term streaming.
  • The tensor-form terminal family orthogonal_tensor_spinor_terminal_channel is now explicit gamma_form plus carried-form generalized_delta rather than compact tensor_form_projection.
  • The form-preserving terminal family orthogonal_tensor_spinor_form_terminal_channel now emits primitive spinor_pair and generalized_delta atoms rather than a tensor_form_spinor_pair descriptor.
  • The form-adding terminal family orthogonal_tensor_spinor_form_add_terminal_channel is now explicit gamma_form plus carried-form generalized_delta, with the inserted form rank recorded from the compact form profiles.
  • The form-power terminal family orthogonal_tensor_spinor_form_power_terminal_channel is now explicit gamma_form plus carried-form generalized_delta, with the inserted form rank recorded from the incremented compact form-profile slot.
  • The terminal gamma-form projector expressions now go through projector-constructor.zig. The constructor infers the gamma rank from profile increments, whole-profile shifts, and single-block moves, then emits primitive gamma_form plus carried-form generalized_delta atoms directly into the scratch buffer.
  • The constructor now has a streaming multi-term API, tested on the vector-spinor gamma-traceless projector, so trace-subtraction formulas can be emitted term-by-term without materializing expression trees.
  • The local path renderer now has a fixed-index term stream for local formula programs. One-term formulas still produce the same \(16^{12}\) stream, but future Hodge and Gram-sum projectors no longer need to be forced through one flat local atom list.
  • Representative A and E atoms exist for epsilon and structure-constant style primitive invariants.
  • The public root exports the minimal symbolic structures needed by current callers.
  • The source changes have matching org mirrors in the tensor-code literate files.

Not Achieved

  • Context.evaluateInvariant remains unsupported by design because its signature is under-specified; Context.evaluateBasisInvariant is the basis-aware replacement.
  • There is no component assignment model for vector, spinor, form, adjoint, or tensor-spinor indices.
  • There is no evaluator for metric_pair, spinor_pair, gamma_matrix, gamma_form, gamma_action, epsilon, structure_constant, generalized_delta, hodge_star, tensor_spinor_projection, or tensor_form_projection.
  • Lowered Clifford-product factors are explicit symbolic factors, not evaluated component contractions.
  • The Hodge and middle-form duality tags are metadata-level. They are not yet executable epsilon/Hodge component operations.
  • Optional canonical gamma reductions are not complete.
  • Chirality zero-selection and canonical Clifford ordering are incomplete.
  • General ADE local projector construction is not complete.
  • The generic highest-weight backend is still limited by missing character and local-projector construction capabilities for many non-minuscule products.
  • There is no general Casimir or residual-linear-algebra projector builder.
  • Expansion cost estimates do not yet include all future component-evaluation costs.
  • Streaming filters are currently term-level. They do not yet prune all intermediate projector branches with sound prefix decisions.

Main Bottlenecks

Evaluator Boundary

The first hard blocker is API shape. Rendering uses: 

renderInvariant(ctx, basis, invariant, options, sink)

Evaluation currently has only: 

evaluateInvariant(ctx, invariant, options, sink)

This cannot be made correct because the same invariant handle value can name different paths in different bases. The next implementation should add a basis-aware evaluator and leave the old method as a typed unsupported entry point until it can be removed or redirected safely.

Component Data Model

The symbolic stream names abstract indices and blocks. A component evaluator needs a lean assignment layout that can be tested and filtered without building dense tensors.

The data should be flat: 

const ComponentAssignment = struct {
    vector_values: []const u16,
    spinor_values: []const u16,
    form_block_offsets: []const u32,
    form_values: []const u16,
    adjoint_values: []const u32,
};

Every atom evaluator should receive only the slices it needs. No evaluator should allocate a product-space object such as \(16^{12}\).

Atom Semantics

The renderer now emits enough atom tags for symbolic consumers, but a numeric or component evaluator needs exact semantics for each atom. The first pass should support predicates and small integer/rational weights:

  • metric: equality or signed diagonal metric entry;
  • generalized delta: ordered or antisymmetric block equality;
  • epsilon: permutation sign after distinctness check;
  • spinor pair: backend-defined charge conjugation pairing;
  • gamma atoms: backend gamma-entry callback;
  • Clifford factors: metric factors plus free-vector routing;
  • Hodge: epsilon complement and normalization;
  • structure constants: backend callback or sparse table iterator.

Formula Registry

The formula registry currently proves enough local coverage for the Spin(10) stress path, but many routes are specialized procedural recognizers. This is acceptable as an intermediate state, but the final system needs projector programs with explicit input/output realization metadata and executable atom emitters.

The basis must not be obtained by emitting an overcomplete set of gamma monomials and then quotienting by Fierz relations. The invariant records are already the basis: they are coupling paths through representation and multiplicity space. Formula programs are only the rendering/evaluation route for each already-independent path. Fierz-style identities may be useful later to choose prettier or more canonical gamma notation, but they are not required for independence and should not sit on the critical path for streaming the basis.

General ADE Coverage

The current generic backend gives useful decomposition/path infrastructure, but the final ADE goal requires more:

  • complete character generation for non-minuscule irreps;
  • multiplicity-space bases for product channels;
  • local CG kernel/projector construction for multiplicity copies;
  • primitive invariant renderers beyond the small representative A/E cases;
  • residual projector solves when Casimir separation does not isolate a channel.

Performance

The primary performance risk is accidentally turning streaming into hidden materialization. The evaluator must reuse scratch buffers per term, emit or reject immediately, and keep all large loops structured so they can later be split by invariant range or path chunk.

Immediate Implementation Plan

  1. Keep projector lowering work organized around structural keys and missing contraction identities. Compact projection atoms are still valid as compact metadata outside expanded rendering, but they should not be counted as solved unless the expanded path goes through candidate enumeration, exact Gram contraction, and streamed term emission.
  2. Add component assignment filtering on top of the basis-aware evaluator:
pub fn evaluateBasisInvariant(
    self: *Context,
    basis: coupling.BasisHandle,
    invariant: coupling.InvariantHandle,
    options: rendering.EvalOptions,
    sink: anytype,
) !rendering.EvaluationAudit

This now exists and streams lowered symbolic terms. The next evaluator work is not another entry point; it is a component assignment filter: 

pub const ComponentFilter = struct {
    assignment: ComponentAssignment,
    decide_fn: *const fn (*const ComponentAssignment, SymbolicTerm) anyerror!FilterDecision,
};

The first filter should support metric and generalized-delta rejection. That gives immediate useful pruning without needing gamma matrices.

  1. Implement atom evaluators in increasing cost order:
  2. metric and generalized delta;
  3. epsilon and Hodge complement;
  4. spinor pair;
  5. gamma matrix/form/action through backend callbacks;
  6. Clifford-product factor streams;
  7. structure constants;
  8. compact tensor-spinor and tensor-form projections.
  9. For future projector gaps, add missing finite contraction identities or

candidate signatures. Do not add another production branch whose main description is a compact formula-family name.

Pseudocode

Basis-Aware Evaluator

pub fn evaluateBasisInvariant(ctx, basis, invariant, options, sink) !EvaluationAudit {
    try ctx.validateEvalOptions(options);

    const path = ctx.impl().couplingPathForInvariant(basis, invariant)
        orelse return error.UnknownInvariant;
    const request = ctx.impl().couplings.basisRequest(basis)
        orelse return error.UnknownBasis;

    var scratch: ExpansionScratch = .{};
    defer scratch.deinit(ctx.allocator);

    const render_options = RenderOptions{
        .projectors = .expanded_terms,
        .signature = options.signature,
        .lower_clifford_product_atoms = true,
    };

    var adapter = EvaluationSinkAdapter{ .inner = sink };
    const expansion_audit = try ctx.impl().streamPathExpansion(
        request,
        path,
        render_options,
        ExpansionFilter.acceptAll(),
        &adapter,
        &scratch,
    );

    return EvaluationAudit{
        .terms = expansion_audit.emitted,
        .rejected = expansion_audit.rejected,
        .lowered_clifford_factors = expansion_audit.clifford_product_factors,
    };
}

Streaming Component Evaluation

fn evaluateTerm(term, assignment, backend, sink) !void {
    var coeff = rationalValue(term.coefficient);

    for (term.atoms) |atom| {
        const factor = switch (atom) {
            .metric_pair => |m| evalMetric(m, assignment),
            .generalized_delta => |d| evalDelta(d, assignment),
            .epsilon => |e| evalEpsilon(e, assignment),
            .spinor_pair => |p| backend.evalSpinorPair(p, assignment),
            .gamma_matrix => |g| backend.evalGammaMatrix(g, assignment),
            .gamma_form => |g| backend.evalGammaForm(g, assignment),
            .gamma_action => |g| backend.evalGammaAction(g, assignment),
            .clifford_product_factor => |f| evalCliffordFactor(f, assignment),
            .structure_constant => |f| backend.evalStructureConstant(f, assignment),
            .hodge_star => |h| evalHodge(h, assignment),
            else => return error.AtomEvaluationNotImplemented,
        };

        if (factor.is_zero) return;
        coeff = try coeff.mul(factor.value);
    }

    try sink.emitComponentValue(coeff);
}

Prefix Filter

fn componentPrefixDecision(prefix, assignment) !FilterDecision {
    for (prefix.atoms) |atom| {
        switch (atom) {
            .metric_pair => |m| {
                if (bothAssigned(m.left, m.right, assignment) and
                    vectorValue(m.left) != vectorValue(m.right))
                    return .reject;
            },
            .generalized_delta => |d| {
                if (blockAssigned(d, assignment) and
                    !sameAntisymmetricBlock(d, assignment))
                    return .reject;
            },
            else => continue,
        }
    }

    if (allNeededAtomsAssigned(prefix, assignment)) return .accept;
    return .undecided;
}

Local Projector Program

fn renderProjectorProgram(program, indices, filter, sink, scratch) !void {
    scratch.clear();
    var frontier = TermFrontier.init(&scratch.a, .{ .coefficient = one });

    for (program.instructions) |instruction| {
        var next = TermFrontier.init(&scratch.b, .{});

        for (frontier.terms()) |partial| {
            try appendInstructionTerms(instruction, partial, &next);

            for (next.newTerms()) |candidate| {
                switch (try filter.decide(candidate)) {
                    .reject => next.discard(candidate),
                    .accept, .undecided => next.keep(candidate),
                }
            }
        }

        frontier = next.swapIntoFrontier();
    }

    for (frontier.terms()) |term| {
        if (try filter.decide(term) != .reject)
            try sink.emitTerm(term);
    }
}

Residual Projector Solve

fn buildResidualProjectors(product_space, channels, backend) !void {
    const casimir_blocks = splitByCasimir(channels);

    for (casimir_blocks) |block| {
        if (block.channels.len == 1) {
            try emitCasimirProjector(block.channels[0]);
            continue;
        }

        var equations = SparseEquationBuilder.init();
        try equations.addIntertwinerConstraints(product_space, block);
        try equations.addIdempotencyConstraints(block);
        try equations.addOrthogonalityConstraints(block);

        const basis = try solveSparseNullspace(equations);
        try chooseMultiplicityBasis(block, basis);
        try emitSparseProjectorPrograms(block);
    }
}

AGENTS Audit And Handoff

This section is the handoff for the next agent. It audits the current note and the current implementation direction against AGENTS.md and Clebsch-Gordan.

What The Next Agent Must Preserve

  • Keep the basis construction in representation/multiplicity space. Do not build an overcomplete gamma-monomial list and then reduce it by Fierz identities. The invariants are emitted directly from coupling paths.
  • Keep \(16^{12}\) as compact basis paths and streamed terms. Do not allocate dense component tensors or a full expanded expression list.
  • Keep the public API small. Add exports only when another module or caller needs them.
  • Keep source and org mirrors synchronized. If a Zig source file is edited, patch the matching org/tensor-code/*.org block in the same turn.
  • Use simple procedural code with lean data structures and explicit counters. Prefer borrowed slices and scratch buffers over owned intermediate symbolic expressions.
  • Tests must check a precise invariant. Do not add tests merely to exercise syntax.
  • Do not revert unrelated dirty worktree changes. This repository currently has many modified tensor-code and CFT files; treat them as user or prior-agent work unless they directly block the task.

Key Information Learned

  • The Spin(10) \(16^{12}\) stress target is already represented as \(73744\) coupling paths.
  • Current formula coverage for that stress basis has been tested to report no missing local formula steps and \(811184\) expandable local steps.
  • The current stream can remove opaque projector operator atoms for the Spin(10) stress basis.
  • The lowered Clifford-product stream replaces compact clifford_product atoms by clifford_product_factor atoms. These factors are explicit metric contractions and free-vector routing records, not dense gamma matrices.
  • The latest full tensor-code verification passed after adding the basis-aware evaluator and after lowering identity/Cartan product atoms.
  • Context.evaluateInvariant remains explicitly unsupported and is also under-specified because InvariantHandle is only meaningful inside a BasisHandle. Use Context.evaluateBasisInvariant instead.
  • The point of the current architecture is to avoid Fierz reduction as a basis construction step. Optional canonical gamma notation can come later, but it must not become a prerequisite for emitting the independent basis.
  • The projectors are only partially explicit. Many Spin(10) routes render to meaningful symbolic atoms, but several atoms still stand for compact local formula families rather than primitive component operations.
  • A dumped \(16^{12}\) term still contains tensor_spinor_projection and tensor_form_projection. The previous cartan_product occurrence is now an explicit spinor_symmetrized_product atom carrying tower powers and chirality. The remaining \(\Pi\)-style tensor atoms are not the final desired gamma/metric/delta/epsilon-only rendering.

Current Non-Opaque Output Shape

The renderer emits SymbolicTerm records. Opaque named projectors look like: 

.{ .named_operator = .{
    .kind = .projector,
    .operator_id = projector_id,
    .first_index = first,
    .index_len = len,
} }

Expanded projector routes should instead emit atoms such as: 

.gamma_matrix
.gamma_form
.gamma_action
.metric_pair
.spinor_pair
.generalized_delta
.identity_route
.spinor_symmetrized_product
.tensor_spinor_projection
.tensor_form_projection
.clifford_product_factor

A simple Spin(10) example is the invariant \[ 16\otimes16\otimes10\to 1. \] Its rendered term has the shape: 

SymbolicTerm{
    .coefficient = rationalOne(),
    .atoms = &.{
        .{ .gamma_matrix = .{
            .operator_id = p_spinor_spinor_vector,
            .spinor_left = 0,
            .spinor_right = 1,
            .vector = 3,
            .orthogonal_dimension = 10,
            .rank = 1,
            .chirality = 1,
            .duality = .none,
        } },
        .{ .metric_pair = .{
            .left = 3,
            .right = 2,
        } },
    },
}

This is schematically \[ (\Gamma^\mu)_{\alpha\beta}\eta_{\mu\nu}. \] It is non-opaque because the vector-channel projector is rendered as a gamma matrix atom and the singlet contraction is rendered as a metric atom. It is not yet a component-evaluated tensor entry.

Performance And Generalization

The optimal design is not to make every ADE projector look like an orthogonal gamma formula. The optimal design is a generic streaming formula-program interface with backend-specific primitive atom vocabularies.

The generic layer should own:

  • coupling-path storage;
  • multiplicity-copy ids;
  • projector ids and derivation metadata;
  • render/evaluation options;
  • streamed term emission;
  • filter decisions and audit counters;
  • scratch-buffer ownership and reuse.

The backend layer should own:

  • the primitive invariant atoms available for that family;
  • the formula program for each projector kind;
  • local normalization and signature conventions;
  • local Hodge/duality or epsilon conventions where relevant;
  • sparse residual projector construction when a generic closed form is not available.

For \(B_n,D_n\), the backend primitive vocabulary includes metrics, spinor pairings, gamma forms/actions, Clifford product factors, antisymmetric deltas, and Hodge/epsilon atoms. For \(A_n\), the primitive vocabulary should be fundamental deltas, epsilons, Cartan/highest-weight product programs, and eventually tableau/Gelfand-Tsetlin style formula programs. For \(E_6,E_7,E_8\), the primitive vocabulary should include structure constants, invariant forms, and sparse backend-specific projector programs. Gamma atoms must remain orthogonal-backend atoms, not generic ADE API.

The performance-critical rule is: lower by formula program, not by occurrence. The current \(16^{12}\) stream has \(235630\) compact formula-family atoms, but those atoms come from a much smaller set of projector ids and formula kinds. The next implementation should count distinct operator ids and then compile or dispatch one lowering program per formula kind. Re-lowering the same operator shape independently for every occurrence would waste time and make parallel execution harder.

The hot data flow should look like this: 

coupling path
  -> local projector formula id
  -> backend formula program
  -> small scratch frontier
  -> streamed primitive atoms
  -> filter
  -> sink

The hot data flow should not look like this: 

all paths
  -> all expanded terms
  -> one huge symbolic expression
  -> simplify/reduce
  -> filter

Each formula program should be written as simple procedural code over lean records. A program should receive only the local indices and metadata it needs, append primitive atoms into caller-owned scratch storage, and emit or discard terms immediately. It should not allocate an owned expression tree. The local renderer now has fixed local term-count and term-index arrays plus caller-owned scratch atom buffers. Multi-summand projector programs should plug into that path by reporting term counts and appending the selected term. Filters must be applied at each safe prefix point so reject-all and component filters do not pay the cost of completing impossible branches.

Parallelization should be straightforward if the state is kept local:

  • basis paths can be split into independent ranges;
  • each worker owns an ExpansionScratch;
  • read-only stores provide projector/formula metadata;
  • sinks either collect per-worker audits or use caller-controlled reduction;
  • no worker writes to a shared giant expression buffer.

Caching should be compact:

  • cache decomposition results and formula-program descriptors;
  • cache small lowering plans keyed by projector id or formula kind;
  • cache Clifford grade/contraction plans because they are tiny and reused;
  • do not cache dense component tensors;
  • do not cache all \(73744\) expanded formulas.

The next high-value performance audit is to count distinct projector operator_id values and formula kinds for:

That audit determines how many actual lowering programs remain. The occurrence counts are large, but the program count should be much smaller. Once the distinct program count is known, lowering should proceed in this order:

Each pass should end by re-running AtomLoweringAuditSink. The target is not "more pretty output"; the target is fewer compact formula atoms while preserving streaming, filterability, and no dense intermediate allocation.

Cache Notes

The two cache directories in the verification command are Zig build caches, not tensor-code data files:

  • .zig-cache-global is passed as ZIG_GLOBAL_CACHE_DIR. Zig uses it for compiler artifacts that would otherwise go into the user-level global cache, usually under the home directory. Keeping it inside the workspace makes the test run independent of a full or stale global cache outside the repository.
  • .zig-cache-local is passed as ZIG_LOCAL_CACHE_DIR. Zig uses it for package-local and build-local artifacts produced while compiling this checkout. Keeping it explicit prevents the test run from writing to an uncontrolled cache location.

These directories are created only for verification. They may contain compiled object files, dependency metadata, incremental compiler state, and build products needed by zig test or zig build test. They do not contain mathematical projector data, invariant bases, formula programs, or source of truth. After the tests finish they can be removed without changing the implementation.

The reason to use workspace-local caches here is practical. Earlier long tensor-code verification runs encountered pressure in the default temporary or global Zig cache locations. Redirecting both caches into the repository keeps the run reproducible under the current sandbox and makes cleanup explicit: 

find .zig-cache-global .zig-cache-local -depth -mindepth 1 -delete
rmdir .zig-cache-global .zig-cache-local

This cleanup should happen only for the two explicitly created verification directories. It must not remove zig-out, source files, org files, or any repository data.

Tensor-code also has internal in-memory caches, which are a different matter. Those caches are part of the implementation and must survive for the lifetime of a Context:

  • the representation store interns algebras and irreps so handles are stable;
  • the decomposition store avoids recomputing tensor-product decompositions;
  • the projector store interns local projector ids and their derivation/formula metadata;
  • the coupling store keeps compact basis requests, paths, and steps;
  • formula-program caching records whether a projector has an executable render route or must fail with a typed missing-formula error.

Those internal caches are needed for performance and correctness. They prevent the \(16^{12}\) stress target from repeatedly regenerating the same product decompositions and local projector metadata. They are deliberately compact: they store handles, spans, counters, and formula metadata, not dense component tensors. The final evaluator should keep this property. Any future component cache must be bounded by local atom/program size or by an explicit caller-owned memoization policy; it must not cache dense spaces such as \(16^{12}\).

The full goal should not be marked complete until the following evidence is present in the current tree:

  • every \(16^{12}\) path streams in expanded, lowered form;
  • every lowered atom needed by that stream has component-evaluation semantics;
  • component filters prune during streaming;
  • evaluateBasisInvariant or its final equivalent is implemented and tested;
  • evaluateInvariant is removed, redirected safely, or explicitly documented as basis-less and unsupported;
  • ADE decomposition works beyond the currently supported generic cases;
  • ADE local projector programs exist or fail with typed missing capability before they appear in an expanded basis;
  • no implementation path allocates dense \(16^{12}\) component tensors.
