1. Goal

This note joins the deficiencies of the current Presets skeleton into one coherent improvement plan. The current code gives us a checked public shape, but it is not yet the right user experience and it does not encode real Wick rules.

The target is:

  • users write physics objects, not ids;
  • operator builders preserve labels;
  • presets lower to Theory data;
  • Wick rules and zero-mode rules are compact generated tables;
  • Correlators still receive only local operators, a compiled config, and a sink.

2. Current Deficiencies

The present implementation has six important gaps.

  1. Handle.Index, Handle.Momentum, Handle.Profile, and related values are naked integer aliases. That leaks storage details into the physics API.
  2. Operator builders discard the labels they receive. expX(k,z,zb) and expX(k2,z,zb) currently produce the same body id.
  3. config.sphere and config.disk contain placeholder Wick and zero-mode ids.
  4. All preset correlator functions return error.NotImplemented.
  5. product and boundary expose hard-coded wrapper builders for the current milestone rather than selecting namespaces from supplied factors.
  6. Boundary extensions are accepted as data, but the generated boundary builder does not yet enforce which extensions are present.

The core mistake is not that ids exist. The mistake is that the user-facing surface suggests users might type those ids by hand. Ids should be assigned by generated stores and used only by lowering/runtime code.

3. UX Boundary

There should be three layers.

  1. The user-facing physics layer has typed values such as Index, Momentum, Profile, TargetPoint, and BoundaryStack. These are opaque structs, not aliases.
  2. The generated builder layer interns those values into a compact label store and builds local operators.
  3. The lowered runtime layer sees only small ids, label spans, Wick-rule tables, zero-mode tables, and coefficient streams.

The user should write code like this: 

const X = cft.presets.freeBoson(.{ .dimension = 10, .alpha_prime = .one });

var local = X.local(allocator);
const mu = try local.index("mu");
const k = try local.momentum("k");
const z = try local.coord("z");
const zb = try local.coord("zb");

const ops = try local.ops(.{
    local.op.dX(mu, 0, z),
    local.op.expX(k, z, zb),
});

try X.correlator(X.config.sphere, ops, sink);

This does not introduce a correlator context. local is a short-lived builder and label arena for the operator collection. The correlator still receives a config, a collection of local operators, and a sink.

4. Opaque Physics Values

The public aliases in Handle should be replaced by generated typed tokens. The internal integer remains, but ordinary user code never needs to type it or read it. In Zig this can be represented as a non-exhaustive integer-backed enum, with private generated helpers for extraction. 

pub const Index = enum(u32) { _ };
pub const Momentum = enum(u32) { _ };
pub const Profile = enum(u32) { _ };
pub const TargetPoint = enum(u32) { _ };
pub const BoundaryStack = enum(u32) { _ };

These tokens are cheap to copy and easy for the optimizer. They also prevent passing a momentum where an index is required.

For boundary data, the user-facing shape should be similarly physical: 

const brane = cft.presets.freeBosonBoundary(.{
    .neumann = X.target.subspace(.{ 0, 1, 2, 3 }),
    .dirichlet = X.target.complement(.{ 0, 1, 2, 3 }),
    .dirichlet_position = try local.point("x0"),
    .chan_paton = cp.stack("N"),
});

The projectors and Chan-Paton tensors may lower to Tensor-Code handles, but the user should not manually provide those handles in ordinary code.

5. Local Builder And Label Store

The generated local builder owns a compact label arena. Operator builders write label records to that arena and return local operators that point to label spans. 

const LocalOp = struct {
    insertion: OperatorInsertion,
    kind: OperatorKindId,
    labels: LabelSpan,
};

const MultiOp = struct {
    operators: []const LocalOp,
    labels: *const LabelStore,
};

This keeps the runtime call narrow while preserving labels. A MultiOp is still just a collection of local operators; it carries the label store because the collection is not meaningful without the labels.

The builder should append small fixed-width label records. It should not allocate expression trees. 

const LabelValue = union(enum) {
    integer: i64,
    rational: Rational,
    tensor: tensor.kernel.TensorExprId,
    symbol: SymbolId,
};

For common labels such as vector indices, derivative labels, momenta, and profile ids, the records are tiny. Larger physics objects remain behind handles owned by the preset, tensor-code, or the client.

6. Operator Builders

Operator builders should stop returning a kind-only body. They should emit a local operator with the appropriate label span. 

pub fn expX(self: *Local, k: Momentum, z: Coord, zbar: Coord) !LocalOp {
    const labels = try self.labels.append(.{ .momentum = raw(k) });
    return self.op(.exp_x, .bulk(z, zbar), labels);
}

The same pattern covers dX(mu,n,z), profile(f,z,zb), dXBoundary(mu,n,y), and cBoundary(n,y). The generated builder knows the schema; the user only sees the typed arguments.

7. User-Side Wick Definitions

The preset author should define primitive Wick rules in physics names. They should not write operator-kind ids, coordinate-factor ids, or coefficient-store records by hand. The built-in presets should contain definitions of this form: 

pub const wick = cft.presets.wick;

const free_boson_sphere_wick_rules = [_]wick.Rule{
    wick.rule(wick.dX(), wick.dX(), .{ .generated = .free_boson_dx_dx }),
    wick.rule(wick.dXt(), wick.dXt(), .{ .generated = .free_boson_dxt_dxt }),
    wick.rule(wick.dX(), wick.expX(), .{ .generated = .free_boson_dx_exp_x }),
    wick.rule(wick.dXt(), wick.expX(), .{ .generated = .free_boson_dxt_exp_x }),
    wick.rule(wick.expX(), wick.expX(), .{ .generated = .free_boson_exp_x_exp_x }),
};

const bc_sphere_wick_rules = [_]wick.Rule{
    wick.rule(wick.b(), wick.c(), .{ .generated = .bc_b_c }),
    wick.rule(wick.bt(), wick.ct(), .{ .generated = .bc_bt_ct }),
};

const free_boson_disk_wick_rules = [_]wick.Rule{
    wick.rule(wick.dXBoundary(), wick.dXBoundary(), .{ .generated = .boundary_free_boson_dx_dx }),
    wick.rule(wick.dXBoundary(), wick.expXBoundary(), .{ .generated = .boundary_free_boson_dx_exp_x }),
    wick.rule(wick.expXBoundary(), wick.expXBoundary(), .{ .generated = .boundary_free_boson_exp_x_exp_x }),
    wick.rule(wick.dX(), wick.dXBoundary(), .{ .generated = .mixed_free_boson_dx_dx_boundary }),
    wick.rule(wick.dXt(), wick.dXBoundary(), .{ .generated = .mixed_free_boson_dxt_dx_boundary }),
    wick.rule(wick.dX(), wick.expXBoundary(), .{ .generated = .mixed_free_boson_dx_exp_x_boundary }),
    wick.rule(wick.dXt(), wick.expXBoundary(), .{ .generated = .mixed_free_boson_dxt_exp_x_boundary }),
    wick.rule(wick.expX(), wick.expXBoundary(), .{ .generated = .mixed_free_boson_exp_x_exp_x_boundary }),
};

const bc_disk_wick_rules = [_]wick.Rule{
    wick.rule(wick.bBoundary(), wick.cBoundary(), .{ .generated = .boundary_bc_b_c }),
    wick.rule(wick.b(), wick.cBoundary(), .{ .generated = .mixed_bc_b_c_boundary }),
    wick.rule(wick.c(), wick.bBoundary(), .{ .generated = .mixed_bc_c_b_boundary }),
    wick.rule(wick.bt(), wick.cBoundary(), .{ .generated = .mixed_bc_bt_c_boundary }),
    wick.rule(wick.ct(), wick.bBoundary(), .{ .generated = .mixed_bc_ct_b_boundary }),
};

The generated evaluator tags are still physics-facing. The lowering step maps these templates to compact Theory rule sets. At runtime the evaluator reads the two local operators, their labels from the MultiOp label store, the selected convention data, and the relevant coordinate slots. This keeps the user-side definition readable while keeping the hot path table-driven.

8. Wick Rule Encoding

The current code does not encode Wick rules. The replacement should be a sparse rule table per CorrelatorConfig. 

const WickRule = struct {
    left: OperatorKindId,
    right: OperatorKindId,
    evaluator: WickEvaluator,
    data: RuleDataId,
};

const WickRuleSet = struct {
    rules: []const WickRule,
};

The evaluator should be either a small generated tag for built-in fast paths or a client-supplied procedure for genuinely custom theories. 

const WickEvaluator = union(enum) {
    generated: GeneratedWickEvaluator,
    custom: CustomWickEvaluator,
};

The evaluator receives only what it needs: two local operators, the label store, rule data, and an output sink. 

fn evalPair(
    rule_data: RuleDataId,
    left: LocalOp,
    right: LocalOp,
    labels: *const LabelStore,
    sink: anytype,
) !void;

For the first presets, the generated evaluator tags should cover:

  • free-boson derivative/derivative pairings;
  • free-boson derivative/exponential pairings;
  • free-boson exponential/exponential multiplicative factors;
  • profile rewrites before Wick evaluation;
  • \(bc\) first-order pairings;
  • boundary free-boson and mixed bulk-boundary kernels;
  • boundary \(bc\) and mixed bulk-boundary \(bc\) kernels.

9. Zero-Mode Rules

Zero-mode rules should be separate from pairwise Wick rules. They consume the residual uncontracted local operators after Wick recursion. 

const ZeroModeRule = struct {
    sector: SectorId,
    evaluator: ZeroModeEvaluator,
    data: RuleDataId,
};

const ZeroModeRuleSet = struct {
    rules: []const ZeroModeRule,
};

For the first presets, the generated zero-mode evaluators should cover:

  • free-boson noncompact momentum conservation;
  • explicit zero-mode integrals for position-space profiles;
  • Neumann projected momentum conservation;
  • Dirichlet evaluation at the brane position;
  • sphere \(bc\) top-form saturation;
  • disk boundary \(bc\) top-form saturation.

Momentum deltas, profile integrals, and brane-position phases should be coefficient factor families. They should not add new branches to the correlator algorithm.

10. Correlator Config

A config should point to actual tables, not placeholder ids. 

pub const CorrelatorConfig = struct {
    wick_rules: WickRuleSetId,
    zero_modes: ZeroModeRuleSetId,
};

The runtime call remains: 

try Theory.correlator(Theory.config.sphere, ops, sink);

Here ops already carries its label store. The config chooses the Wick and zero-mode tables. No surface object or boundary-condition object is passed at runtime.

11. Product And Boundary Composition

The current hard-coded product/boundary wrapper is acceptable as a temporary scaffold, but the improved lowering should merge generated namespaces from the supplied factors and extensions.

The rule is simple:

  • product(.{ X, bc }) exposes only builders contributed by X and bc;
  • boundary(Bulk, .{ freeBosonBoundary(...) }) exposes only the selected boundary free-boson builders;
  • adding bcDiskBoundary(.{}) exposes boundary ghosts and mixed ghost rules;
  • Chan-Paton stacks remain labels on boundary operators and may point to tensor-code data.

This avoids a generic runtime registry. Composition is a compile-time lowering step over a small tuple of factors.

12. Implementation Order

  1. Replace public naked Handle aliases in Presets with generated opaque physics structs.
  2. Add a generated Local builder with a compact label arena and typed constructors for coordinates, indices, momenta, profiles, target points, subspaces, and Chan-Paton stacks.
  3. Change operator builders to preserve label spans in LocalOp.
  4. Replace placeholder CorrelatorConfig ids with real WickRuleSet and ZeroModeRuleSet ids.
  5. Implement generated Wick evaluator tags for free boson and \(bc\) on the sphere.
  6. Implement generated zero-mode evaluators for free-boson momentum/profile rules and \(bc\) top forms.
  7. Extend the same lowering to disk free-boson BCFT and boundary \(bc\).
  8. Replace hard-coded product/boundary wrappers with compile-time namespace composition over supplied factors.

13. Tests Worth Keeping

Tests should check design invariants, not syntax.

  • expX(k1,...) and expX(k2,...) preserve distinct momentum labels.
  • dX(mu,n,z) preserves both the vector index and derivative label.
  • product(.{X,bc}) exposes exactly the expected bulk builders.
  • boundary(...freeBosonBoundary...) exposes boundary free-boson builders and does not expose boundary ghosts unless bcDiskBoundary is present.
  • sphere \(bc\) top form evaluates the three-\(c\) correlator normalization.
  • free-boson sphere zero modes emit a momentum-conservation factor for plane waves.

The first two tests should be written before any Wick evaluator. They protect the UX/data boundary that is currently broken.

14. What Not To Do

Do not add a general runtime “context” object to correlator calls. The operator collection can carry labels; the config can carry Wick and zero-mode tables. That is enough.

Do not make coefficient-code learn about every physics case. Momentum deltas, profile integrals, Chan-Paton traces, pure-spinor measures, and lattice theta factors should remain factor families.

Do not implement a broad plugin registry or reflection-heavy namespace merger before the first free-boson/\(bc\) presets work. The compile-time tuple of factors is sufficient for now.

Do not make Wick rules allocate full expanded expressions. Rule evaluators stream coefficient factors and residual local operators into sinks.

15. AGENTS Audit

This plan is aligned with AGENTS.md.

  • Data-oriented: labels are compact arena records; local operators point to spans; Wick and zero-mode rules are sparse tables.
  • Minimal runtime data: correlator receives a config, a local-operator collection, and a sink.
  • Memory discipline: rule evaluators stream terms and do not materialize large symbolic trees.
  • Parallelizable flow: sectors and independent Wick branches can be streamed independently once the label store is immutable.
  • Minimal public API: users see typed physics builders; ids, label spans, evaluator ids, and rule data stay private.
  • Literate structure: this note links to the relevant literate modules; the implementation should happen in Presets, Theory, CFT Kernel, Wick, and Correlators.
  • Test discipline: the proposed tests protect label preservation, namespace selection, zero-mode rules, and first real physics checks.

The approved design point is that MultiOp carries a pointer to its immutable label store. It preserves the principle that correlator does not receive a separate context, while making the operator collection self-contained enough for fast runtime evaluation.
