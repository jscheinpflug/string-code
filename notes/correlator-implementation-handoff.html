1. Purpose

This note records the current implementation boundary for the future full correlator. It is a handoff for implementing the algorithm, not a redesign of the CFT data structures.

The relevant code nodes are CFT-Code, Presets, Preset Shared Runtime, Free Boson Preset, bc Preset, Preset Composition, CFT Kernel, and Correlators. Coefficients are represented by Coefficient, while tensor factors are intended to flow into Tensor-Code.

The design principle to preserve is narrow data flow. The correlator receives only the operator collection, a compiled correlator config, and a sink. It does not receive a theory context, a surface object, boundary-condition data, or user-side preset internals. Surface and boundary choices have already been compiled into Wick rules, zero-mode rules, and small typed config entries.

2. Current User-Facing Shape

The root CFT API is intentionally compact. User code should import the root module and use family objects: 

const cft = @import("string-code").cft;

const X = cft.FreeBoson.make(.{ .dimension = 26 });
const Ghost = cft.Bc.sphere(.{});
const Sphere = cft.product(.{ X, Ghost });

const Disk = cft.boundary(Sphere, .{
    cft.FreeBoson.boundary(.{
        .neumann = X.target.subspace(&.{ 0, 1, 2, 3 }),
        .dirichlet = X.target.complement(&.{ 0, 1, 2, 3 }),
        .dirichlet_position = X.target.point("x0"),
        .chan_paton = X.target.boundaryStack("stack"),
    }),
    cft.Bc.diskBoundary(.{}),
});

The root exposes Handle and scalars as support vocabulary, but it does not expose implementation modules such as presets, kernel, theory, or expressions. The old flat constructor names are also not root API.

Generated presets expose:

  • op namespaces for local operator builders;
  • profile and target helpers where a preset needs physics handles;
  • config with named correlator configs such as sphere or disk;
  • local(allocator) for building a MultiOp with its label store;
  • correlator(config_ptr, ops, sink) as the current execution wrapper.

The current wrapper is a first streaming boundary, not the final correlator. It emits primitive pair Wick terms and zero-mode rule events. The full implementation should replace this with recursive Wick pairing and base-case zero-mode evaluation while keeping the same narrow call shape.

3. Runtime Inputs

The full correlator should take exactly: 

pub fn correlator(config_ptr: *const CorrelatorConfig, ops: kernel.Call.MultiOp, sink: anytype) !void

In the current preset implementation, CorrelatorConfig is internal to Preset Shared Runtime. It contains: 

const CorrelatorConfig = struct {
    wick_rules: []const wick.Rule,
    zero_modes: []const zero_mode.Rule,
    config_entries: []const ConfigEntry = &.{},
};

The correlator should treat this as compiled runtime data. It should not ask for a separate surface. Sphere, disk, doubling, Neumann/Dirichlet projectors, Chan-Paton stack handles, and convention scalars enter through the selected config and its rule tables.

The operator input is kernel.Call.MultiOp from CFT Kernel: 

const MultiOp = struct {
    operators: []const LocalOp,
    labels: *const LabelStore,
};

This is just a collection of local operators plus the out-of-line labels those operators reference. It is not a context. The correlator may reorder, contract, or mark entries inactive in a work stack, but it should not allocate a large expression tree.

4. Wick Access

The full correlator must not inspect Wick-rule internals. The current implementation boundary is the pair emitter in Preset Shared Runtime: 

pub fn emitWickPairTerms(
    config_ptr: *const CorrelatorConfig,
    ops: kernel.Call.MultiOp,
    left_index: usize,
    right_index: usize,
    sink: anytype,
) !usize

This function takes two operator positions, matches the compiled Wick rule table, resolves runtime labels and config-backed projectors, evaluates universal coordinate derivatives on powers/logs/Green kernels, and emits each primitive Wick term to a sink. It returns the number of primitive terms emitted.

The sink contract is structural: 

try sink.emitWickTermStart(event);
try sink.emitWickScalar(factor);
try sink.emitWickCoordinate(factor);
try sink.emitWickTensor(factor);
try sink.emitWickAction(factor);
try sink.emitWickTermEnd();

Only this sink boundary should be visible to the recursive correlator. The correlator should not receive wick.Rule, resolved label references, config references, or derivative bookkeeping. If the correlator needs to multiply a primitive contraction into its current coefficient, it should use a small accumulator sink that receives these events and appends the factors to the current streamed term.

The factors currently emitted cover:

  • structured scalar monomials, including rational factors, \(i\)-powers, and named atoms such as \(\alpha'\);
  • coordinate factors: powers, logarithms, named Green kernels, and Green-exponential factors;
  • tensor factors: metrics, momentum-index contractions, momentum pairs, and config-backed projector versions of these;
  • action factors: profile derivatives and projected profile derivatives.

This already covers the primitive Wicks needed for the implemented free boson, its Neumann/Dirichlet boundary extension, and the \(bc\) system on sphere and disk. Future \(\psi,\phi,\eta,\xi\), Narain/bosonized spin fields, SO(32), and \(E_8\times E_8\) presets should extend the rule vocabulary only when a new primitive factor cannot be represented by these scalar, coordinate, tensor, or action events.

5. Zero-Mode Access

Zero-mode rules are separate from Wick rules. They are selected by the compiled config: 

config_ptr.zero_modes

Current rule expressions include momentum conservation, explicit profile integrals, Dirichlet positions, and \(bc\) top-form saturation. The current streamer simply emits them after primitive pair events. The full correlator must instead apply zero-mode rules at the Wick-recursion base case.

The base case is reached after no more Wick pairings are chosen for a branch. At that point the branch has:

  • a residual ordered list of uncontracted local operators;
  • a coefficient accumulator built from emitted Wick factors;
  • a sign/parity accumulator once fermionic sectors are added;
  • the same config_ptr used for Wick matching.

The zero-mode evaluator should inspect only the residual operators, their labels, and config_ptr.zero_modes. It should emit either zero branch weight, a finite coefficient factor, or a residual symbolic zero-mode object. For arbitrary free-boson profiles, keeping the zero-mode integral explicit is the correct generic behavior. Fourier-presented profiles may later allow partial evaluation by momentum conservation.

The zero-mode evaluator should be a separate small procedure, not folded into the Wick pair emitter. Wick pair emission knows about two local operators. Zero-mode evaluation knows about the residual collection.

6. Full Correlator Algorithm

The target algorithm is a streaming recursive Wick engine.

  1. Build a work view over ops.operators. This can be an index array, an active bitset, or a small stack frame. Do not copy local operators unless a compact index view is insufficient.
  2. Choose the next active operator. The first implementation can use the first active index. Later heuristics may choose the operator with fewest possible Wick partners.
  3. For each active partner to its right, call emitWickPairTerms with a branch accumulator sink.
  4. For each emitted primitive term, multiply the emitted factors into the branch accumulator, mark the two operators contracted, and recurse.
  5. Also decide whether a no-contraction branch is allowed. For ordinary Wick-only normal-ordered elementary fields it is not always allowed in the same way; for residual operators and zero-mode-sensitive fields it may be necessary. This should be controlled by operator/preset data, not by an ad-hoc global rule.
  6. At the base case, run the zero-mode evaluator on the residual operators and the accumulated coefficient. Emit final terms to the user sink immediately.

The essential point is that the correlator streams branches. It should not construct the full sum of pairings before simplification. Simplification should be attachable as a downstream filter on the output stream.

7. Accumulators And Sinks

The implementation needs at least two sink layers.

The first sink is a primitive Wick-term accumulator. It is local to one candidate pair and one recursion branch. It receives events from emitWickPairTerms and appends factors into a compact term buffer.

The second sink is the final correlator output sink. It receives completed correlator terms after zero-mode evaluation. Its exact public event vocabulary can be introduced in Correlators, but it should mirror the same data-oriented idea:

  • begin term;
  • emit scalar factor;
  • emit coordinate factor;
  • emit tensor factor;
  • emit residual operator or zero-mode object;
  • end term.

The primitive accumulator should use bounded stack storage for the common case, or caller-provided scratch storage for large terms. It should not own a general expression tree. When a primitive term is complete, the recursive engine either immediately recurses with that term multiplied into the branch or discards the branch if any factor resolution failed.

8. Signs And Fermions

The current implemented presets are free boson and \(bc\). The full correlator must nevertheless leave a clean place for signs before adding the RNS and heterotic sectors.

The correct place is the recursion frame:

  • each local operator kind needs enough parity data to decide the sign for bringing two fields together;
  • the work view must know the current ordered residual list;
  • when contracting positions \(i,j\), the branch sign is determined by moving the selected fields through the active residual list according to their parities and sector tactics.

Do not encode special cases such as “\(\phi\)-\(\psi\) system” in the correlator. Presets should compile operator parities and Wick factors. For example, an \(e^{q\phi}\psi\) sector can make \(e^{q\phi}\) odd for odd \(q\) and even for even \(q\), while \(\psi\) remains fermionic, without changing the correlator algorithm.

9. What Is Already Implemented

Current working pieces:

  • root CFT API with compact family objects FreeBoson and Bc;
  • product and boundary composition of generated presets;
  • local operator builders with typed handles and out-of-line labels;
  • compile-time generated operator kind ids and zero-mode sector ids;
  • structured scalar factors, so constants like \(-\alpha'/2\) are not stored as magic strings;
  • config-backed Wick factors, including Neumann/Dirichlet projectors and Chan-Paton stack handles;
  • primitive pair Wick emission for free-boson and \(bc\) pairs;
  • derivative labels acting on coordinate powers and logarithms;
  • action factors for \(dX^\mu(z)F(X(w))\)-type contractions;
  • current zero-mode rule records for momentum conservation, profile integrals, Dirichlet positions, and \(bc\) top forms.

The current streamCorrelator is only a diagnostic driver. It loops over all operator pairs and emits pair-level Wick events plus zero-mode events. It does not yet choose non-overlapping pairings, recurse through branches, manage fermionic signs, multiply factors into a branch coefficient, or evaluate zero-mode base cases.

10. Immediate Implementation Plan

  1. Move the full algorithm into the correlator implementation boundary, but keep the user call shape identical: config_ptr, MultiOp, sink.
  2. Keep emitWickPairTerms as the only way the algorithm asks for primitive pair contractions. If this function must move modules later, preserve the opaque sink contract.
  3. Implement a compact branch frame:
    • active operator mask or index list;
    • accumulated sign;
    • compact coefficient-factor stack;
    • residual operator view.
  4. Implement a primitive-term accumulator sink used only inside recursion.
  5. Implement base-case zero-mode evaluation as a separate function over the residual operator view and config_ptr.zero_modes.
  6. Add tests that prove concepts, not syntax:
    • free-boson two-point \(dX dX\) emits one final term;
    • free-boson \(dX e^{ikX}\) resolves momentum-index tensor data and derivative coordinate factors;
    • boundary free-boson rules resolve config-backed Neumann projectors;
    • \(bc\) sphere top-form zero mode distinguishes saturated from unsaturated residual \(c\)-ghost configurations;
    • a three- or four-operator input uses non-overlapping pairings rather than emitting all pair events independently.

11. Things Not To Add Yet

Do not add a correlator context. The config pointer is the context that the generic algorithm needs.

Do not add separate OPE and OPEProjected machinery here. OPE should later use correlators plus pairing/projection data and can call the same primitive Wick boundary.

Do not add a general simplifier inside the correlator. Emit a stream of final terms and allow simplification to be a filter.

Do not encode pure-spinor constraints, equations of motion, regularization schemes, or string-field-theory vertex data in the generic correlator. Those belong in client layers or in concrete preset rule generation.

Do not expose wick.Rule, zero_mode.Rule, or shared runtime internals in the root API. If the implementation needs a better internal boundary, introduce a small opaque pair-emitter interface rather than widening the user API.

12. Open Questions Before Coding

The next implementation pass should ask for domain sign-off on these points:

  1. For the first recursive correlator, should residual uncontracted operators be allowed only when a zero-mode rule can consume them, or should presets explicitly mark which operator families may survive to the base case?
  2. What exact \(bc\) sphere top-form should the first zero-mode evaluator recognize: only three \(c\)-type insertions, or also derivative descendants such as \(c\partial c\partial^2 c\) as equivalent saturated forms?
  3. For final correlator output, should residual zero-mode/profile integrals be emitted as a coefficient factor or as a residual operator-like object?
  4. When fermionic sectors are added, where should operator parity be stored in generated preset data so the recursive sign algorithm never inspects physics-specific operator names?

These are the points that affect the implementation shape. They should be settled before widening the algorithm beyond free boson and \(bc\).
