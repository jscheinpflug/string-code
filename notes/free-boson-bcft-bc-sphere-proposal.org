#+title: Free Boson, Profiles, bc Sphere, And Basic BCFT Proposal
#+date: 2026-06-06
#+PROPERTY: header-args:zig :tangle no

* Goal

This is a drawing-board proposal for the first concrete CFT presets to build
on top of [[id:20260605T090102.250727][Theory]], [[id:20260603T094125.997360][Operators]],
[[id:20260603T094138.285453][Correlators]], [[id:20260606T064107.303587][Wick]], and
[[id:20260605T075909.433647][Tensor-Code]].

The target is deliberately small but physically diagnostic:

- a \(D\)-dimensional free boson \(X^\mu\), including arbitrary \(X\)-profiles
  as in =prototype-string-code/=;
- the holomorphic \(bc\) ghost system on the sphere;
- the basic BCFT extensions needed for a free boson with Neumann/Dirichlet
  directions, plus the standard boundary ghost sector.

The proposal keeps runtime correlators lean.  A correlator receives local
operators and a compiled rule config: Wick rules, zero-mode rules, and the
few convention constants needed by those rules.  Boundary conditions, gluing,
and doubling are used earlier when building the BCFT preset.

* Free Boson Preset

The free boson is a bulk CFT sector parameterized by dimension, conventions,
and target-space invariant data.  Dimension is not a cosmetic label: it
decides the vector representation, the metric/delta contractions, and whether
epsilon-type \(SO(D)\) invariants are available.

#+begin_src zig
const FreeBosonSpec = struct {
    dimension: u16,
    alpha_prime: ConventionScalar,
    dX_normalization: ConventionScalar,
    vector_symmetry: TensorSymmetryRef,
    vector_rep: TensorRepRef,
    metric: TensorInvariantRef,
};
#+end_src

For the first implementation, =vector_symmetry= should be \(SO(D)\) with the
vector representation.  The tensor module should own identities such as
\(\delta^\mu{}_\mu=D\), metric contractions, and optionally epsilon identities.
The free-boson Wick rules should only ask tensor-code for those invariant
handles and streamed contractions.

The bulk operator families are:

- \(\partial^{n+1}X^\mu(z)\), represented as =dX= with a vector index and a
  nonnegative derivative label \(n\);
- \(\bar\partial^{n+1}X^\mu(\bar z)\), represented as =dXt=;
- \(:e^{ikX}(z,\bar z):\), with a momentum label in the vector dual;
- holomorphic and antiholomorphic factorized exponentials when the client
  explicitly chooses a chiral presentation;
- arbitrary \(X\)-profiles, with labels pointing to a symbolic target-space
  profile and to the target derivatives already taken.

The profile point is important.  A profile is not a surface and not a special
case in the correlator.  It is an operator body whose label says "this body
depends on \(X\) through a profile \(F(X)\)".  The free-boson preset may then
rewrite that body through a chosen presentation before using the generic
correlator.

For a genuinely arbitrary profile, this does not mean there is a closed
pairwise Wick factor \(F(X(z))G(X(w))\).  Such a closed factor exists for
exponentials and for special derivative-closed families, but not for an
arbitrary function.  In position space, the exact free-boson answer is a
Gaussian differential operator acting on the profile product, followed by the
zero-mode integral.

#+begin_src zig
const FreeBosonBodyLabel = union(enum) {
    dX: struct { mu: TensorIndex, derivative: u16 },
    dXt: struct { mu: TensorIndex, derivative: u16 },
    expX: struct { momentum: MomentumRef },
    expX_holo: struct { momentum: MomentumRef },
    expX_anti: struct { momentum: MomentumRef },
    profileX: ProfileLabel,
    profileX_holo: ProfileLabel,
    profileX_anti: ProfileLabel,
};

const ProfileLabel = struct {
    profile: ProfileRef,
    target_derivatives: ProfileDerivativeSpan,
};
#+end_src

This mirrors the prototype's =ProfileX[profile, ders, z, zbar]=,
=ProfileXHolo=, and =ProfileXAntiHolo=.  The new code should not expand
profiles into polynomials unless the user selected the polynomial
presentation.  The preset decides whether a profile is evaluated in position
space, Fourier space, or a polynomial expansion; the generic correlator only
sees the resulting bodies and scalar factors.

* Free Boson Wick Data

The sphere Wick rules are the local data:

- \(dX^\mu dX^\nu\) gives a metric/delta tensor times derivatives of the
  holomorphic kernel;
- \(dXt^\mu dXt^\nu\) is the antiholomorphic copy;
- mixed \(dX dXt\) vanishes on the sphere;
- \(dX^\mu\) contracts with \(e^{ikX}\) by emitting \(k^\mu\);
- \(dX^\mu\) acting on a position-space profile contributes a differential
  operator \(\partial_\mu F\) inside the residual profile functional;
- Fourier-presented profiles reduce to exponentials, so exponential Wick
  factors are reused;
- polynomial-presented profiles reduce to finite normal-ordered products of
  \(X\)-fluctuation bodies.

This is still ordinary Wick data once the presentation has been chosen.
The only additional distinction is that some pairings are additive
contractions, while exponential pairings are multiplicative factors.  That
distinction belongs in the Wick rule table, not in the operator data
structure.

#+begin_src zig
const WickRuleKind = enum {
    additive_pair,
    multiplicative_pair,
};

const WickRule = struct {
    left_kind: OperatorKindId,
    right_kind: OperatorKindId,
    kind: WickRuleKind,
    evaluator: WickEvaluatorRef,
};
#+end_src

The runtime correlator does not need to know that one of these rules came from
a profile or a plane wave.  It only needs to stream the rule's emitted
coefficient and residual operator bodies.

* Weights And Conventions

The free boson must compute weights at runtime from labels:

- \(dX^\mu_n\) has holomorphic weight \(1+n\);
- \(dXt^\mu_n\) has antiholomorphic weight \(1+n\);
- \(e^{ikX}\) has weights determined by the chosen \(\alpha'\) convention and
  \(k^2\);
- profile weights are rule-defined.  Initially they can be abstract unless the
  profile label supplies enough data to compute them.

The convention set should make it easy to change \(\alpha'\), the sign of the
two-point function, and the normalization of \(dX\).  These are preset
conventions, not client-side rewrites of every Wick rule.

#+begin_src zig
const FreeBosonConvention = struct {
    alpha_prime: ConventionScalar,
    xx_green_sign: i2,
    dX_dX_prefactor: ConventionScalar,
    expX_weight_prefactor: ConventionScalar,
    boundary_expX_weight_prefactor: ConventionScalar,
};
#+end_src

For the first preset, the values can match the prototype.  The point of this
object is that Ashoke/Xi/other convention choices become data used by the
rule builders, not forks of the operator representation.

* bc System On The Sphere

The sphere \(bc\) ghost preset is a chiral first-order system with:

- \(b(z)\), weight \(2\), ghost number \(-1\), fermionic;
- \(c(z)\), weight \(-1\), ghost number \(+1\), fermionic;
- optional antiholomorphic copy \(bt(\bar z),ct(\bar z)\) for closed-string
  calculations;
- Wick kernel \(b(z)c(w)\sim 1/(z-w)\) with derivative labels handled by
  differentiating the kernel;
- a sphere zero-mode/top-form rule for the three \(c\) zero modes.

The correlator engine should not hard-code \(\langle ccc\rangle\).  It should
receive a zero-mode rule saying that the surviving \(c\)-sector top form on
the sphere is represented by three modes.  From that, the familiar values
such as
\[
  \langle c(z_1)c(z_2)c(z_3)\rangle
  =(z_1-z_2)(z_1-z_3)(z_2-z_3)
\]
are emitted by the zero-mode evaluator.

For the \(bc\) preset, this is private rule data behind the generic
zero-mode evaluator:

#+begin_src zig
const BcTopFormData = struct {
    sector: SectorId,
    field_kind: OperatorKindId,
    modes: []const i16,
    normalization: ConventionScalar,
    kill_if_unpaired_kind_present: []const OperatorKindId,
};
#+end_src

This is the same physics as the prototype's registered top-form VEV sector,
but it is not a public coefficient variant.  It is table data used by the
=bc_sphere_top_form= zero-mode evaluator.  The same private shape also works
for the antiholomorphic \(ct\) copy.

* Free Boson BCFT

The free-boson BCFT is compiled from the bulk free-boson preset plus a boundary
condition.  The bulk CFT spec remains boundary-free.

A Neumann/Dirichlet condition is most compactly encoded by a reflection matrix
on the vector representation:
\[
  R^\mu{}_\nu = +\delta^\mu{}_\nu \quad \text{on Neumann directions},\qquad
  R^\mu{}_\nu = -\delta^\mu{}_\nu \quad \text{on Dirichlet directions}.
\]
Dirichlet directions may also carry a position \(x_0^\mu\).  Neumann
directions carry the ordinary momentum-conservation zero-mode rule.

#+begin_src zig
const FreeBosonBoundaryCondition = struct {
    name: []const u8,
    reflection: TensorExprRef,
    neumann_projector: TensorExprRef,
    dirichlet_projector: TensorExprRef,
    dirichlet_position: ?TargetVectorRef,
};
#+end_src

From this, the BCFT builder compiles:

- boundary-local operator kinds such as \(dX_B^\mu(x)\), boundary
  exponentials, and boundary profiles;
- mixed bulk-boundary Wick kernels;
- disk/UHP zero-mode rules;
- optional boundary-changing families for strings stretched between different
  Dirichlet positions or more general branes.

Boundary operators are chiral in the boundary CFT.  A bulk operator remains
bulk and may be chiral, antichiral, or both.  The BCFT builder may use the
doubling trick internally, but the runtime correlator only sees the resulting
local operators and rule config.

* Neumann And Dirichlet Boundary Operators

For Neumann directions, boundary \(X\)-dependent operators have a genuine
zero mode along the brane.  Boundary exponentials and boundary profiles may
carry momentum/profile dependence in the Neumann subspace, and the disk
zero-mode rule imposes the corresponding conservation law.

For Dirichlet directions, the zero mode is fixed by the brane position.  Bulk
closed-string exponentials near the disk can produce factors depending on
\(x_0^\mu\), while boundary exponentials should not pretend that Dirichlet
momentum is integrated.  This distinction belongs in the BCFT zero-mode rule
and in the allowed boundary operator families.

The stringbook convention that the boundary normal ordering differs from bulk
normal ordering should be represented by the boundary Wick rule and boundary
weight rule.  In particular, the dimension of a boundary exponential is
controlled by the boundary kernel and need not equal the sum of the bulk left
and right weights.

#+begin_src zig
const BoundaryFreeBosonFamilies = struct {
    dX_boundary: OperatorKindId,
    expX_boundary: OperatorKindId,
    profileX_boundary: OperatorKindId,
    boundary_changing: []const OperatorKindId,
};
#+end_src

The factor of two relating \(\partial_y X(y)\) and the holomorphic boundary
field in Neumann directions should be a convention in the BCFT preset.

* Boundary bc Ghosts

The ghost BCFT is not Neumann/Dirichlet in the target-space sense.  It is the
standard boundary gluing of the holomorphic and antiholomorphic ghost systems,
compiled into a chiral boundary \(bc\) system with disk zero modes.

For the first implementation, it is enough to support:

- boundary \(b(x)\), \(c(x)\) with the same first-order Wick kernel;
- disk/UHP top-form rule for the three boundary conformal Killing zero modes;
- mixed bulk-boundary ghost rules for open-closed disk amplitudes.

This keeps the target-space Neumann/Dirichlet data attached only to the free
boson and keeps the ghost boundary condition as ghost-sector BCFT data.

* Correlator Algorithm Check

The existing correlator direction is sufficient if the config object is
specific enough.  The algorithm should be:

1. Receive a collection of local operators and a =CorrelatorConfig=.
2. Flatten multilocal input into local insertions without changing bodies.
3. Stream over sectors and operator bodies; do not allocate a full expanded
   expression unless the caller explicitly asks for materialization.
4. Apply zero-mode selection early when it can prove the correlator vanishes.
5. Apply additive and multiplicative Wick rules by pair lookup on operator
   kinds and labels.
6. Pass leftover uncontracted fields to the zero-mode rule.
7. Emit coefficient/tensor/operator residual terms as a stream.

That gives enough data for:

- free-boson sphere correlators with \(dX\), \(dXt\), \(e^{ikX}\), and
  arbitrary profiles;
- sphere \(bc\) correlators, including derivative \(c\)'s and insertions at
  infinity once BPZ limits are implemented;
- disk/UHP free-boson BCFT correlators for Neumann/Dirichlet directions;
- boundary ghost correlators on the disk.

The OPE implementation can still be the projected OPE computed from
correlators plus pairing data.  For local bulk OPEs the sphere config is
enough; for boundary OPEs the disk/BCFT config is enough.

* User-Facing Theory Tools

The public surface for defining a CFT should be physics-facing.  A user should
not construct coefficient terms, scalar-factor labels, scratch buffers, or
stream filters by hand.  Those are implementation details used by generated
theory code.

For the free-boson and \(bc\) presets, the theory author should declare:

- operator families such as \(dX^\mu\), \(X^\mu\), \(e^{ikX}\), profiles,
  \(b\), and \(c\);
- their weights, statistics, quantum numbers, and label schemas;
- Wick kernels, written as physics rules such as
  \(\langle X^\mu(z)X^\nu(w)\rangle=-\alpha'\eta^{\mu\nu}\log|z-w|\)
  or \(\langle b(z)c(w)\rangle=(z-w)^{-1}\);
- zero-mode rules such as \(bc\) top-form saturation or free-boson momentum
  conservation/profile integration;
- optional presentation rewrites such as Fourier profiles and polynomial
  Riemann-normal-coordinate expansions.

The preset builder lowers these declarations to compact operator-kind ids,
label schemas, Wick evaluators, zero-mode evaluators, and scalar-factor
families.  The generated theory then exposes ergonomic builders such as
=O.dX(mu, n, z)=, =O.X(mu, z, zbar)=, =O.expX(k, z, zbar)=,
=O.profile(F, z, zbar)=, =O.b(z)=, and =O.c(z)=.

* Zero Modes And Coefficient Factors

The phrase "zero-mode rule" should mean the last evaluation step after Wick
contractions.  It is not only a selection rule.  It consumes the residual
uncontracted bodies in one sector and emits scalar coefficient factors.  For
the \(bc\) system this is finite Grassmann top-form saturation.  For free
bosons this is continuous zero-mode integration.  For arbitrary profiles, the
correct first implementation is to keep the zero-mode integral explicit.

The important data-shape decision is that [[id:20260604T083119.372970][Coefficient]] should not learn new
physics every time a user defines a CFT.  It should know how to multiply,
add, stream, sort, and compare compact coefficient terms.  The existing
=RationalFunction= shape should be extended into the tight scalar-factor
product used by all coefficient terms.

#+begin_src zig
const CoeffTerm = struct {
    scalar: ExactScalar,
    scalar_function: RationalFunction,
    tensor_factor: TensorExprRef,
};

const RationalFunction = struct {
    factors: FactorSpan,
};

const Factor = union(enum) {
    polynomial_power: PolynomialPower,
    coordinate_power: CoordinatePower,
    coordinate_log: CoordinateLog,
    named_kernel: NamedKernelFactor,
    custom: CustomScalarFactor,
};
#+end_src

This keeps the coefficient module tight.  It does not need a public variant
called =momentum_delta= or =profile_integral=.  Those are user or preset
=custom= factor families.  The coefficient engine only treats custom factors
through family-supplied equality, hashing, canonicalization, printing, and
optional one-term simplification.

This is necessary because explicit \(X\) insertions and position-space
profile functionals naturally produce logarithmic Green kernels, while local
OPEs of derivative fields and exponentials mostly produce coordinate powers.
Both should be scalar-function factors.  Frequently used factor families such
as coordinate powers and logs should receive optimized implementations, but
the coefficient module should not grow a new union tag for each physics case.

The built-in scalar-function factors should be deliberately few:

#+begin_src zig
const CoordinatePower = struct {
    base: Polynomial,
    exponent: Rational,
};

const CoordinateLog = struct {
    argument: Polynomial,
    convention: LogConventionId,
};

const NamedKernelFactor = struct {
    kernel: GreenKernelId,
    arguments: LabelSpan,
    derivative_labels: LabelSpan,
};

const CustomScalarFactor = struct {
    family: CustomScalarFactorFamilyId,
    labels: LabelSpan,
};
#+end_src

=coordinate_power= covers factors such as \((z-w)^q\), including fractional
powers from spin fields and exponentials.  =coordinate_log= covers factors
such as \(\log(z-w)\), \(\log|z-w|^2\), and their convention variants after
the preset has selected a branch/form.  These two families are small, local,
and common enough to optimize in coefficient-code.

The general Green function should be only a named kernel reference, not a
closed formula baked into coefficient-code.  On a sphere this name may print
as a logarithm.  On a torus it may be represented by theta functions and a
quadratic imaginary-period term.  On a higher-genus surface it may involve
prime forms and period matrices.  On a BCFT surface it may include image
terms.  The coefficient engine should store the factor as
=named_green_kernel(kernel, z, w, derivative_labels)=; the selected
=CorrelatorConfig= or surface preset owns the formula, branch convention,
normal-ordering subtraction, and optional simplifier.

The custom factor extension is how users define new CFTs without editing
coefficient-code.  Examples include momentum delta functions, inverse Fourier
integrals, profile zero-mode integrals, pure-spinor zero-mode measures,
NLSM counterterm factors, lattice theta factors, and partition-function
normalizations.  The kernel can stream these factors and apply user-supplied
filters, but their physics remains outside the coefficient module.

* Zero-Mode Rule Shape

The correlator config should point to sector-wise residual evaluators.
Each evaluator receives only the residual bodies from its sector, the
already-collected scalar factors, and the minimal rule data needed for that
sector.  It returns a stream of coefficient factors, usually one term.

#+begin_src zig
const ZeroModeRule = struct {
    sector: SectorId,
    evaluator: ZeroModeEvaluatorRef,
    rule_data: RuleDataRef,
};

const ZeroModeInput = struct {
    residual_bodies: OperatorBodySpan,
    labels: LabelStoreRef,
};

const ZeroModeOutput = struct {
    factors: FactorSpan,
};
#+end_src

Concrete free-boson rule families then become ordinary preset data:

- =free_boson_bulk_noncompact=: sum all momenta carried by \(e^{ikX}\) and
  Fourier-profile bodies, emit the \(D\)-dimensional momentum delta, and leave
  arbitrary profile zero modes as an explicit integral;
- =free_boson_neumann_boundary=: project momenta and profiles to Neumann
  directions, emit momentum conservation along the brane, and keep profile
  zero-mode integrals over Neumann zero modes when needed;
- =free_boson_dirichlet_boundary=: project to Dirichlet directions and emit
  evaluation/phase factors at \(x_0\), with no Dirichlet momentum integration;
- =bc_sphere_top_form=: localize the surviving \(c\)-ghost modes and emit the
  finite top-form normalization;
- =charge_background=: handle bosonized charge-background rules such as
  \(\phi\), \(H_i\), or later lattice systems.

The zero-mode evaluator should not ask for the full surface object.  It only
uses the rule data already selected by the correlator config.  A sphere free
boson rule and a torus free boson rule may share operator bodies but emit
different scalar factors.

* Momentum And Profiles

Momentum should be first-class enough to sum, project, and pair without
expanding it into coefficient syntax.  This is not a new tensor-code physics
layer; it is a compact vector-expression handle used by free-boson operator
labels and zero-mode rules.

#+begin_src zig
const MomentumLabel = struct {
    vector: VectorExprRef,
};

const ProfileZeroModeLabel = struct {
    profile: ProfileRef,
    argument_space: TargetSubspaceRef,
    target_derivatives: ProfileDerivativeSpan,
};
#+end_src

[[id:20260605T075909.433647][Tensor-Code]] should supply the vector algebra: \(SO(D)\) metric, projectors
for Neumann/Dirichlet subspaces, dot products, and streamed simplification of
linear vector expressions.  It should not know that a vector expression is a
momentum-conservation constraint.  The free-boson zero-mode rule knows that.

For arbitrary profiles, the residual factor should be explicit.  Schematically
the free-boson bulk zero-mode rule can emit only the zero-mode part
\[
  \int d^D x_0\,
  F_1(x_0) \cdots F_r(x_0)\,
  \exp\!\left(i x_0\cdot\sum_j k_j\right),
\]
or the projected Neumann/Dirichlet analogue.  If all profile labels are
Fourier-like, a later user-side simplifier may collapse this to a momentum
delta.  The generic correlator should not require that collapse.

For actual position-space correlators of arbitrary normal-ordered profiles,
the nonzero modes are represented by a residual Gaussian profile functional:
\[
  \int d^D x_0\,
  \left.
  \exp\!\left(
    \sum_{i<j} C_{ij}\,\partial_{x_i}\!\cdot\partial_{x_j}
  \right)
  F_1(x_1)\cdots F_r(x_r)
  \right|_{x_i=x_0}.
\]
Here \(C_{ij}\) is the surface-dependent nonzero-mode Green kernel with the
chosen normal-ordering convention.  Insertions of \(\partial X^\mu(z)\) act by
adding single-profile differential operators, schematically
\[
  \sum_i K_i(z)\,\partial_{x_i}^{\mu},
\]
plus the ordinary \(\partial X\partial X\) pairings among derivative fields.

This is the honest position-space fallback.  It is exact but usually not
"computed" to elementary functions by the generic kernel.  A client can later
evaluate it by choosing a presentation:

- Fourier presentation turns the Gaussian differential operator into the
  usual exponential momentum factors and momentum-conservation constraints;
- polynomial presentation truncates the differential operator to finitely many
  derivatives and is the natural Riemann-normal-coordinate/NLSM path;
- a special profile family may provide its own simplifier for the residual
  Gaussian factor.

There are three useful presentations for profiles, and the operator label
should allow any of them.  The presentation is chosen by the theory/client,
not by the generic correlator engine.

#+begin_src zig
const ProfilePresentation = union(enum) {
    position_space: ProfileRef,
    fourier_space: FourierProfileRef,
    polynomial: PolynomialProfileRef,
};

const FourierProfileRef = struct {
    momentum_variable: VectorExprRef,
    transform_factor: CustomScalarFactorFamilyId,
};

const PolynomialProfileRef = struct {
    expansion_point: TargetPointRef,
    terms: PolynomialProfileTermSpan,
};

const PolynomialProfileTerm = struct {
    coefficient: CustomScalarFactorFamilyId,
    powers: TargetIndexMultiSetRef,
};
#+end_src

The kernel still does not need to know Fourier analysis or Riemann normal
coordinates.  The free-boson or NLSM preset provides the rewrite stage:

- a Fourier-presented profile becomes an exponential body plus an opaque
  transform factor;
- a polynomial-presented profile becomes a finite normal-ordered product of
  \(X\)-fluctuation bodies with target-index coefficients;
- a position-space profile stays as a residual zero-mode integral.

After the rewrite, the usual Wick rules apply.  For Fourier profiles, the
zero-mode rule emits the ordinary momentum constraint.  A later stream filter
may use that constraint to eliminate one Fourier momentum and keep the
remaining inverse transform explicit.  For polynomial profiles, Wick
contractions pair \(X\)-fluctuations and leave target tensors/coefficient
derivatives in the output.

This keeps both representations available:

- position-space profiles give explicit zero-mode integrals;
- Fourier-space profiles reuse \(e^{ikX}\) Wick rules and leave inverse
  Fourier integrals as scalar factors;
- polynomial profiles support Riemann-normal-coordinate and NLSM perturbative
  expansions without introducing new correlator semantics;
- special profiles may provide their own simplifier without touching the
  correlator engine or coefficient module.

* Exact Preset Code Shape

The code below is the shape to implement.  The public functions live in the
presets layer and return generated theory types.  Users call these functions;
they do not construct [[id:20260605T090102.250727][Theory]] records directly.

The free-boson preset is parameterized only by physics data: dimension and
conventions.  It exports ergonomic operator builders and named configs.

#+begin_src zig
/// FreeBosonConfig declares a noncompact D-dimensional free boson preset.
pub const FreeBosonConfig = struct {
    dimension: u16,
    alpha_prime: ConventionScalar = .symbol("alpha_prime"),
    convention: FreeBosonConvention = .stringbook,
    explicit_x: bool = true,
};

/// freeBoson builds the bulk free-boson CFT preset.
pub fn freeBoson(comptime cfg: FreeBosonConfig) type {
    return cft.preset(.{
        .name = "free_boson",
        .sectors = &.{ x_sector(cfg) },
        .operators = free_boson_operators(cfg),
        .profiles = free_boson_profiles(cfg),
        .wick = &.{ free_boson_sphere_wick(cfg) },
        .zero_modes = &.{ free_boson_bulk_zero_modes(cfg) },
        .configs = &.{ free_boson_sphere_config(cfg) },
        .stress_tensor = free_boson_stress_tensor(cfg),
    });
}
#+end_src

The operator declarations are local and small.  =X= is included because
explicit \(X\)'s and position-space profile functionals produce logarithms.
=dX= and =dXt= carry derivative labels; =expX= carries momentum; =profileX=
has presentation data selected by the builder.

#+begin_src zig
fn free_boson_operators(comptime cfg: FreeBosonConfig) []const cft.OperatorDecl {
    _ = cfg;
    return &.{
        cft.bulkBoth("X", .{ .labels = &.{ .vector_index }, .weight = .fixed(.{ 0, 0 }) }),
        cft.bulkHolo("dX", .{ .labels = &.{ .vector_index, .derivative }, .weight = .rule(.dX_weight) }),
        cft.bulkAnti("dXt", .{ .labels = &.{ .vector_index, .derivative }, .weight = .rule(.dXt_weight) }),
        cft.bulkBoth("expX", .{ .labels = &.{ .momentum }, .weight = .rule(.expX_weight) }),
        cft.bulkBoth("profileX", .{ .labels = &.{ .profile_presentation }, .weight = .rule(.profile_weight) }),
    };
}
#+end_src

The generated user-facing builders should hide labels and body stores.  The
names follow the physics notation, with =dX(mu, n, z)= meaning
\(\partial^{n+1}X^\mu(z)\).

#+begin_src zig

#+end_src

The profile API exposes the three presentations.  Fourier and polynomial
presentations are rewrite choices; position-space is the exact residual
Gaussian profile functional.

#+begin_src zig
/// profile groups the generated profile presentation builders.
pub const profile = struct {
    /// positionSpace keeps the profile as a residual position-space functional.
    pub fn positionSpace(f: TargetFunction) Profile;
    /// fourier rewrites the profile through its Fourier transform.
    pub fn fourier(f_hat: FourierTransform) Profile;
    /// polynomialRnc rewrites the profile as a finite RNC polynomial.
    pub fn polynomialRnc(point: TargetPoint, terms: []const PolynomialProfileTerm) Profile;
};
#+end_src

The sphere \(bc\) preset is independent of the free boson.  The convention is
the chiral half compatible with the closed-string normalization in stringbook.

    include_antiholomorphic_copy: bool = true,

Product theories concatenate sectors, operator families, quantum-number lists,
and rule tables.  There is no tensor-product payload object at runtime.

#+begin_src zig
/// product builds a CFT from independent preset factors.

    return cft.productPreset(.{
        .factors = factors,
        .configs = product_configs(factors),
    });
}

const BosonicSphere = cft.presets.product(.{
    cft.presets.freeBoson(.{ .dimension = 26, .alpha_prime = .symbol("alpha_prime") }),
    cft.presets.bcSphere(.{}),

#+end_src

BCFTs are built compositionally.  The bulk CFT is specified without mentioning a
boundary.  Each boundary preset contributes a small extension: boundary-local
operators, mixed bulk-boundary Wick rules, boundary zero-mode rules, and optional
boundary stress tensor data.  The =boundary= builder merges these extensions
into one BCFT rule config.

#+begin_src zig
/// boundary builds a BCFT from a bulk CFT and independent boundary extensions.
pub fn boundary(comptime Bulk: type, comptime extensions: anytype) type {
    return cft.bcftPreset(.{
        .bulk = Bulk,
        .extensions = extensions,
        .configs = boundary_configs(Bulk, extensions),
    });
}
#+end_src

The free-boson boundary extension follows stringbook's boundary notation.
=dXBoundary(mu, n, y)= is \(\partial^{n+1}X^\mu(y)\), the holomorphic boundary
limit.  The real derivative \(\partial_yX\) is not a primitive operator: for
Neumann it is \(2\partial X\), while for Dirichlet it vanishes even though the
holomorphic boundary limit remains nontrivial.

#+begin_src zig
/// FreeBosonBoundaryConfig declares Neumann and Dirichlet data for a brane.

        .operators = free_boson_boundary_operators(cfg),
        .wick = &.{ free_boson_disk_wick(cfg) },

        .boundary_stress_tensor = free_boson_boundary_stress_tensor(cfg),

If a client later wants a Neumann real-boundary derivative, it can build

* Minimal API Shape

The public API should stay close to the physics.  It should not expose
=CoeffTerm=, custom factor labels, zero-mode evaluator ids, or operator-body
stores.  Those are generated internals.  A user defines or imports presets,
combines them, and then calls ergonomic operator builders.

#+begin_src zig
const FreeBoson = cft.presets.freeBoson(.{
    .dimension = 10,
    .alpha_prime = .one,
    .convention = .prototype,
});

const BosonicSphere = cft.presets.product(.{
    FreeBoson,
    cft.presets.bcSphere(.{}),
});

const BosonicDisk = cft.presets.boundary(BosonicSphere, .{
    cft.presets.freeBosonBoundary(.{
        .neumann = neumann_projector,
        .dirichlet = dirichlet_projector,
        .dirichlet_position = x0,
        .chan_paton = cp_stack,
    }),
    cft.presets.bcDiskBoundary(.{}),
});
#+end_src

The generated theory should expose ordinary body builders and the two runtime
operations:

#+begin_src zig
const O = BosonicSphere.op;

try BosonicSphere.correlator(
    BosonicSphere.config.sphere,
    .{ O.c(z1), O.c(z2), O.c(z3) },
    sink,
);

try BosonicSphere.correlator(
    BosonicSphere.config.sphere,
    .{ O.dX(mu, 0, z), O.expX(k, w, wbar) },
    sink,
);

try BosonicDisk.correlator(
    BosonicDisk.config.disk,
    .{ BosonicDisk.op.expXBoundary(k, x), BosonicDisk.op.cBoundary(0, y) },
    sink,
);
#+end_src

This is schematic.  The important boundary is that =correlator= receives
operators plus a rule config, not a surface object, boundary-condition object,
or gluing rule.

For profiles, the user should choose a presentation at the builder level:

#+begin_src zig
const Fpos = FreeBoson.profile.positionSpace(F);
const Ffourier = FreeBoson.profile.fourier(Fhat);
const Frnc = FreeBoson.profile.polynomialRnc(expansion_point, terms);

try BosonicSphere.correlator(
    BosonicSphere.config.sphere,
    .{ O.profile(Ffourier, z, zbar), O.dX(mu, 0, w) },
    sink,
);
#+end_src

This is the desired ergonomics: the user works with \(F(X)\), \(\hat F(k)\),
or a polynomial expansion.  The preset handles the rewrite, factor families,
zero-mode residuals, and stream simplifiers.

* Signed Decisions

The current implementation target has the following sign-offs.

1. The first free-boson preset uses the prototype/stringbook normalization
   \(\langle X X\rangle=-\alpha'\log|z-w|\), equivalently
   \(dX dX\sim-\alpha'/2\,(z-w)^{-2}\), with runtime-selectable
   \(\alpha'\).
2. [[id:20260604T083119.372970][Coefficient]] should extend =RationalFunction= tightly: built-in
   coordinate powers and coordinate logs, named Green kernels by reference,
   and custom scalar factors for user/theory physics.
3. There is one =profileX= operator family, with position-space,
   Fourier-space, and polynomial/RNC presentations selected by the builder.
4. The \(bc\) sphere convention follows stringbook: the full closed-string
   normalization is
   \(\langle \prod_{i=1}^3 c(z_i)\tilde c(\bar z_i)\rangle
    = |z_{12}z_{13}z_{23}|^2\), equivalently the BPZ inner product
   \(\langle\langle\downarrow,\downarrow|c_0\tilde c_0|\downarrow,\downarrow\rangle=1\).
   The chiral preset uses the compatible holomorphic convention
   \(\langle c(z_1)c(z_2)c(z_3)\rangle=z_{12}z_{13}z_{23}\).
5. Boundary free-boson operators follow stringbook: the primitive is
   =dXBoundary(mu,n,y)= for the holomorphic boundary limit
   \(\partial^{n+1}X^\mu(y)\).  We do not expose \(\partial_yX\) or =dyX= in the
   first-pass operator API.
6. BCFT data is compositional: the bulk theory stays boundary-free, and
   independent boundary extensions are merged by =cft.presets.boundary=.
7. The first BCFT pass includes mixed bulk-boundary ghost insertions, not only
   boundary \(bc\) insertions.

My recommended implementation order is:

1. [[id:20260604T083119.372970][Coefficient]] scalar factors: coordinate powers, coordinate logs, named
   kernels, and custom factor-family hooks;
2. tensor-code \(SO(D)\) vector invariant handles and dimension contraction;
3. free-boson bulk operator families, labels, weights, and sphere Wick rules;
4. profile presentations, Fourier rewrites, and polynomial/RNC rewrites;
5. sphere \(bc\) top-form zero-mode rule and \(b c\) Wick rule;
6. free-boson Neumann/Dirichlet BCFT compilation;
7. boundary and mixed bulk-boundary \(bc\) disk config.

* Review Against AGENTS

This proposal is ready to implement because the data flow is narrow:

- =correlator= receives only local operators, a compiled rule config, and a
  sink;
- Wick rules and zero-mode rules stream coefficient factors instead of
  materializing expanded expressions;
- the only new coefficient-code surface is the small scalar-factor product;
- boundary data is compiled before runtime and can be stacked by composition;
- Chan-Paton factors are labels that may point to tensor-code structures, not an
  independent tensor system;
- the public preset API is limited to =freeBoson=, =bcSphere=, =product=,
  =boundary=, =freeBosonBoundary=, and =bcDiskBoundary=, plus generated operator
  builders.

The design also extends to the later modules without overfitting:

- on-shell RNS adds \(\psi,\phi,\eta,\xi\), spin fields, GSO, and Narain-lattice
  cocycles as additional sectors and Wick/zero-mode rule families;
- [[id:20260606T064107.303587][Wick]] still owns pair evaluation and signs, including cocycle signs;
- [[id:20260605T075909.433647][Tensor-Code]] owns \(SO(D)\), \(SO(10)\), \(SO(32)\), \(E_8\times E_8\),
  and Chan-Paton tensor structures;
- [[id:20260603T094138.285453][Correlators]] remains a generic streamed evaluator, so SFT, amplitudes,
  projections, BRST, and picture-changing stay client-side;
- NLSM calculations use polynomial profile presentations and named kernels
  without changing operator storage;
- pure-spinor and curved-background calculations can add custom zero-mode
  measures, constraints, and simplifiers as client factor families.

The only implementation caveat is discipline: preset-author internals such as
operator declarations, evaluator ids, zero-mode rule data, and custom
factor-family ids should stay private unless another module demonstrably needs
them.
