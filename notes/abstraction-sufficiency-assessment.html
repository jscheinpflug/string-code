1. Scope

This note assesses whether the abstractions currently defined in org/, mainly cft-code and tensor-code, are sufficient for:

  • superstring perturbation theory,
  • bosonic and super string field theory,
  • string theory on weakly curved backgrounds, i.e. perturbative quantization of nonlinear sigma models.

I read the relevant project notes in org/, the tangled Zig source in src/, and the local stringbook source at stringbook/texsource/string notes.tex.

After the first pass, I also read prototype-string-code/ to calibrate the target more precisely. The prototype should be treated as evidence for the workflows we need to support, not as the abstraction model to copy. The target is not a full formal implementation of supermoduli geometry, BV geometry, or general string perturbation theory as mathematical objects. The target is a performant, extensible symbolic-algebra kernel, centered on tensor-code and cft-code, that can later support ghost-number, picture, bracket, amplitude, and SFT-specific logic as client layers.

2. Bottom Line

The current abstractions are not yet sufficient for the intended performant kernel, but the missing pieces are more concrete and narrower than a full theory-geometry stack.

There is a reasonable seed for a symbolic worldsheet CFT kernel: local operators, normal-ordered operator bodies, rational coordinate coefficients, a sectorized theory object, and a tensor-structure slot in coefficients. The design notes also identify several right extension points: streaming Wick/OPE evaluation, generated theory-specific Wick rules, picture number, richer tensor expressions, PCO contours, and local-coordinate data.

However, the implemented abstractions are still too skeletal for the actual computational workflows suggested by prototype-string-code/. They do not yet model a sufficiently generic field/operator registry, a lean normal-product representation, generic quantum-number bookkeeping, a contraction/OPE mechanism that can return residual operators, projected OPE/Taylor expansion, or the tensor-structure solver needed for Type II spin-field calculations.

For the intended package, we do not need to encode every global construction from the book as first-class data. We do need enough hooks to let a concrete bracket or amplitude prescription provide local coordinate maps, finite PCO zero-mode actions, projection targets, and surface-dependent zero-mode rules.

3. Prototype-Calibrated Target

The prototype’s README.md describes a Mathematica package for algebraic worldsheet calculations: normal-ordered products, Wick contractions, OPEs, brackets, BRST action, Type IIB superstring support, flat-space/minimal-model backgrounds, and CFT-specific field data.

The detailed ALGORITHMS.md makes the target architecture especially clear:

  • A metadata-driven field registry via DefineField stores statistics, simple/composite status, holomorphicity, index status, collapsability, factorizability, pairings, ghost number, weights, picture, and GSO parity.
  • R[...] is a normal-ordered product with graded canonicalization, scalar stripping, multilinearity, nilpotency of regular fermions, and Type II bosonized-exponential merge rules.
  • Wick is split into Wick, SWick, and MWick, with DWick providing shared recursion over normal-ordered products.
  • OPE has a two-layer structure: it handles multilinearity and collapsable/non-collapsable splitting, while OPEWick performs free-field recursion on the collapsable sector.
  • OPEProjected rescales insertion positions, reads off powers, and Taylor-expands to a target conformal weight.
  • TaylorAtOrder rewrites fields around a target point, including field-specific rules for exponentials, profiles, superghost exponentials, and spin fields.
  • Bracket uses supplied local-coordinate maps, conformal placement, curly-\(B\) construction, b-ghost mode action, projected OPE, and Type II PCO zero-mode actions.
  • Type II spin-field projected OPE uses a basis-generation and tensor-structure solving pipeline rather than pure Wick recursion.

The new Zig/literate design should therefore aim to express these workflows in a type-driven, streamable, extensible way. It should not mechanically reproduce the prototype’s public heads or its split into Wick, SWick, and MWick. A cleaner kernel can use a single contraction operation whose result is a symbolic expression, possibly containing residual operators. Likewise, the normal-ordered product should be a lean canonical product representation, not a heavy recursive tree copied from Mathematica syntax. That is a different bar from representing the full supermoduli or BV geometry.

4. Kernel Design Stance

The kernel boundary should be tensor-code plus cft-code.

4.1. Tensor-Code

Tensor-Code should know about abstract symmetry data, representations, indices, invariant tensors, tensor expressions, canonicalization, and evaluation/probing of tensor structures. It should not know about string amplitudes, brackets, or picture-changing.

For Type II flat-space work, the first serious target is still concrete: spinor/vector tensor structures built from deltas, charge-conjugation matrices, antisymmetrized gamma products, epsilon-like structures when needed, and linear independence selection. The abstractions should be general enough that this is an instance of invariant-tensor generation and manipulation, not a hardcoded “Type II spin projection” subsystem.

4.2. CFT-Code

CFT-Code should know about local fields/operators, local products, insertion positions, derivatives, conformal weights, generic quantum numbers, OPE/contraction rules, Taylor/projection logic, and correlator/OPE algorithms.

It should not know that a certain \(U(1)\) charge is “ghost number” or “picture number”. Those are just named/additive quantum numbers to the CFT layer. Later string-specific layers may impose interpretations such as ghost-number anomaly, picture balance, GSO projection, or physical-state constraints.

The CFT kernel should therefore support:

  • named/additive quantum numbers with selection-rule hooks;
  • operator families with generic metadata, not string-specific flags;
  • generic contraction/OPE rules that may return scalar coefficients, residual operators, or sums of both;
  • lean local-product canonicalization with statistics/sign rules supplied by the CFT;
  • basis generation by weight and quantum numbers;
  • projection to target weights by local Taylor expansion;
  • streaming emission of terms rather than owned expression-tree blowup.

4.3. Client Layers

Ghost-number constraints, picture-changing, string brackets, amplitude prescriptions, boundary/orientifold logic, and SFT propagators should be clients of the kernel. They can request CFT operations, inspect generic quantum numbers by name, and supply extra rule tables, but they should not force the CFT core to bake in their physical semantics.

5. Spectrum Projections And Boundary Conditions

The current CFT specs are also not yet sufficient for two concrete operations we should expect early:

  • take an already-defined operator/state spectrum and project it by a finite symmetry, such as an orbifold, GSO-like parity, or orientifold action;
  • compute correlators with a boundary once boundary-condition data has been supplied.

Both can be added with small, generic abstractions. They do not require CFT-Code to know what an orientifold, D-brane, ghost number, or picture number means.

5.1. Missing From The Current Specs

The existing specs talk about operator families, quantum numbers, Wick rules, and projected OPEs. That is the right core, but the following data is missing:

  1. A first-class operator spectrum view. Basis generation should produce a list or stream of candidate local bodies/states with weight, named quantum numbers, tensor labels, sector labels, and descendant data. A projection cannot be applied cleanly if the spectrum is only implicit inside ad hoc generator code.
  2. Linear actions on operators and states. A projection needs an action \(g\cdot O_i=\sum_j M_{ji}(g)O_j\), not just predicates on metadata. The action must be able to map sectors, operator families, extras, tensor indices, quantum numbers, and possibly chirality/left-right factors.
  3. Projector construction. Given a finite action, the kernel should build \[ P_\chi O = {|G|}^{-1}\sum_{g\in G}\chi(g)^{-1} g\cdot O \] and reduce the result in the generated basis. For a simple even/odd projection this is just \((1\pm g)/2\). For a full orbifold, twisted sectors and twist fields are extra spectrum data; the projection machinery itself only needs a group action on whatever spectrum has been supplied.
  4. Orientation-reversing actions. Orientifolds are not just internal symmetry projections: they can exchange holomorphic and antiholomorphic sectors and act on insertion coordinates. The minimal abstraction is still generic: an action may be orientation-preserving or orientation-reversing, and may map an insertion/body to a linear combination of insertions/bodies.
  5. Boundary condition data as gluing data. Boundary correlators require a gluing map from antiholomorphic fields to holomorphic image fields, plus zero-mode rules. This is not present in the current CFT spec.
  6. Boundary-local insertions. A boundary operator is not the same runtime insertion shape as a bulk \((z,\bar z)\) operator. The runtime layer needs a boundary insertion position, a boundary-condition label or brane-pair label, and a body expressed in boundary generators or in doubled chiral fields.
  7. Surface context for correlators. A correlator on the plane is not the same operation as a correlator on the upper half-plane/disk. The correlator call needs a small context containing the surface kind, boundary condition labels, zero-mode prescription, and image/doubling map.

5.2. Minimal Generic Design

The smallest design that seems enough is the following. 

pub const SpectrumTerm = struct {
    body: OperatorBodyId,
    weight: ConformalWeights,
    quantum_numbers: QuantumVector,
    sector: SectorId,
    coeff: Coeff,
};

pub const SymmetryActionSpec = struct {
    name: []const u8,
    orientation: enum { preserving, reversing },
    order: u16,
    action_on_body: BodyActionFn,
    action_on_insertion: InsertionActionFn,
    action_on_extra: ExtraActionFn,
};

pub const ProjectionSpec = struct {
    action: SymmetryActionId,
    character: CharacterFn,
};

pub const BoundaryConditionSpec = struct {
    name: []const u8,
    gluing: []const GluingRule,
    zero_modes: ZeroModeRuleSet,
    boundary_families: []const BoundaryOperatorFamilySpec,
};

pub const GluingRule = struct {
    anti_family: OperatorFamilyId,
    image_expr: GluingImageTemplate,
};

The actual functions should be generated at comptime from declarative specs. Runtime code should only call fixed operations such as: 

Theory.projectSpectrum(projection, spectrum, sink);
Theory.doubleBulkInsertion(boundary_condition, bulk_op, sink);
Theory.boundaryCorrelator(context, insertions, sink);

The critical rule is that the DSL supplies data for known algorithms. It should not generate new runtime algorithms. Projection is linear algebra over a generated basis; boundary correlators use gluing/doubling plus the ordinary chiral correlator engine.

5.3. Free Boson D-Brane Check

For a flat free boson CFT with \[ X^\mu(z,\bar z)=X_L^\mu(z)+X_R^\mu(\bar z), \] a D\(p\)-brane is specified locally by a reflection matrix \[ R^μν =

\begin{cases} +\delta^\mu{}_\nu & \mu,\nu \text{ tangent to the brane},\\ -\delta^\mu{}_\nu & \mu,\nu \text{ normal to the brane}. \end{cases}

\]

The boundary condition data is just the gluing rule \[ \bar\partial X^\mu(\bar z) \mapsto R^\mu{}_\nu \partial X^\nu(\bar z). \]

Then boundaryCorrelator on the upper half-plane reduces every antiholomorphic insertion to a holomorphic image insertion and calls the ordinary chiral free-boson Wick engine. For example:

\[ \langle \partial X^\mu(z)\bar\partial X^\nu(\bar w)\rangle_B = -{\alpha'\over 2} {R^\nu{}_\rho\eta^{\mu\rho}\over (z-\bar w)^2}. \]

Neumann and Dirichlet zero modes are not CFT metadata; they belong to the boundary condition:

  • Neumann directions integrate zero modes and impose momentum conservation along the brane.
  • Dirichlet directions fix the zero mode to the brane position and produce position-dependent phases for momentum-carrying bulk operators.

Boundary open-string operators on a single brane are represented as boundary-local products of the doubled chiral fields at \(x\in\mathbb R\), with Chan-Paton labels as optional external labels. Boundary-changing operators between different branes are not derivable from the gluing map alone; their spectrum and bulk-boundary OPE constants must be supplied as additional boundary CFT data.

5.4. Free Fermion And Beta-Gamma D-Brane Check

For the NSR matter fermions, the D-brane supplies the same reflection matrix together with a spin-structure/sign label \(\eta_B=\pm1\):

\[ \tilde\psi^\mu(\bar z) \mapsto \eta_B R^\mu{}_\nu \psi^\nu(\bar z). \]

The ordinary holomorphic free-fermion rule \[ \psi^\mu(z)\psi^\nu(w)\sim {\eta^{\mu\nu}\over z-w} \] then immediately gives the mixed boundary contraction \[ \langle \psi^\mu(z)\tilde\psi^\nu(\bar w)\rangle_B = {\eta_B R^\nu{}_\rho\eta^{\mu\rho}\over z-\bar w}. \]

For the \(\beta\gamma\) system, the boundary condition is another gluing automorphism:

\[ \tilde\beta(\bar z)\mapsto \lambda_\beta\beta(\bar z), \qquad \tilde\gamma(\bar z)\mapsto \lambda_\gamma\gamma(\bar z), \qquad \lambda_\beta\lambda_\gamma=1. \]

In bosonized variables this is equivalently a rule for \(\tilde\phi,\tilde\eta,\tilde\xi\) that preserves the OPEs and the chosen PCO/BRST convention. The CFT kernel does not need to know why these fields are superghosts. It only checks that the gluing map preserves the declared OPEs, weights, and any named quantum numbers the client asks it to preserve.

With these rules, mixed bulk-boundary correlators involving \(e^{q\phi}\), \(\eta\), \(\xi\), \(\beta\), \(\gamma\), and matter fermions are computed by the same doubled chiral correlator/OPE engine used for bulk free-field calculations. String-specific layers can later decide which picture, GSO parity, or BRST constraints are physically allowed.

5.5. Consequence

This reinforces the earlier conclusion: the CFT kernel should expose generic spectra, linear actions, projectors, gluing maps, boundary insertions, zero-mode prescriptions, and surface correlator contexts. Orbifold/orientifold and D-brane physics can then be implemented as data and client-side interpretation. Without these additions, the current specs cannot project a spectrum or derive boundary correlators in a controlled way.

6. Book-Derived Requirements

This section records what the book says the physical calculations come from. For the package design, these should be read as sources of local symbolic requirements, not as a claim that every global object must be implemented as a complete formal abstraction.

6.1. On-shell bosonic string amplitudes

The stringbook formulates genus-\(h\), \(n\)-point amplitudes as CFT correlators integrated over \({\cal M}_{h,n}\), with \(b\)-ghost insertions tied to moduli and \(c\)-ghost insertions at punctures. Vertex operators must be regularized primaries of weight \((1,1)\), and the correlator is a top-degree form on moduli space (string notes.tex lines 1637–1650).

This requires abstractions for:

  • Concrete local-coordinate maps and their derivatives with respect to finite moduli used in a chosen bracket/amplitude prescription.
  • \(b\)-ghost measure insertions as symbolic mode actions or finite contour-mode expansions.
  • BRST-closed vertex operators and physical-state constraints.
  • Regularized local operators and surface-dependent zero-mode selection rules.
  • Optional degeneration/factorization metadata only insofar as it drives effective brackets and propagator/projector insertions.

6.2. Superstring perturbation theory

The superstring path integral introduces even moduli, odd supermoduli, spin structures, superghosts, analytic delta insertions \(\delta({\cal B}_\nu)\), and matter+ghost supercurrent insertions (string notes.tex lines 3767–3803). The book then replaces odd-moduli integration by PCO insertions, with a BRST-regularized PCO \({\cal X}(z)\), PCO positions forming a bundle over moduli space, and an integrand containing \({\cal X}-d\xi\) (string notes.tex lines 4225–4264).

It also emphasizes spurious singularities and the need for patchwise/vertical integration: the determinant \(\det(f_a(z_b))\) can vanish, and no global section generally avoids this; one must break the integration contour into patches and interpolate (string notes.tex lines 4338–4385).

This requires abstractions for:

  • NS/R sectors, spin structures, GSO projections, and fermion parity signs.
  • Picture number, small/large Hilbert spaces, \(\beta\gamma\) or \((\phi,\eta,\xi)\) superghost systems.
  • PCOs as concrete algebraic operators and zero-mode actions, especially residue extraction by OPE plus Taylor expansion.
  • Enough PCO bookkeeping to know how many PCOs to apply and in which chiral sector; full vertical integration can be supplied externally unless doing global amplitude integration.
  • Ramond spin fields, spinor cocycles, and excited spin-field OPE/correlator machinery.

6.3. String field theory

For bosonic closed SFT, the book defines the string field space by \(b_0^-\Psi=L_0^-\Psi=0\), notes that this space is not closed under the ordinary OPE, and replaces OPE closure with string-field brackets (string notes.tex lines 2383–2393). Off-shell amplitudes live on a bundle \({\cal P}_{h,n}\) whose fiber contains local coordinate maps at punctures, and the amplitude is an integral over chains \(S_{h,n}\) satisfying symmetry and boundary compatibility conditions (string notes.tex lines 2393–2440). Factorization requires plumbing compatibility and gives Siegel-gauge propagators \(b_0^+b_0^-/L_0^+\) (string notes.tex lines 2464–2494).

For super SFT, the book adds GSO-projected NS/R string-field spaces, auxiliary Ramond picture \(-3/2\) fields, a bundle \({\cal Q}_{h,n}\) with spin structures and PCO locations, chains whose boundaries are vertical slits, Ramond-plumbing PCO insertions, picture-adjusted propagators, and a BV master equation (string notes.tex lines 5510–5688).

This requires abstractions for:

  • Local operators or basis states carrying enough grading/weight data to act as string-field components.
  • BRST charge, BPZ pairing, \(b_0^\pm,c_0^\pm,L_0^\pm\), Siegel gauge, and propagators.
  • Local-coordinate maps \(f_i(w_i)\), finite moduli symbols, b-mode expansions, and conformal placement.
  • String products/brackets as concrete algorithms over MultiOp, projected OPE, projectors, and propagators.
  • Super SFT-specific picture-adjusted propagator/projector operations where needed by effective bracket calculations.

6.4. Weakly curved backgrounds / NLSM quantization

The book treats strings in backgrounds through a generalized Polyakov action with \(G_{\mu\nu}(X)\), \(B_{\mu\nu}(X)\), \(T(X)\), and \(\Phi(X)R(g)\), preserving perturbative renormalizability with up to two-derivative couplings (string notes.tex lines 1331–1339). Quantization uses background-field expansion in Riemann normal coordinates, covariant fluctuation fields \(\xi^\mu\), curvature expansions of \(G_{\mu\nu}(X)\), \(H=dB\), functional determinants, dimensional regularization, beta functions, and Weyl-anomaly cancellation equations (string notes.tex lines 1341–1414).

This requires abstractions for:

  • Target manifolds, metrics, connections, curvature tensors, \(B\)-fields, \(H\)-flux, dilaton profiles, and tachyon/background potentials.
  • Background-field splitting \(X=X_0+\xi+\cdots\) in Riemann normal coordinates.
  • Covariant worldsheet actions and regularization schemes.
  • Counterterms, renormalized couplings, beta functions, Weyl-anomaly conditions, and field-redefinition/scheme dependence.
  • Composite operators defined inside a regulated path integral, not only free-field normal-ordered products.

7. Current Project Abstractions

7.1. CFT-Code

The current project overview says CFT-Code is intended to handle local operators, OPEs, and correlators on various Riemann surfaces (org/overview.org lines 7–13). Its specific physical goal is covariant R-sector OPE/correlators for GSO-projected free fermion plus ghost theories, at all mass levels and practical speed (org/overview.org lines 16–17).

The implemented Zig source currently provides:

  • Operator = insertion + body, where bodies may be identity, atomic, or normal_ordered (src/cft-code/expressions/operators.zig lines 5–19).
  • Atomic operator bodies with a kind id and extra-data handle (operators.zig lines 21–30).
  • Operator-kind metadata for holomorphicity, conformal weights, quantum numbers, and correlator tactics (operators.zig lines 32–65).
  • Insertions with a single position or holomorphic/anti-holomorphic pair and derivative counts (operators.zig lines 67–79).
  • Expressions as sums of coefficient times one operator (src/cft-code/expressions/expressions.zig).
  • Theory as a list of sectors, each with operator kinds and one correlator tactic (src/cft-code/theory/theory.zig lines 3–12).

The org notes define intended correlator tactics: abstract selection-rule filtering, Wick contraction with surface-dependent propagators and zero modes, and bosonization by tensor-structure matching (org/cft-code/correlators/correlators.org lines 8–13). The OPE note proposes deriving OPEs from a basis, a nondegenerate pairing/BPZ-like pairing, and correlators (org/cft-code/ope/ope.org lines 8–10).

Assessment:

  • The operator-body split is a good abstraction for free-field composite local operators such as \(e^{-\phi}\psi^\mu\), \(:bc:\), and \(:\partial X^\mu\partial X^\nu:\).
  • It is not yet enough for the required workflows because there is no generic operator-family registry equivalent in power to DefineField: statistics/sign behavior, holomorphicity, index payload shape, rule-participation tags, pairings/contractions, weights, generic charges, and discrete labels.
  • More importantly, the future registry should be more generic than the prototype: ghost number, picture, and GSO-like data should be encoded as generic named quantum numbers or discrete labels, not privileged CFT concepts.
  • The present Expr type carries a single operators.Operator per term, so it does not yet represent R[...] as a list-valued normal-ordered local product, nor MultiOp[...] as a multi-local product. Both are central in the prototype.
  • The code has no abstraction for a concrete algebraic rule table. This need not copy Wick/SWick/MWick; a single contraction/OPE rule interface that returns a symbolic expression with scalar and operator pieces is likely cleaner.
  • The source has unresolved type/import issues: CorrelatorTactics is used but only CorrelatorTactic is defined, TensorIndexId is used but not defined, and several imports omit the visible file layout. So the current implementation is not yet an executable abstraction layer.

7.2. Tensor-Code

The project goal for Tensor-Code is ambitious: quickly generate independent invariant tensors in tensor products of representations, because R-sector amplitudes may require extremely large invariant-tensor spaces (org/overview.org lines 18–22 and 31–34).

The implemented source currently provides:

  • Symmetries as \(u(1)\) or simple Lie algebras with Dynkin-family labels (src/tensor-code/tensor-code.zig lines 1–26).
  • Representation ids and representation labels as rational \(u(1)\) charge or Dynkin labels (tensor-code.zig lines 28–46).
  • Tensor indices and a TensorStructure that is only none or one Kronecker delta (tensor-code.zig lines 48–59).

Assessment:

  • This is not sufficient for the tensor algebra needed in superstring amplitudes or weakly curved backgrounds.
  • Against the prototype, the immediate missing pieces are products of tensor factors, delta contractions, gamma antisymmetric products, spinor/vector index domains, chirality, exact gamma-matrix evaluation, tensor candidate enumeration, independent-subset selection, sparse/dense probe evaluation, and symbolic coefficient solving.
  • More general invariant tensors and representation theory are still important, but the first target should cover the Type II flat-space tensor-structure pipeline currently under OPE/TypeII/FlatSpace/TensorStructures and SpinProjection.
  • The design notes correctly say tensor structure should become its own symbolic language and not be hardcoded to Kronecker deltas, but the implemented TensorStructure has not reached that design.

7.3. SFT-Code, NLSM-Code, On-Shell-Code, Pure-Spinor-Code

The module notes are currently mostly high-level declarations:

  • SFT-Code claims it will define brackets and vertices using local-coordinate data, OPE/correlators, abstract moduli chains, and PCO insertions (org/sft-code/sft-code.org line 6).
  • NLSM-Code is only an overview stub (org/nlsm-code/nlsm-code.org line 6).
  • On-Shell-Code claims support for all five superstrings, open/closed/open-closed sectors, ghost-system theories, boundary conditions, and GSO projections (org/on-shell-code/on-shell-code.org line 6).
  • Pure-Spinor-Code claims a regularized pure-spinor NLSM on \(PSU(2,2|4)\) (org/pure-spinor-code/pure-spinor-code.org line 6).

These are requirements statements, not implemented abstractions. They do not currently close the sufficiency gaps.

8. Sufficiency By Target

8.1. Superstring perturbation theory

Current status: insufficient.

The current CFT abstraction can begin to represent local free-field ingredients, but it lacks the structures that make superstring perturbation theory well-defined:

  • NS/R sector typing and spin structures.
  • GSO projections and fermion parity signs.
  • Picture number and \(\beta\gamma\)/\((\phi,\eta,\xi)\) Hilbert-space distinctions.
  • PCOs and vertical-integration chains.
  • Spurious singularity detection/avoidance.
  • Worldsheet supermoduli or their PCO-contour replacement.
  • Spin fields, cocycles, and gamma-matrix/tensor identities.

For the concrete symbolic package, the actionable subset is smaller:

  • generic charge/parity/sector metadata on fields and products, with string layers interpreting some charges as picture or ghost number;
  • explicit PCO operators and zero-mode actions implemented as ordinary CFT operations plus residue/Taylor extraction;
  • spin-field OPE projection through basis generation and tensor solving;
  • gamma/tensor algebra sufficient for 10D Type II flat-space spinor-vector structures.

The correlator tactic sketch is directionally right, especially the bosonization tactic for R-sector spin-field correlators. But without a tensor engine capable of spinor invariants and without explicit picture/PCO bookkeeping, it cannot yet reproduce the prototype’s Type II workflows.

8.2. String field theory

Current status: insufficient.

SFT-Code correctly identifies local coordinates, moduli chains, brackets, vertices, and PCO insertions as necessary. The current CFT/OPE abstractions are only a dependency for SFT; they are not a substitute for SFT-specific geometry and algebra.

Missing core abstractions include:

  • constrained string-field state spaces \({\cal H}_0\), auxiliary Ramond spaces, and ghost/picture grading;
  • BRST and BPZ operations;
  • local-coordinate-map objects and their conformal action on operators/states;
  • moduli-space chains, plumbing fixtures, and compatibility/geometric master equations;
  • string brackets/products and \(L_\infty/A_\infty\) identities;
  • BV symplectic form, field/antifield splitting, propagators, and gauge fixing.

For the prototype-calibrated package, the first SFT layer should be much more concrete:

  • Bracket over local R or MultiOp inputs;
  • local-coordinate data supplied by a bracket preset;
  • conformal placement using field weights;
  • finite curly-\(B\) construction and b-mode action;
  • projection by local OPE/Taylor;
  • held/projector/propagator operations for effective brackets.

The existing local operator model is useful for CFT insertions inside SFT vertices, but it needs MultiOp, local-coordinate placement, b-mode action, projected OPE, and PCO-zero-mode hooks before it can replace the prototype.

8.3. Weakly curved backgrounds / NLSM quantization

Current status: insufficient.

The current abstractions are free-CFT-oriented. The book’s weak-background calculation is instead a covariant perturbative path integral with a chosen regulator, target-space geometry, background-field expansion, counterterms, and beta functions.

Missing core abstractions include:

  • target manifolds, coordinate charts, metric/connection/curvature, \(B\)-field and \(H=dB\), dilaton and tachyon profiles;
  • Riemann-normal-coordinate background-field expansion;
  • covariant worldsheet actions and fluctuation operators;
  • dimensional regularization or point-splitting schemes;
  • counterterm and beta-function machinery;
  • scheme-dependent field redefinitions;
  • composite operators as regulated path-integral insertions.

Tensor-Code will be needed here, but the current representation-theory focus is not enough. NLSM quantization needs differential geometry and perturbative QFT abstractions, not just invariant tensors.

For a concrete symbolic package, NLSM support can begin with a narrower feature set: ProfileX style composite operators, symbolic target-index derivatives, covariant/tensor-valued coefficient payloads, background-field vertices, and rule-driven Wick contractions around a chosen weak-background expansion.

9. What Is Promising

  • The Operator = insertion + body_id direction is a good base for local CFT expressions and normal-ordered free-field composites.
  • Separating coefficient rational functions from tensor structures is the right coefficient architecture.
  • The project already recognizes that large Wick/OPE calculations must stream results rather than materialize all intermediate expressions.
  • The design notes correctly identify that richer tensor expressions, generated theory-specific Wick rules, and external aggregation are needed.
  • The CFT module has a plausible role as the shared kernel for on-shell amplitudes and SFT vertices, provided it exposes generic operator, charge, OPE, projection, and tensor hooks that later string-specific layers can interpret.

10. Highest-Priority Kernel Abstractions

  1. Make the current source coherent and executable. Define missing ids/types, fix imports, expose the intended modules, and add a minimal test theory such as \(bc + X^\mu + \psi^\mu + \beta\gamma\).
  2. Implement a generic operator-family registry. This should drive predicates and rule dispatch for statistics/sign behavior, holomorphicity, index payload shape, weight rules, generic quantum numbers, and rule participation. It should avoid baking in string-specific meanings like “ghost number” or “picture”.
  3. Make lean local products first-class. A local product should be compact, canonicalizable, and stream-friendly. It must support ordered factors, sign/canonicalization rules, scalar separation, additive quantum-number queries, and theory-supplied merge/nilpotency hooks. It should not be a direct Mathematica-style tree.
  4. Use a single generic contraction/OPE rule interface. Do not require separate Wick, SWick, and MWick concepts in the core. A contraction between two operator factors or products should be able to return zero, a scalar coefficient, a residual operator/product, or a sum of such terms. The algorithm can then recurse uniformly.
  5. Implement projected OPE as a core operation. This includes collapsable/non-collapsable splitting, factorization of mixed-chirality fields, scaling-parameter projection, Taylor expansion to target weights, and memoized/streamed OPE recursion.
  6. Add spectrum and linear-projection support. Basis generation should expose a spectrum stream/list with weights, sectors, named quantum numbers, tensor labels, and bodies. Projection should be a generic finite linear action on this spectrum, capable of preserving or reversing orientation, exchanging chiral sectors, acting on tensor extras, and reducing the projected result in a generated basis. Orbifold, orientifold, GSO-like, and parity projections should all be client data over this mechanism.
  7. Add boundary-condition and boundary-correlator hooks. A boundary condition should be a gluing automorphism plus zero-mode prescription and optional boundary-operator spectrum. For free theories this is enough to implement the doubling trick: rewrite antiholomorphic fields as holomorphic image fields and call the ordinary chiral Wick/OPE/correlator engine. Boundary-changing sectors and bulk-boundary OPE constants must be supplied as extra boundary CFT data when needed.
  8. Upgrade Tensor-Code to support the Type II spin-projection workflow. Add tensor-expression products, delta factors, invariant factors, gamma antisymmetric products as one concrete invariant family, spinor chirality, vector/spinor domains, exact/sparse evaluation, candidate enumeration, independent-subset selection, and coefficient solving.
  9. Expose extension hooks for later string-specific logic. Brackets, amplitudes, PCOs, propagators, and ghost/picture constraints should be built outside the CFT kernel but must be able to call kernel operations, inspect named quantum numbers, and define additional operator families/rules.
  10. Add a minimal weak-background/NLSM symbolic layer. Start with ProfileX-like operators, target derivative symbols, covariant tensor coefficients, background-field expansion vertices, and scheme-labeled counterterm/beta-function outputs. Full geometric automation can come later.

11. Conclusion

The existing abstractions are a useful start for a future worldsheet CFT kernel, but they are not sufficient for the intended performant symbolic-algebra package. The gap is not mainly a matter of adding more operator kinds, and the answer is not to copy the prototype’s exact Mathematica heads. The missing pieces are more abstract kernel capabilities: generic operator-family metadata, named quantum numbers, lean canonical local products, a uniform contraction/OPE rule interface that can return residual operators, projected OPE/Taylor, streamable spectrum generation, finite linear projections, boundary gluing/doubling data, streaming term emission, and a substantially stronger tensor algebra engine.

The most pragmatic next milestone is not full SFT or NLSM support. It is a compiling tensor-code and cft-code kernel that can express \(bc+X+\psi+\phi\eta\xi\) as ordinary CFT data, compute nontrivial OPEs with residual operators through one generic contraction mechanism, project to target weights by Taylor expansion, project a small generated spectrum under a finite action, derive upper-half-plane correlators from a supplied D-brane gluing map, and generate/solve a small Type II spinor-vector tensor-structure problem. That milestone would test the abstractions that matter most while keeping ghost number, picture, brackets, amplitudes, and SFT logic as later client layers.
