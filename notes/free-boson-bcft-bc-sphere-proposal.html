1. Goal

This is a drawing-board proposal for the first concrete CFT presets to build on top of Theory, Operators, Correlators, Wick, and Tensor-Code.

The target is deliberately small but physically diagnostic:

  • a \(D\)-dimensional free boson \(X^\mu\), including arbitrary \(X\)-profiles as in prototype-string-code/;
  • the holomorphic \(bc\) ghost system on the sphere;
  • the basic BCFT extensions needed for a free boson with Neumann/Dirichlet directions, plus the standard boundary ghost sector.

The proposal keeps runtime correlators lean. A correlator receives local operators and a compiled rule config: Wick rules, zero-mode rules, and the few convention constants needed by those rules. Boundary conditions, gluing, and doubling are used earlier when building the BCFT preset.

2. Free Boson Preset

The free boson is a bulk CFT sector parameterized by dimension, conventions, and target-space invariant data. Dimension is not a cosmetic label: it decides the vector representation, the metric/delta contractions, and whether epsilon-type \(SO(D)\) invariants are available. 

const FreeBosonSpec = struct {
    dimension: u16,
    alpha_prime: ConventionScalar,
    dX_normalization: ConventionScalar,
    vector_symmetry: TensorSymmetryRef,
    vector_rep: TensorRepRef,
    metric: TensorInvariantRef,
};

For the first implementation, vector_symmetry should be \(SO(D)\) with the vector representation. The tensor module should own identities such as \(\delta^\mu{}_\mu=D\), metric contractions, and optionally epsilon identities. The free-boson Wick rules should only ask tensor-code for those invariant handles and streamed contractions.

The bulk operator families are:

  • \(\partial^{n+1}X^\mu(z)\), represented as dX with a vector index and a nonnegative derivative label \(n\);
  • \(\bar\partial^{n+1}X^\mu(\bar z)\), represented as dXt;
  • \(:e^{ikX}(z,\bar z):\), with a momentum label in the vector dual;
  • holomorphic and antiholomorphic factorized exponentials when the client explicitly chooses a chiral presentation;
  • arbitrary \(X\)-profiles, with labels pointing to a symbolic target-space profile and to the target derivatives already taken.

The profile point is important. A profile is not a surface and not a special case in the correlator. It is an operator body whose label says “this body depends on \(X\) through a profile \(F(X)\)”, and whose Wick rule knows how to emit target derivatives such as \(\partial_\mu F\). 

const FreeBosonBodyLabel = union(enum) {
    dX: struct { mu: TensorIndex, derivative: u16 },
    dXt: struct { mu: TensorIndex, derivative: u16 },
    expX: struct { momentum: MomentumRef },
    expX_holo: struct { momentum: MomentumRef },
    expX_anti: struct { momentum: MomentumRef },
    profileX: ProfileLabel,
    profileX_holo: ProfileLabel,
    profileX_anti: ProfileLabel,
};

const ProfileLabel = struct {
    profile: ProfileRef,
    target_derivatives: ProfileDerivativeSpan,
};

This mirrors the prototype’s ProfileX[profile, ders, z, zbar], ProfileXHolo, and ProfileXAntiHolo. The new code should not expand profiles into polynomials unless a client later asks for that. The generic free-boson Wick rule emits symbolic target derivatives of the profile and leaves the target-space simplification to tensor-code or to the client.

3. Free Boson Wick Data

The sphere Wick rules are the local data:

  • \(dX^\mu dX^\nu\) gives a metric/delta tensor times derivatives of the holomorphic kernel;
  • \(dXt^\mu dXt^\nu\) is the antiholomorphic copy;
  • mixed \(dX dXt\) vanishes on the sphere;
  • \(dX^\mu\) contracts with \(e^{ikX}\) by emitting \(k^\mu\);
  • \(dX^\mu\) contracts with \(F(X)\) by emitting \(\partial_\mu F\);
  • exponential/profile pairs multiply by powers determined by target-space pairings such as \(k\cdot p\), \(k\cdot \partial F\), and \(\partial F\cdot\partial G\).

This is still ordinary Wick data. The only additional distinction is that some pairings are additive contractions, while exponential/profile pairings are multiplicative factors. That distinction belongs in the Wick rule table, not in the operator data structure. 

const WickRuleKind = enum {
    additive_pair,
    multiplicative_pair,
};

const WickRule = struct {
    left_kind: OperatorKindId,
    right_kind: OperatorKindId,
    kind: WickRuleKind,
    evaluator: WickEvaluatorRef,
};

The runtime correlator does not need to know that one of these rules came from a profile or a plane wave. It only needs to stream the rule’s emitted coefficient and residual operator bodies.

4. Weights And Conventions

The free boson must compute weights at runtime from labels:

  • \(dX^\mu_n\) has holomorphic weight \(1+n\);
  • \(dXt^\mu_n\) has antiholomorphic weight \(1+n\);
  • \(e^{ikX}\) has weights determined by the chosen \(\alpha'\) convention and \(k^2\);
  • profile weights are rule-defined. Initially they can be abstract unless the profile label supplies enough data to compute them.

The convention set should make it easy to change \(\alpha'\), the sign of the two-point function, and the normalization of \(dX\). These are preset conventions, not client-side rewrites of every Wick rule. 

const FreeBosonConvention = struct {
    alpha_prime: ConventionScalar,
    xx_green_sign: i2,
    dX_dX_prefactor: ConventionScalar,
    expX_weight_prefactor: ConventionScalar,
    boundary_expX_weight_prefactor: ConventionScalar,
};

For the first preset, the values can match the prototype. The point of this object is that Ashoke/Xi/other convention choices become data used by the rule builders, not forks of the operator representation.

5. bc System On The Sphere

The sphere \(bc\) ghost preset is a chiral first-order system with:

  • \(b(z)\), weight \(2\), ghost number \(-1\), fermionic;
  • \(c(z)\), weight \(-1\), ghost number \(+1\), fermionic;
  • optional antiholomorphic copy \(bt(\bar z),ct(\bar z)\) for closed-string calculations;
  • Wick kernel \(b(z)c(w)\sim 1/(z-w)\) with derivative labels handled by differentiating the kernel;
  • a sphere zero-mode/top-form rule for the three \(c\) zero modes.

The correlator engine should not hard-code \(\langle ccc\rangle\). It should receive a zero-mode rule saying that the surviving \(c\)-sector top form on the sphere is represented by three modes. From that, the familiar values such as \[ \langle c(z_1)c(z_2)c(z_3)\rangle =(z_1-z_2)(z_1-z_3)(z_2-z_3) \] are emitted by the zero-mode evaluator.

For the \(bc\) preset, this is private rule data behind the generic zero-mode evaluator: 

const BcTopFormData = struct {
    sector: SectorId,
    field_kind: OperatorKindId,
    modes: []const i16,
    normalization: ConventionScalar,
    kill_if_unpaired_kind_present: []const OperatorKindId,
};

This is the same physics as the prototype’s registered top-form VEV sector, but it is not a public coefficient variant. It is table data used by the bc_sphere_top_form zero-mode evaluator. The same private shape also works for the antiholomorphic \(ct\) copy.

6. Free Boson BCFT

The free-boson BCFT is compiled from the bulk free-boson preset plus a boundary condition. The bulk CFT spec remains boundary-free.

A Neumann/Dirichlet condition is most compactly encoded by a reflection matrix on the vector representation: \[ R^\mu{}_\nu = +\delta^\mu{}_\nu \quad \text{on Neumann directions},\qquad R^\mu{}_\nu = -\delta^\mu{}_\nu \quad \text{on Dirichlet directions}. \] Dirichlet directions may also carry a position \(x_0^\mu\). Neumann directions carry the ordinary momentum-conservation zero-mode rule. 

const FreeBosonBoundaryCondition = struct {
    name: []const u8,
    reflection: TensorExprRef,
    neumann_projector: TensorExprRef,
    dirichlet_projector: TensorExprRef,
    dirichlet_position: ?TargetVectorRef,
};

From this, the BCFT builder compiles:

  • boundary-local operator kinds such as \(dX_B^\mu(x)\), boundary exponentials, and boundary profiles;
  • mixed bulk-boundary Wick kernels;
  • disk/UHP zero-mode rules;
  • optional boundary-changing families for strings stretched between different Dirichlet positions or more general branes.

Boundary operators are chiral in the boundary CFT. A bulk operator remains bulk and may be chiral, antichiral, or both. The BCFT builder may use the doubling trick internally, but the runtime correlator only sees the resulting local operators and rule config.

7. Neumann And Dirichlet Boundary Operators

For Neumann directions, boundary \(X\)-dependent operators have a genuine zero mode along the brane. Boundary exponentials and boundary profiles may carry momentum/profile dependence in the Neumann subspace, and the disk zero-mode rule imposes the corresponding conservation law.

For Dirichlet directions, the zero mode is fixed by the brane position. Bulk closed-string exponentials near the disk can produce factors depending on \(x_0^\mu\), while boundary exponentials should not pretend that Dirichlet momentum is integrated. This distinction belongs in the BCFT zero-mode rule and in the allowed boundary operator families.

The stringbook convention that the boundary normal ordering differs from bulk normal ordering should be represented by the boundary Wick rule and boundary weight rule. In particular, the dimension of a boundary exponential is controlled by the boundary kernel and need not equal the sum of the bulk left and right weights. 

const BoundaryFreeBosonFamilies = struct {
    dX_boundary: OperatorKindId,
    expX_boundary: OperatorKindId,
    profileX_boundary: OperatorKindId,
    boundary_changing: []const OperatorKindId,
};

The factor of two relating \(\partial_y X(y)\) and the holomorphic boundary field in Neumann directions should be a convention in the BCFT preset. We should ask for sign-off before freezing that normalization.

8. Boundary bc Ghosts

The ghost BCFT is not Neumann/Dirichlet in the target-space sense. It is the standard boundary gluing of the holomorphic and antiholomorphic ghost systems, compiled into a chiral boundary \(bc\) system with disk zero modes.

For the first implementation, it is enough to support:

  • boundary \(b(x)\), \(c(x)\) with the same first-order Wick kernel;
  • disk/UHP top-form rule for the three boundary conformal Killing zero modes;
  • mixed bulk-boundary ghost rules only if an immediate open-closed amplitude calculation needs them.

This keeps the target-space Neumann/Dirichlet data attached only to the free boson and keeps the ghost boundary condition as ghost-sector BCFT data.

9. Correlator Algorithm Check

The existing correlator direction is sufficient if the config object is specific enough. The algorithm should be:

  1. Receive a collection of local operators and a CorrelatorConfig.
  2. Flatten multilocal input into local insertions without changing bodies.
  3. Stream over sectors and operator bodies; do not allocate a full expanded expression unless the caller explicitly asks for materialization.
  4. Apply zero-mode selection early when it can prove the correlator vanishes.
  5. Apply additive and multiplicative Wick rules by pair lookup on operator kinds and labels.
  6. Pass leftover uncontracted fields to the zero-mode rule.
  7. Emit coefficient/tensor/operator residual terms as a stream.

That gives enough data for:

  • free-boson sphere correlators with \(dX\), \(dXt\), \(e^{ikX}\), and arbitrary profiles;
  • sphere \(bc\) correlators, including derivative \(c\)’s and insertions at infinity once BPZ limits are implemented;
  • disk/UHP free-boson BCFT correlators for Neumann/Dirichlet directions;
  • boundary ghost correlators on the disk.

The OPE implementation can still be the projected OPE computed from correlators plus pairing data. For local bulk OPEs the sphere config is enough; for boundary OPEs the disk/BCFT config is enough.

10. Zero Modes And Coefficient Shape

The phrase “zero-mode rule” should mean the last evaluation step after Wick contractions. It is not only a selection rule. It consumes the residual uncontracted bodies in one sector and emits scalar coefficient factors. For the \(bc\) system this is finite Grassmann top-form saturation. For free bosons this is continuous zero-mode integration. For arbitrary profiles, the correct first implementation is to keep the zero-mode integral explicit.

The important data-shape decision is that Coefficient should not learn new physics every time a user defines a CFT. It should know how to multiply, add, stream, and canonicalize a small algebra of coefficient terms. Physics families such as \(\delta^D(\sum k_i)\), \(Z'_X(\Sigma)\), \(e^{-ikx_0}\), Green-kernel exponentials, and explicit profile zero-mode integrals should be opaque scalar factors owned by the theory preset or by the client. 

const CoeffTerm = struct {
    scalar: ExactScalar,
    coordinate_kernel: CoordinateKernelRef,
    tensor_factor: TensorExprRef,
    symbolic_factors: SymbolicFactorSpan,
};

const SymbolicFactor = struct {
    family: SymbolicFactorFamilyId,
    labels: LabelSpan,
};

This keeps the coefficient module tight. It does not need a public variant called momentum_delta or profile_integral. The user-defined factor family names the meaning. The coefficient engine only treats these as commuting scalar factors with optional family-supplied equality/canonicalization and printing.

The coordinate part remains narrow: rational powers of coordinate differences, and later the small set of algebraic coordinate kernels that are common enough to justify first-class storage. Torus prime forms, higher-genus Green functions, and explicit zero-mode integrals should begin life as symbolic factors, not as built-in coefficient syntax.

11. Zero-Mode Rule Shape

The correlator config should point to sector-wise residual evaluators. Each evaluator receives only the residual bodies from its sector, the already-collected scalar factors, and the minimal rule data needed for that sector. It returns a stream of coefficient factors, usually one term. 

const ZeroModeRule = struct {
    sector: SectorId,
    evaluator: ZeroModeEvaluatorRef,
    rule_data: RuleDataRef,
};

const ZeroModeInput = struct {
    residual_bodies: OperatorBodySpan,
    labels: LabelStoreRef,
};

const ZeroModeOutput = struct {
    factors: SymbolicFactorSpan,
};

Concrete free-boson rule families then become ordinary preset data:

  • free_boson_bulk_noncompact: sum all momenta carried by \(e^{ikX}\) and Fourier-profile bodies, emit the \(D\)-dimensional momentum delta, and leave arbitrary profile zero modes as an explicit integral;
  • free_boson_neumann_boundary: project momenta and profiles to Neumann directions, emit momentum conservation along the brane, and keep profile zero-mode integrals over Neumann zero modes when needed;
  • free_boson_dirichlet_boundary: project to Dirichlet directions and emit evaluation/phase factors at \(x_0\), with no Dirichlet momentum integration;
  • bc_sphere_top_form: localize the surviving \(c\)-ghost modes and emit the finite top-form normalization;
  • charge_background: handle bosonized charge-background rules such as \(\phi\), \(H_i\), or later lattice systems.

The zero-mode evaluator should not ask for the full surface object. It only uses the rule data already selected by the correlator config. A sphere free boson rule and a torus free boson rule may share operator bodies but emit different symbolic factors.

12. Momentum And Profiles

Momentum should be first-class enough to sum, project, and pair without expanding it into coefficient syntax. This is not a new tensor-code physics layer; it is a compact vector-expression handle used by free-boson operator labels and zero-mode rules. 

const MomentumLabel = struct {
    vector: VectorExprRef,
};

const ProfileZeroModeLabel = struct {
    profile: ProfileRef,
    argument_space: TargetSubspaceRef,
    target_derivatives: ProfileDerivativeSpan,
};

Tensor-Code should supply the vector algebra: \(SO(D)\) metric, projectors for Neumann/Dirichlet subspaces, dot products, and streamed simplification of linear vector expressions. It should not know that a vector expression is a momentum-conservation constraint. The free-boson zero-mode rule knows that.

For arbitrary profiles, the residual factor should be explicit. Schematically the free-boson bulk zero-mode rule can emit \[ \int d^D x_0\, F_1(x_0) \cdots F_r(x_0)\, \exp\!\left(i x_0\cdot\sum_j k_j\right), \] or the projected Neumann/Dirichlet analogue. If all profile labels are Fourier-like, a later user-side simplifier may collapse this to a momentum delta. The generic correlator should not require that collapse.

13. Minimal API Shape

The public API should stay close to the current kernel boundary. 

const FreeBoson = cft.presets.freeBoson(.{
    .dimension = 10,
    .conventions = .prototype,
});

const BosonicSphere = cft.presets.tensor(.{
    FreeBoson,
    cft.presets.bcSphere(.{}),
});

const DpBrane = cft.presets.freeBosonBoundary(.{
    .bulk = FreeBoson,
    .neumann = neumann_projector,
    .dirichlet = dirichlet_projector,
    .position = x0,
});

The generated theory should expose ordinary body builders and the two runtime operations: 

const O = BosonicSphere.op;

try BosonicSphere.correlator(&.{
    O.local(O.c(.{}, z1)),
    O.local(O.c(.{}, z2)),
    O.local(O.c(.{}, z3)),
}, BosonicSphere.config.sphere);

try DpBrane.correlator(&.{
    DpBrane.op.boundary(DpBrane.op.expXBoundary(k, x)),
}, DpBrane.config.disk);

This is schematic. The important boundary is that correlator receives operators plus a rule config, not a surface object, boundary-condition object, or gluing rule.

14. What Needs Sign-Off

Before implementing these presets, I need domain sign-off on four precise physics choices:

  1. Profile semantics: should ProfileX denote a general local functional \(F(X)\), a normal-ordered exponential-like insertion whose pairings are governed by \(\partial F\), or both via two profile operator families?
  2. Boundary free-boson normalization: should the boundary generator be named and normalized as \(\partial X(y)\), as \(\partial_y X(y)\), or should both be exposed with a fixed factor-of-two conversion?
  3. Dirichlet zero modes: should the first implementation allow boundary profile/exponential labels with Dirichlet components and let the zero-mode rule evaluate them at \(x_0\), or reject those labels at construction?
  4. Ghost boundary scope: for the first BCFT pass, do we need only boundary \(bc\) correlators on the disk, or also mixed bulk-boundary ghost insertions immediately?

My recommended implementation order is:

  1. tensor-code \(SO(D)\) vector invariant handles and dimension contraction;
  2. free-boson bulk operator families, labels, weights, and sphere Wick rules;
  3. profile labels and profile Wick rules;
  4. sphere \(bc\) top-form zero-mode rule and \(b c\) Wick rule;
  5. free-boson Neumann/Dirichlet BCFT compilation;
  6. boundary \(bc\) disk config.
